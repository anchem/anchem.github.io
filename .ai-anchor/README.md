# .ai-anchor —— 本站的认知锚点目录

这里存放**能够塑造稳定 AI 行为的信息资产**：项目现在是什么（全量锚点）、这次要改什么（增量锚点）、
以及让协作过程可观测 / 可追溯 / 可审计的过程记录。

方法论见 [`docs/selfdevelop/ability/ai/ai-collaboration-methodology.md`](../docs/selfdevelop/ability/ai/ai-collaboration-methodology.md)。

## 一、为什么是这个位置

- **和产物同源同版本**：锚点与 `docs/`、`blog/`、`src/` 在同一个仓库、同一条 git 历史里。
  锚点一旦脱离版本管理，第二天就开始过期。
- **必须被 git 跟踪**：不要把 `.ai-anchor/` 写进 `.gitignore`。它是资产，不是缓存。
- **不会被发布**：Docusaurus 只把 `static/` 复制进 `build/`，`.ai-anchor/` 既不会构建也不会部署。

## 二、目录层级

```
.ai-anchor/
├── README.md                    # 本文件：目录说明、命名规范、文件清单与作用
├── PROJECT.md                   # ① 全量锚点：本站的项目手册（十格）
├── DECISIONS.md                 # ④ 决策日志：一行一次裁决
├── ROLES.md                     # ⑤ 角色卡：协作者 / 评审者 / 人的裁决清单
├── TEMPLATES/                   # 空表模板，开一次新变更就复制一份
│   ├── CHANGE.md
│   ├── REVIEW.md
│   └── REPLY.md
└── changes/                     # 每次变更一个目录
    └── YYYY-MM-DD-<slug>/
        ├── CHANGE.md            # ② 增量锚点
        ├── REVIEW.md            # ③ 评审单
        └── REPLY.md             # 协作者对评审的回应
```

层级只有三层：**根（常驻资产）→ 分类目录（TEMPLATES / changes）→ 一次变更的目录**。
不再往下嵌套。一次变更就是一个目录，所有相关文件平铺在里面。

## 三、命名规范

| 对象 | 规范 | 例子 |
| --- | --- | --- |
| 常驻文件 | 全大写 + `.md`，名字即角色 | `PROJECT.md`、`DECISIONS.md`、`ROLES.md` |
| 变更目录 | `YYYY-MM-DD-<slug>`，日期用**变更开始**那天 | `2026-09-21-cognitive-anchors-publish` |
| 变更内的 slug | 小写英文 kebab-case，语义化，不用中文、不用数字前缀 | `piano-guide-price-scope` |
| 变更内三个文件 | 固定为 `CHANGE.md` / `REVIEW.md` / `REPLY.md`，**不改名** | — |

规则只有一条值得强调：**变更目录名一旦创建就不再改动**。它同时是变更的编号、决策日志的外键、
和事后追溯的入口；改名等于断链。

## 四、文件清单与作用

| 文件 | 对应锚点 | 谁写 | 作用 | 什么时候更新 |
| --- | --- | --- | --- | --- |
| `README.md` | — | 人 | 说清这套目录是怎么用的，让新人和 AI 都能自助上手 | 目录结构或命名规范变化时 |
| `PROJECT.md` | 全量锚点 | 人主导，AI 可起草 | 本站的"真相源"：定位、边界、概念、结构、**不变量**、流程、约定、取舍、权限、风险 | 每次归集（第⑤步）至少动一行 |
| `DECISIONS.md` | — | 人 | 一行一次裁决：谁产出、谁评审、人判了什么、依据、影响哪些锚点 | 每次归集追加一行，**只追加不改写** |
| `ROLES.md` | — | 人 | 三张常驻提示词，开新会话直接粘贴，不必每次重申角色 | 角色行为反复出问题时 |
| `TEMPLATES/CHANGE.md` | 增量锚点空表 | 人 | 开新变更时复制到 `changes/<变更目录>/` | 字段定义变化时 |
| `TEMPLATES/REVIEW.md` | 评审单空表 | — | 同上 | 同上 |
| `TEMPLATES/REPLY.md` | 回应空表 | — | 同上 | 同上 |
| `changes/<目录>/CHANGE.md` | 增量锚点 | 人起草，AI 补全 | 本次改什么、不改什么、怎么算完、碰不碰不变量 | ① 立锚起草、② 共创定稿 |
| `changes/<目录>/REVIEW.md` | — | AI 评审者（独立模型） | 把风险、偏离、分歧整理成人能判断的材料 | ④ 校核 |
| `changes/<目录>/REPLY.md` | — | AI 协作者 | 逐条回应阻断项，接受或给出反驳理由 | ④ 校核末 |

## 五、一次变更的生命周期

1. **建目录**：`changes/$(date +%F)-<slug>/`，把 `TEMPLATES/` 三个文件复制进去。
2. **定车道**：读 `PROJECT.md` 第五格「不变量清单」，回答一个问题——这次动的东西在不变量里吗？
   - 不在 + 影响面小 + 可回滚 → **快车道**（跳过共创）
   - 不在，但影响面不小 → **标准道**
   - 在 → **改道**：先单独开一轮把 `PROJECT.md` 改掉，再回来做原变更
3. **走步骤**：按车道的步骤填 `CHANGE.md` → 出制品 → 填 `REVIEW.md` → 填 `REPLY.md`。
4. **归集**：
   - 更新 `PROJECT.md` 被本次变更改动的格子；
   - 在 `DECISIONS.md` 追加一行；
   - 变更目录**保留不删**，它就是这个变更的审计记录。

**只有人能做的三件事**：判定车道、填写「非目标」与「待裁决」、在归集时下裁决。
AI 可以起草这三样，但必须由人确认后才算成立。

## 六、和其他目录的边界

| 目录 | 是什么 | 谁看 | 是否入库 |
| --- | --- | --- | --- |
| `.ai-anchor/` | **项目的真相**：稳定、可复用、给 AI 和人共读的锚点 | 人 + AI | 是 |
| `.workbuddy/` | **助手的工作件**：记忆、草稿、评审过程、临时脚本、快照 | 只有助手 | 否（已 gitignore） |
| `build/`、`build_old*/` | 构建产物，可随时重建 | 部署用 | 否 |

判断一个文件该放哪：**「半年后接手的人是否需要读它」——需要，放 `.ai-anchor/`；不需要，放 `.workbuddy/`。**

## 七、开工前的最小检查

```text
[ ] PROJECT.md 存在，且第五格「不变量清单」非空
[ ] 本次变更的目录已建，三个文件已复制
[ ] 车道已判定，并写进了 CHANGE.md
[ ] 出口条件都满足（见 PROJECT.md 第六格「关键流程」）
[ ] 本次用了哪个模型做协作者、哪个做评审者，已记进 DECISIONS.md
```
