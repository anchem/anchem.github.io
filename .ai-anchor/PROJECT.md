## 一、定位：这是什么，为谁而做

**倚码千言**（`https://codethousand.cn`）是一个**个人知识与写作站点**。

- **第一读者是作者自己**：它首先是一个把思考固化下来的地方，其次才是一个公开站点。
- **第二读者是同行**：写代码的人、做父母的人、想长期学习的人。
- **它不是一个产品**：没有用户系统、没有注册登录、不做商业化、不追增长指标。
- **它存在的意义**：让作者能长期、公开、诚实地写下去。任何设计决策若与此冲突，以此为准。

## 二、边界：它不做什么

明确写下"不做什么"，比写下"做什么"更能省事——边界之外的东西，AI 和人都不必再讨论。

- 不引入后端服务、数据库、登录体系；站点是**纯静态**的。
- 不引入需要长期运维或持续付费续期的依赖（现有例外：Algolia 搜索、Google Analytics、百度统计）。
- 不做 SEO 作弊手段（关键词堆砌、隐藏文本、内容农场式批量生成）。
- 不为追热点牺牲已发布文章的口径；**旧文可以改准，不可以被新文推翻后不改**。
- 不把工作件发布到站点：草稿、蓝本、评审记录、锚点目录一律留在仓库外或 `.workbuddy/`。
- 不发布他人未授权的内容；转载必须标注来源与许可。
- 不删除已发布文章。确需下架时，保留文件并在文中说明，不做静默消失。
- 不做需要人工持续盯守的功能（如实时评论、实时数据看板）。

## 四、结构与模块

```text
anchem.github.io/
├── docusaurus.config.js      # 站点配置：导航、主题、插件、构建期数据注入
├── sidebars.js              # 四个 sidebar，全部 autogenerated
├── package.json             # Docusaurus 3.10.0 / React 19 / node >= 20
├── CNAME                    # 自定义域名，不可删
├── docs/                    # 知识库（222 篇 md）：四个板块
│   ├── softwaremaster/      # 软件大师之路
│   ├── selfdevelop/         # 个人成长：health / cognition / ability / outlook 四维
│   ├── growthtree/          # 阿不成长树：classification（能力树）+ timeline（时间轴）
│   └── lifeforfun/          # 为乐而生：music / invest / basketball / drama
├── blog/                    # 随笔：YYYY-MM-DD-<slug>.md + authors.yml
├── src/
│   ├── pages/               # 首页 index.js、随想 thoughts.js、关于 about.md
│   ├── components/          # 首页书架、最新随笔、随想轮播、天空层、季节装饰、分节标题
│   ├── config/              # homepageData.js（构建期统计）、shelves.js、prismThemes.js
│   ├── hooks/               # useThoughts.js
│   ├── theme/Root.js        # 全站背景层的挂载点
│   └── css/custom.css       # 色令牌与全站样式（§1 是唯一色源）
├── static/                  # img/、js/、域名校验文件，原样复制进 build
├── i18n/                    # zh-Hans（当前只有一种语言）
└── .ai-anchor/              # 本目录：项目锚点，不参与构建
```

**依赖方向**：`docusaurus.config.js` → `src/config/*`（构建期注入）→ `src/components/*`（渲染期消费）；
`docs/` 与 `blog/` 是纯内容，只被 Docusaurus 读取，彼此之间只有链接关系，没有代码依赖。
**改动风险最高的是 `docusaurus.config.js` 与 `src/css/custom.css`**，一次误改会影响全站每一页。

## 五、不变量清单 ★

这是本手册的灵魂。**改动清单中的任何一条，都必须走「改道」：先单独开一轮把本文件改掉，再做原变更。**

| # | 不变量 | 为什么（破了会怎样） |
| --- | --- | --- |
| 1 | 四个板块的目录名不可改：`softwaremaster`、`selfdevelop`、`growthtree`、`lifeforfun` | 目录名即 URL。改名等于全站外链一次性失效 |
| 2 | 站点名「倚码千言」、站点 URL `https://codethousand.cn`、根目录 `CNAME` 文件不可改 | 域名与站点身份；动了搜索引擎与已有外链全部重来 |
| 3 | 每个 docs 目录必须有 `_category_.json` 与 `index.md`，且 `index.md` 不能是空壳 | 缺配置 → sidebar 显示目录名；空壳 index → 首页书架统计虚高 |
| 4 | 排序只用 `sidebar_position`；目录名与 `label` 中不出现数字前缀 | 数字前缀会泄漏到 URL 和面包屑里，且改名即换链接 |
| 5 | docs 内 front matter 键位固定：`sidebar_position` / `title` / `tags`（长文另加 `description` / `keywords`） | 键位不统一会让搜索索引与卡片渲染行为不一致 |
| 6 | 随笔 front matter 固定五键：`slug` / `title` / `date` / `authors` / `tags`；正文首行重复 H1 | blog 插件按这套字段取摘要、作者与排序，缺一个就渲染异常 |
| 7 | 随笔中的站内链接一律写绝对路径 `/docs/...` | blog 不在 docs 文件树里，相对 `.md` 链接无法解析 |
| 8 | 色令牌只在 `src/css/custom.css` §1 定义；深色选择器必须写 `html:root[data-theme='dark']` | 色值散落会让明暗两套主题打架；选择器写浅了赢不了级联，深色主题静默失效 |
| 9 | 天空层切换只切 `opacity`，不切 `background-image` | 切图会导致深色下背景闪烁与重绘抖动 |
| 10 | `build/`、`build_old*/`、`node_modules/`、`.docusaurus/` 是产物，永不手工编辑 | 它们是生成物，改了会被下一次构建覆盖，且掩盖真实来源 |
| 11 | `trailingSlash: false` 下所有内链不带结尾斜杠 | 带斜杠会触发一次重定向，且部分外链校验会失败 |
| 12 | MDX 正文中的 `<` `>` 必须转义；表格单元格内的 `|` 写作 `\|`；admonition 不插在表格中间 | 这三条会让 `npm run build` 直接失败 |

## 六、关键流程

### 6.1 写作与发布（一次内容变更）

```text
选题与定位 → 素材与数据核查 → 初稿 → 自我校验 → 落盘 → 构建验证 → 部署
```

| 环节 | 出口条件（门禁） |
| --- | --- |
| 定位 | 能一句话说清这篇写给谁、读完他能带走什么 |
| 素材核查 | 所有硬数据都有出处；无法核实的数字宁可留白 |
| 初稿 | front matter 键位齐全；标题层级连续；表格与 admonition 位置合法 |
| 自我校验 | 链接全部命中；MDX 无裸 `<` `>`；文风自检通过 |
| 落盘 | 文件落在既有目录，**不新建目录**（新建目录要走 6.3） |
| 构建验证 | 本地构建 exit 0，且新增页面的 URL 出现在 `build/sitemap.xml` |
| 部署 | 推到 `gh-pages`；若失败，回滚到上一个可用提交 |

### 6.2 校验与构建（本机操作口径）

```bash
# 链接与锚点体检（递归，当前 222 篇）
node .workbuddy/check-doc-links.js docs

# 构建：先把旧产物移开，不要直接删 build/
Rename-Item build build_old
node node_modules/@docusaurus/core/bin/docusaurus.mjs build
```

**为什么先改名**：本机的 safe-delete 守卫会拦住构建清空 `build/` 的动作并挂住进程。
移开旧产物是唯一合规的绕法；`build_old*` 删不掉就留着，**不要绕过守卫**。

**验链最便宜的办法**：不跑构建，直接在 `build/sitemap.xml` 里查目标路径是否存在。

### 6.3 结构与目录变更（高风险）

```text
新增/移动/重命名目录 → 同步 _category_.json 与 index.md → 全量修复站内链接 → 重跑链接体检 → 构建验证
```

任何一步没做完都不算完成。尤其是**第三步**：目录一动，跨目录的相对链接会集体失效，
必须全量扫描而不是只看改动的文件。

### 6.4 与 AI 协作（回到本目录）

```text
① 立锚（人，CHANGE.md 草案）→ ② 共创（强模型补全）→ ③ 执行（成本模型出制品）
→ ④ 校核（独立模型出 REVIEW.md ⇄ 协作者 REPLY.md）→ ⑤ 归集（人裁决 + 更新本文件 + DECISIONS.md 落一行）
```

车道判定、文件清单与生命周期见 [README.md](README.md)。

## 八、设计取舍记录（ADR）

每条三行：选了什么 / 放弃了什么 / 为什么。

**ADR-001 sidebar 全部用 autogenerated**
选：`sidebars.js` 只声明四个 `dirName`，顺序由文件系统的 `_category_.json` 与 `sidebar_position` 决定。
放弃：手写 sidebar 带来的精细控制（插入外链、切分组、跨板块混排）。
为什么：手写 sidebar 每加一篇文档都要改两处，长期必然漂移；目录结构本身就是最好的导航结构。

**ADR-002 主题双轨，默认浅色且不跟随系统**
选：浅色「春晓」+ 深色「夜幕」两套完整皮肤，`respectPrefersColorScheme: false`。
放弃：跟随系统偏好。
为什么：这个站点的视觉表达本身就是内容的一部分，作者的默认选择必须稳定可控；
让系统替你决定，等于让一半访客看不到作者本意。

**ADR-003 首页数据在构建期算**
选：`customFields.homepageData = buildHomepageData()`，构建时扫描 docs/blog 算出书架与摘要。
放弃：运行时请求接口或读取静态 JSON。
为什么：纯静态站点不该为了首页多一次网络往返；构建期计算让数据必然与内容一致，不会出现"内容发了但书架没变"。

**ADR-004 构建产物不删，只移开**
选：`Rename-Item build build_old` 后再构建。
放弃：直接清理 `build/`。
为什么：本机安全守卫不允许递归删除，绕过它带来的风险远大于省下的磁盘空间。

**ADR-005 链接校验不依赖构建**
选：先在 `build/sitemap.xml` 里查路径，必要时再用 `.workbuddy/check-doc-links.js` 做全量体检。
放弃：每次改文都跑一次完整构建。
为什么：一次构建两分多钟，而绝大多数链接问题在 sitemap 里就能判定；把昂贵校验留到发布前。

**ADR-006 随笔的 slug 与文件名解耦**
选：文件名带日期（排序友好），`slug` 单独声明（URL 友好）。
放弃：用文件名直接生成 URL。
为什么：`/blog/2026-09-21-xxx` 这类 URL 又长又脆；解耦后改名不影响外链。

**ADR-007 锚点目录放在仓库根，且必须入库**
选：`.ai-anchor/` 与 `docs/`、`blog/` 同仓库同版本。
放弃：放进已 gitignore 的 `.workbuddy/`。
为什么：锚点一旦脱离版本管理，就无法回答"这句话是哪个版本的项目说的"，第二天就开始过期。

## 九、权限与红线

### AI 可以自主决定（不必请示）

- 在既有目录内新增文章、补 `index.md` 导览；
- 修错别字、断链、标点、格式、表格对齐；
- 运行链接体检与只读检查；
- 起草 `CHANGE.md` / `REVIEW.md` / `PROJECT.md` 的更新建议；
- 更新 `.ai-anchor/` 下的锚点文件（不变量章节除外）。

### 必须请示人（停下来问，不要自己拍板）

- 触碰第五格「不变量清单」中任何一条；
- 改 `docusaurus.config.js`、`sidebars.js`、`package.json`；
- 改 `src/css/custom.css` 的色令牌、`src/theme/Root.js`、任何 `src/components/`；
- 新增、删除、重命名、移动任何目录；
- 批量重构（一次涉及 5 个以上文件）；
- 删除任何已发布的文章或文件；
- 执行部署，或修改 `CNAME`。

### 红线（任何情况下都不做）

1. 编辑 `build/`、`build_old*/`、`node_modules/`、`.docusaurus/` 下的任何文件。
2. 绕过本机的 safe-delete 守卫去删除文件。
3. 把工作件（草稿、蓝本、评审记录、锚点目录）发布进 `docs/` 或 `blog/`。
4. 为了让构建通过而删掉报错的内容——**先弄清为什么报错，再改内容**。
5. 在未读 `PROJECT.md` 的情况下开始改动本项目。

## 附：本文件的维护规则

- **只写"现在是什么"，不写"曾经是什么"**：历史留在 git 与 `DECISIONS.md`，本文件永远描述当前状态。
- **不变量一经写明就不轻易改**：要改，走「改道」并在 `DECISIONS.md` 留下理由。
- **宁可写得粗糙，也不要空着**：第五格（不变量）与第九格（权限与红线）宁可先写错，也不能留白——
  空白等于把判断责任交给 AI。
