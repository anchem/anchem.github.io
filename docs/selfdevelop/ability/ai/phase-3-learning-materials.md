# 阶段三学习材料：创造 MVP（约 3 周）

本材料是《[一人公司的 AI 实战进阶计划（AI Agent 学习路线）](ai-agent-one-person-company-plan.md)》第三阶段的配套学习内容。

这三周要把一张卡片变成一件真实存在、别人能自己打开使用的东西。判断标准只有一个：找一个不认识你的人，不解释，让他自己用起来。

动手前认清两件事：第一版一定丑，能用比好看重要；卡住是常态，不是你的问题，卡住时该做的是缩小范围，不是硬扛。

## 零、开始之前 {#before-start}

### 0.1 前置检查 {#prereq}

- [ ] 你的产品机会卡片七栏已填满，其中第②栏用的是用户原话；
- [ ] 你有 ≥ 1 个愿意深度试用的承诺者（阶段二留下的名单）；
- [ ] 你已确定产品形态与开发路线（[见决策树](#route-tree)）；
- [ ] 你接受"三周后交出来的东西可能只完成一半"，这正常，不算失败。

### 0.2 别把第一天耗在注册上 {#signup-tips}

零基础者最容易忽略的一道隐形门槛是账号与资质：

| 门槛 | 你需要先确认的事 |
| --- | --- |
| 实名认证 | 多数国内平台需要绑定手机号，部分功能需实名（身份证） |
| 免费额度 | 额度会变化，注册当天就记进 `00-工具箱.md` |
| 企业资质 | 涉及支付、收款、小程序发布等功能往往需要企业主体；第一版请绕开需要企业资质的路径（如用"留联系方式"代替在线支付） |
| 域名与备案 | 用平台自带的一键部署域名通常不需要；自己买域名指向国内服务器需要备案，第一版不建议自购域名 |
| 发布时间 | 小程序类存在审核周期，不要把它排在最后两天做 |

### 0.3 时长节奏 {#rhythm}

[逐日清单](#daily-plan)按每周约 8 小时设计：

| 节奏 | 每周投入 | 怎么用 |
| --- | --- | --- |
| 保命档 | 约 5 小时 | 用[最小版本](#daily-plan)：只做"输入 → 输出"两个功能，10 天交付 |
| 标准档 | 约 8 小时 | 按二十一天清单走 |
| 加速档 | 12 小时以上 | 加做一次可用性测试 + 把视觉包装做得更完整 |

## 一、本阶段学习目标 {#goals}

| 维度 | 三周后达标线 | 对应本材料章节 |
| --- | --- | --- |

## 二、开发路线：先选对路，再动手 {#route}

### 2.1 三种起步形态与对应工具 {#forms}

| 形态 | 是什么 | 适合谁 | 2026 年推荐工具 | 预计上手难度 |
| --- | --- | --- | --- | --- |
| 信息产品 | 电子书、课程、模板包、付费专栏 | 有内容/经验积累的人，最快启动 | 腾讯文档 / WPS AI（写与排版）、Canva 可画 / 稿定（封面与版式） | 最低 |
| 网页小工具 | 一个解决具体问题的网页应用 | 想做出"可交互的东西"的人 | 秒悟 Meoo / 百度秒哒（无代码）；Trae / 通义灵码（AI 编程） | 中 |
| 自动化服务 | 用 Agent 帮客户做重复工作 | 手上已有客户或明确需求的人 | 扣子（Coze）工作流 + 飞书/金山表格；影刀 RPA | 中 |

怎么选：先问自己三个问题。手上已经有什么？有内容积累选信息产品，有明确客户选自动化服务，都没有但有想法选网页小工具。想不想碰代码？完全不想走无代码，愿意花时间学走 AI 编程。三周内最能交付的是什么？最诚实的答案是"最小的那一个"，宁可做小不要做大。

### 2.2 路线决策树 {#route-tree}

```text
你的 MVP 是什么？
├─ 主要是"知识/经验/模板"类内容
│   └─ → 信息产品：腾讯文档 / WPS AI 排版 + Canva 封面
│
├─ 是一个"输入 → 处理 → 输出"的小工具，逻辑简单
│   ├─ 完全不想写代码 → 秒悟 Meoo / 百度秒哒（说话生成全栈应用，一键上线）
│   └─ 愿意学一点     → Trae（SOLO 模式）/ 通义灵码
│
├─ 需要"实时对话/自动应答/编排多步流程"
│   └─ → 扣子（Coze）：Bot + 知识库 + 工作流
│
└─ 是"帮某类客户做重复劳动"的服务
    └─ → 扣子工作流 + 人工交付；或 影刀 RPA 处理固定桌面操作
```

### 2.3 三条路线的具体起步步骤 {#route-steps}

路线 A：无代码生成（零基础优先）

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1 | 打开秒悟 Meoo 或百度秒哒，注册登录 | 都用手机号，有免费额度 |
| 2 | 用一段话说清你要什么：谁用、解决什么、有哪几个页面、每页放什么 | 这段话的写法见[第三章 3.3](#prompt-for-gen) |
| 3 | 生成后立即预览，逐个功能点一遍 | 生成快，但第一版一定有不合意的地方 |
| 4 | 用逐条修改的方式提意见："登录页去掉手机号，只要邮箱" | 一次只说一件事，改完再看 |
| 5 | 满意后一键部署，拿到可分享的公网链接 | 这一步无代码平台的优势 |
| 6 | 让 2 个朋友打开链接试一下 | 见[第七章](#usability) |

路线 B：AI 编程（愿意投入时间者）

先做 1 天热身，热身不通过就不要进入正式开发。

| 热身步骤 | 做什么 | 通过标志 |
| --- | --- | --- |
| 1 | 用 Trae（或通义灵码）打开一个空文件夹 | 工具就绪 |
| 2 | 说"帮我做一个网页，上面有一个按钮，点一下显示当前时间" | 生成代码并能在本地预览 |
| 3 | 故意让它报错：改成"点一下显示昨天北京时间，带时区" | 出现报错或结果不对 |
| 4 | 把报错原文完整贴回去，说"先解决这个报错，不要改别的地方" | 它修好，你看到"生成 → 报错 → 丢回去 → 跑通"的完整循环 |
| 5 | 复盘：刚才那一轮你做了什么、它做了什么 | 能说清这个循环 |

热身通过的标准：你不再害怕报错，知道"报错原文 + 一句约束"就是最好的提问。

路线 C：扣子 Bot / 工作流

| 步骤 | 操作 |
| --- | --- |
| 1 | 新建 Bot，写清人设、语气、边界（[阶段二的任务书写法](phase-2-learning-materials.md#briefs)照样适用） |
| 2 | 建知识库，上传你的资料（产品说明、FAQ、模板），开启自动调用 |
| 3 | 加插件（搜索、时间等），必要时加工作流（收集信息 → 写进表格 → 通知你） |
| 4 | 右侧对话测试：正常问题能答、超纲问题会拒答或转人工、多轮不串台 |
| 5 | 发布到可用渠道，拿到可分享入口 |

扣子这类平台里，上下文长度与知识库切片方式会直接影响回答质量。文档排版越清晰（标题分层、一段一件事），检索命中率越高。上传前花 10 分钟整理资料来源，比上线后反复调提示词有效得多。

## 三、需求拆解：从想法到 3～5 个功能 {#scope}

### 3.1 拆解四步法 {#scope-steps}

| 步骤 | 做什么 | 时长 | 输出 |
| --- | --- | --- | --- |
| 1. 写全量 | 把"想要的功能"全部写出来，不设限（通常 15～30 条） | 30 分钟 | 功能清单 |
| 2. 划红线 | 逐条问："没有它，用户是不是就完全用不了？"不是就砍掉 | 30 分钟 | 红线功能（通常 2～4 条） |
| 3. 定闭环 | 把红线功能串成一条最短可用路径：用户从进入到最后拿到结果要走哪几步 | 30 分钟 | 一条 3～5 步的路径 |
| 4. 排顺序 | 按"没有它就走不通"排序，形成开发顺序 | 15 分钟 | 开发排期 |

### 3.2 一个完整的拆解示例 {#scope-example}

想法：一个帮技术组长整理周报的网页工具。

| 步骤 1：全量清单（18 条） | 步骤 2：划线判断 |
| --- | --- |
| 用户注册登录 | ✂ 砍——第一版不注册，用本地存储 |
| 粘贴零散记录 | ✅ 红线——没有它什么都做不了 |
| 一键生成结构化周报 | ✅ 红线——这是产品本身 |
| 可编辑生成结果 | ✅ 红线——AI 一定会出错，必须能改 |
| 导出 Markdown / 复制 | ✅ 红线——用户要拿去用 |
| 历史记录列表 | ⏸ 延后——第二版 |
| 周报模板可切换 | ⏸ 延后 |
| 团队共享 | ⏸ 延后 |
| 数据统计图表 | ✂ 砍——没人要求过 |
| 付费订阅 | ⏸ 延后——先用"加微信"测意愿 |
| ...（其余 8 条同理） | —— |

步骤 3：最短可用路径

```text
打开网页 → 粘贴零散记录 → 点生成 → 看到结构化周报 → 复制走
       （4 步，其中 2 步是用户操作、1 步是系统、1 步是用户取用）
```

步骤 4：开发顺序

1. 页面骨架 + 粘贴框（1 天）
2. 接入模型，粘贴能出结果（1～2 天）
3. 结果可编辑（1 天）
4. 复制 / 导出（半天）
5. 打磨：加载状态、错误提示、手机端能看（2～3 天）

### 3.3 给无代码平台的"生成提示语"模板 {#prompt-for-gen}

```text
帮我做一个网页应用，名字叫"______"。使用者是______。
它要解决的是：______。

页面只有 1 个，从上到下依次是：
1. 顶部标题和一句说明；
2. 一个大的多行输入框，提示文字是"把你这周的零散记录粘进来"；
3. 一个"生成周报"按钮；
4. 下方一个结果区域，生成后显示整理好的内容，可以直接编辑；
5. 一个"复制"按钮。

不需要登录、不需要数据库、不需要历史记录。
风格：干净、留白多、按钮明显、手机上也好看。
```

迭代时的提意见模板：

```text
只改一处：______（具体到哪个元素、改成什么）。
其他所有部分保持不动。
改完告诉我改了哪里。
```

:::warning 不提"再优化一下"
"优化一下""让它更好看"这类指令必然带来大面积改动，可能把你已验收的部分改坏。每一轮都要能说清"改了哪一处"。
:::

## 四、Agent 化开发：小步快跑的循环 {#dev-loop}

### 4.1 循环的四步与每步的验收动作 {#loop}

| 步骤 | 你做什么 | 验收动作 | 用时占比 |
| --- | --- | --- | --- |
| 拆需求 | 从开发顺序里取下一个最小改动 | 用一句话说清这一轮要改什么 | 5% |
| Agent 生成 | 把这一件事写清楚给 Agent，附上"不要改别的地方" | 看它改了几个文件，超出范围就让它回退 | 15% |
| 人验收 | 实际点一遍——不是看代码，是用一遍 | 记录"能用/不能用/哪一步卡" | 20% |
| 迭代 | 有问题就贴报错或现象；没问题就进入下一个最小改动 | 通过后立刻备份这一版 | 60% |

生成 15%、验收 20%、调试迭代 60%，这个比例和多数人的直觉相反，记住它你就不会在第三小时怀疑自己。

### 4.2 提问模板（开发专用）{#dev-prompt}

让 Agent 加一个功能

```text
【当前状态】现在页面能做到：______（一句话）。
【只做这一件事】请增加：______。
【不要动】不要修改______和______，不要重构现有代码。
【做完告诉我】改了哪些文件、怎么验证这一处能工作。
【如果有报错】把报错原文贴回来，先解决报错，不要绕过它。
```

出了问题时

```text
【现象】我点______，结果是______，我期望的是______。
【报错原文】
（完整粘贴，不要截断、不要改写）
【我的判断】我怀疑问题在______，但不确定。
【要求】先告诉我可能的原因（不超过 3 条），我确认后再改代码。
```

### 4.3 备份纪律（必需）{#backup}

| 做法 | 适合谁 | 具体操作 |
| --- | --- | --- |
| 手工另存 | 无代码平台用户 | 每完成一个可用版本，在平台内"复制一份"，命名 `v1-可用-日期` |
| 文件夹快照 | AI 编程新手 | 每完成一个可用版本，把整个项目文件夹复制一份并改名 |
| Git 提交 | 愿意学一点的人 | 用 Trae/通义灵码的对话让它帮你执行 `git init` 与提交；每验收通过一次就提交一次 |

:::warning 最少做到"手工另存"
不要在没有备份的版本上让 AI 做大改动，这是初学者最常发生的灾难：让它"重新生成一遍"，结果把已经调好的部分全改坏了，而且没有退路。
:::

## 五、包装：让它看起来像个东西 {#packaging}

### 5.1 包装四件套与做法 {#packaging-list}

| 元素 | 做什么 | 推荐工具 | 注意 |
| --- | --- | --- | --- |
| 产品名 | 好记、好念、能搜到 | 让 AI 出 20 个候选，你挑 3 个，问 5 个人 | 避开已有商标与大厂产品名 |
| 一句话说明 | 我帮谁解决什么，怎么做 | 让 AI 出 10 个版本，你改 | 不超过 40 字，说人话 |
| Logo / 视觉 | 一个图形 + 一套配色 | 即梦 / Canva 可画 / 稿定 | 商用前确认授权 |
| 界面文案 | 按钮、提示、空状态 | 让 AI 按你的语气写，你再改 | 提示语要告诉用户"下一步做什么" |

### 5.2 界面文案的三个关键位（最容易被忽略，影响最大）{#ui-copy}

| 位置 | 反例 | 正例 |
| --- | --- | --- |
| 输入框提示 | "请输入内容" | "把你这周的零散记录粘进来，一句话一行也行" |
| 按钮文字 | "提交" | "生成周报" |
| 空状态 | （空白） | "还没有内容。先用上面的框试一条，看看效果。" |
| 出错提示 | "错误：500" | "生成失败了。可能是网络问题，请再点一次；如果一直失败，把这段话发我。" |

### 5.3 商用版权：四条自查 {#copyright}

:::warning 商用素材四条自查
1. 图像：生成式平台的条款是否允许商用？免费档生成的内容授权是否不同？
2. 字体：界面与封面用的字体是否免费商用？中文字体是重灾区，很多"免费"字体只免费个人使用；
3. 图标/素材：图标库的授权类型（是否需署名）；
4. 代码：AI 生成的代码可能包含开源片段，注意许可证要求。

做不到全部确认时，选最保守的方案：用平台自带字体与素材、用自己生成且标明可商用的图。第一版不需要完美，但需要干净。
:::

## 六、上线：拿到可分享的链接 {#deploy}

| 你的形态 | 上线方式 | 具体做法 |
| --- | --- | --- |
| 无代码生成的应用 | 平台内一键部署 | 秒悟 Meoo / 秒哒 生成后点击部署，得到公网链接 |
| 自己写的静态网页 | 静态托管 | GitHub Pages / Vercel / Netlify；让 AI 帮你写部署步骤 |
| 需要后端的小应用 | 云服务 | 阿里云/腾讯云轻量服务器；或微信云开发 |
| 扣子 Bot | 平台内发布 | 发布为网页挂件或对应渠道，拿到分享入口 |
| 信息产品 | 文档或 PDF | 腾讯文档 / WPS 生成分享链接，设置权限 |
| 自动化服务 | 不需要链接 | 交付物是"跑出来的结果"，但要有演示记录（截图/录屏） |

:::warning 上线前的三件小事
1. 在手机上打开一次，很多第一版在手机上完全错位；
2. 换一个没登录你账号的浏览器打开，确认不需要你的登录态；
3. 把链接发给一个朋友，看他能不能打开，本地预览可以、公网打不开是常见问题。
:::

## 七、验收：可用性测试与付费验证 {#usability}

### 7.1 可用性测试五步法（本阶段最重要的一小时）{#usability-steps}

| 步骤 | 做什么 | 关键纪律 |
| --- | --- | --- |
| 1. 找 1～2 个不认识你（或只认识但不了解这个项目）的人 | 熟人可以，但要严格保密项目背景 | 不要选"怕伤你面子"的人 |
| 2. 只给一句话任务："请用它完成______" | 不解释、不演示、不指路 | 你一旦开口，数据就失效了 |
| 3. 全程闭嘴观察，记录三件事 | ① 他先点了哪里；② 他在哪里停了超过 10 秒；③ 他问了什么问题 | 他的每一个问题都是产品缺陷 |
| 4. 结束后再问三句 | "你觉得这是干什么用的？""哪一步最别扭？""你会再来用吗？" | 只听，不辩解 |
| 5. 当天把卡点整理成一张清单，按"人数 × 严重程度"排序 | 下一个迭代就改排名第一的 | 不改你的判断，只改产品 |

找不到陌生人时，按可行性顺序试这几个渠道：

| 渠道 | 具体话术 | 特点 |
| --- | --- | --- |
| 阶段二的承诺者 | "上次你说愿意试试，我做出来了，能麻烦你花 15 分钟用一下吗？" | 最顺，但不算"陌生人"，结论要打折扣看 |
| 互测社群 | "我在做一个 XX，想找 3 个人互测——你出测试任务我帮你测，我出测试任务你帮我测。" | 有效，双方都受益，最容易约到 |
| 垂直社群 | 先答别人的问题，几次之后再提："做了个小工具，想找人挑毛病，谁方便？" | 慢，但反馈最真实 |
| 熟人转介绍 | "你身边有没有做 ______ 的人？我想找 1 位帮我看看，15 分钟就行。" | 质量高，一次只求一个人 |
| 公开招募 | 在内容里发一条："我做了个东西，前 3 位愿意用的，帮我记 3 个卡点就行。" | 能拿到真正的陌生人，但需要内容已有一定曝光 |

最低要求是 1 位不了解这个项目的人。如果只能找到熟人，严格执行"不解释、不演示"，把熟人当陌生人用，数据依然有效。

| --- | --- | --- | --- | --- | --- |
| 1 | | | | | |

:::warning 千万别做"场外提示"
看到对方卡住时，你会有强烈的冲动想提醒。忍住。你提醒一次，就永远不知道真实情况；而真实的卡点，在你的 10 个陌生用户身上会重复出现 10 次。
:::

### 7.3 付费验证 {#pay-check}

一级（可用性）通过后，再往前走一步。三种可用的轻量做法：

| 做法 | 怎么做 | 拿到什么证据 |
| --- | --- | --- |
| 明确表态 | 问："如果正式版收 ____ 元，你会买吗？" | 意愿级 |
| 等待名单 + 定金 | 在页面上放"正式版开放时通知我"，愿意留联系方式；进一步可收可退定金 | 关注级 / 承诺级 |
| 反向验证 | 把链接发给 5 个人，说"这是要收费的，你觉得值多少？" | 价格区间 + 意愿级 |

拿不到付费证据时，常见原因有三类，各自对应不同处置：

| 卡在哪里 | 可能的原因 | 下一步 |
| --- | --- | --- |
| 有人用，但都说"免费的话会用" | 价值不够稀缺，或人群不对 | 换人群，或把价值做成"省下来的时间/钱"可量化 |
| 没人愿意点开链接 | 一句话说明没讲清，或渠道不对 | 重写说明，换渠道（阶段四解决） |
| 用了一次就不再用 | 没有"反复使用"的理由 | 找"高频场景"重做功能，或改成一次性交付物 |

假装乐观没有价值。把这三类原因如实写下，阶段五才有依据。

### 参考答案与解析 {#answer-key}

练习 1 参考[3.2 示例](#scope-example)。要点：全量清单要真的写全（写不全说明还没想清楚）；红线功能控制在 2～4 条；最短路径必须能闭环，不能断在"然后呢"。

练习 2

1. B。理由：A 是开放式指令，必然带来大面积改动；B 限定到具体元素，可验收。
2. B。理由：A 没有现象、没有报错、没有约束；B 给了现象、原文、期望，并要求先分析再动手。
3. B。理由：A 会让已验收的部分被覆盖；B 是典型的"一次只改一小块"。

练习 3 参考[5.2 表格](#ui-copy)。要点：每个空状态都要告诉用户"下一步做什么"；报错要给出可执行的下一步，而不是错误码。

练习 4 参考[7.1 五步法](#usability-steps)。关键：唯一一句话任务要具体（"请用它把这段记录变成一份周报"），不能是"你试试看"。

练习 5

1. B　2. B　3. B　4. B　5. B　6. B　7. B　8. B　9. B　10. B
11. 错（丑和不能用是两件事；先丑后美）
12. 错（要求一次说清改哪一处，否则会改坏已验收部分）
13. 错（能不能用只有真人能判断，而且通常会发现你没预料到的卡点）
14. 错（1～2 个人就能暴露最主要的卡点；阶段三是尽力而为，不必凑人数）
15. 对
16. 拆需求 → Agent 生成 → 人验收 → 迭代。备份在"验收通过后、进入下一个最小改动前"。
17. 因为生成只要一次正确的输出，而调试要面对所有你没预料到的情况（环境、边界、状态、依赖）。策略：小而频繁，一次只改一小块，改完立刻验收，保持可回退的备份。
18. 它定义了"用户从进入到拿到结果"的最短闭环，是判断"能不能用"的基准线。例：打开网页 → 粘贴记录 → 点生成 → 复制结果。
19. 因为你的任何提示都会泄露"设计者的预期"，被试会顺着你的思路走，于是你测到的是"能不能理解你的解释"，而不是"产品能不能自己说清楚"。
20. 算过关。阶段三的过关标准是"找一个不认识你的人，不解释，让他自己用你的 MVP 完成一个任务"，以及如实记录付费验证结果。功能少不是问题，闭环不成立才是问题。

阶段三最常见的未达标是三周做不完。处置原则是缩小范围，不延长时间：

1. 红线功能从 4 条砍到 2 条，只留「输入 → 输出」；
2. 视觉包装全部延后，第一版用平台默认样式；
3. 上线方式换成最简单的，静态页面加一键部署；
4. 仍然做不完，就把「能不能让一个陌生人用起来」这一步单独做出来（哪怕是需要你手动帮忙的半成品），完整版移入阶段四前两周。

最不能接受的是因为做不完就跳过阶段四，或者因为做不完就不找人测试。

## 附录 A：常见卡点与对策 {#appendix-trouble}

| 卡点 | 典型现象 | 对策 |
| --- | --- | --- |
| 越做越大 | 功能从 4 条涨到 12 条 | 回头看红线标准，本周只做 2 条 |
| 反复重构 | 每轮都"顺手优化一下" | 严格执行"只改一处"模板 |
| 备份丢失 | 让 AI 重新生成后调好的部分没了 | 立刻重建备份习惯，接受这次损失 |
| 部署失败 | 本地能看，公网打不开 | 换最简单的托管方式；让 AI 读部署报错 |
| 没人测试 | 找不到陌生人 | 去相关社群发帖换测试（"我帮你测你的，你帮我测我的"）；或用陌生人社交渠道发链接 |
| 视觉焦虑 | 花三天调颜色 | 停。第一版用默认样式，把时间还给可用性 |
| 成本失控 | 生成接口被刷 | 先设使用上限；给生成功能加简单的频次限制或口令 |

## 附录 C：AI 编程报错速查（走 AI 编程路线必看）{#appendix-errors}

新手遇到的报错九成属于下面六类。看懂类型，你就能给出更有用的提问。

| 类型 | 典型现象/关键词 | 通常的原因 | 你该怎么说 |
| --- | --- | --- | --- |
| 环境问题 | command not found、不是内部或外部命令、版本不匹配 | 工具没装、装错版本、终端没重启 | "我运行 `____` 报错原文如下……请告诉我需要装什么、装哪个版本、在哪一步装" |
| 依赖问题 | Cannot find module、ModuleNotFoundError、package 缺失 | 没装依赖、装到别的目录、锁文件冲突 | "请告诉我需要执行哪条安装命令，并在哪个目录下执行" |
| 端口/占用 | EADDRINUSE、address already in use | 上一次的服务没关、端口被占 | "请先帮我关掉占用该端口的进程，或者换一个端口" |
| 路径/文件名 | ENOENT、no such file、路径含空格或中文 | 文件不在预期位置、路径没引号 | "请确认项目目录结构，告诉我文件应该放在哪里" |
| 语法/类型 | SyntaxError、Unexpected token、类型不匹配 | 生成代码有笔误、版本语法不兼容 | "只修这一处语法错误，不要改其他逻辑" |
| 权限/认证 | 401、403、permission denied、API key 无效 | 密钥没配、权限不足、额度用完 | "这是我的报错，请列出 3 个可能原因，我从最简单的开始试" |

三条通用纪律：

1. 贴完整原文，不要截断，不要手动改写报错（改写常常丢掉关键的路径与行号）；
2. 一次只解决一个错，报错常有连环，先解决第一个，再跑一次看第二个；
3. 要求先分析再动手："先告诉我可能原因（不超过 3 条），我确认后再改代码"。这一句能防止 AI 在你的项目里乱改一通。

:::warning 两个必须记住的动作
- 改之前先备份（[见 4.3](#backup)）。报错不可怕，可怕的是"改着改着把能跑的部分也改坏了，而且回不去"；
- 卡住超过 40 分钟就换策略：把问题缩小到最小可复现的例子（让 AI 单独写一个 20 行的示例），跑通再往项目里搬。不要在复杂项目里直接调一个你看不懂的错。
:::
