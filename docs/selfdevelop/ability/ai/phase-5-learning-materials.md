# 阶段五学习材料：运营与迭代（约 3 周）

本材料是《[一人公司的 AI 实战进阶计划（AI Agent 学习路线）](ai-agent-one-person-company-plan.md)》第五阶段的配套学习内容。

## 零、开始之前 {#before-start}

### 0.1 前置检查 {#prereq}

- [ ] 你手上有 ≥ 3 条真实的用户反馈原话（阶段四的第一批用户）；
- [ ] 你的 MVP 有一个能持续被访问的入口（链接 / 文档 / 微信群任一）；
- [ ] 你愿意每周固定花 1 小时看数据并做决定（这件事本阶段叫“周会”，是最重要的习惯）；
- [ ] 你接受一个事实：三周后你可能发现这条路不太行。能发现它，也是本阶段的合格产出。

### 0.2 时长节奏 {#rhythm}

[逐日清单](#daily-plan)按每周约 8 小时设计：

| 节奏 | 每周投入 | 怎么用 |
| --- | --- | --- |
| 保命档 | 约 5 小时 | 用[最小版本](#daily-plan)：10 天完成 2 轮闭环 + 2～3 份周报；客服降级为“手动回复 + 话术模板” |
| 标准档 | 约 8 小时 | 按二十一天清单走 |
| 加速档 | 12 小时以上 | 加做一次完整用户声音分析 + 把客服 Bot 的边界测试做透 |

## 一、本阶段学习目标 {#goals}

| 维度 | 三周后达标线 | 对应本材料章节 |
| --- | --- | --- |
| 客服 | 客服 Bot 上线，能答常见问题，复杂/情绪/付款问题一律转人工 | [第三章](#service) |
| 分析 | 完成 1 轮用户声音分析，且做了人工复核 | [第四章](#voice) |
| 指标 | 定义 3 个最小指标，每个都有分子分母与统计口径 | [第五章](#metrics) |
| 迭代 | 完成 2～3 轮迭代，每轮有完整记录与指标对比 | [第六章](#flywheel) |
| 周报 | 3 份迭代决策周报（AI 出数据与建议 + 你写三行） | [第七章](#weekly-report) |
| 判断 | 写下停损判据；如需要，真的执行过一次降级或换向 | [第八章](#stop-loss) |

## 二、工具选型 {#tools}

| 环节 | 推荐工具 | 怎么用 | 降级方案 |
| --- | --- | --- | --- |
| 客服 Bot | 扣子（Bot + 知识库 + 工作流） | 知识库放 FAQ，工作流处理“收集信息/转人工/通知我” | 手动回复 + 保存话术模板 |
| 微信生态客服 | 腾讯元器 / 企业微信 + 扣子 | 若用户主要在微信/企微里 | 手动回复 |
| 反馈汇总 | 飞书多维表格 / 金山表格 | 所有反馈与线索汇总到一张表 | 一张 Excel |
| 反馈分析 | Kimi（长文本）/ WorkBuddy / DeepSeek | 归纳好评、吐槽、隐藏需求 | 手动分类计数 |
| 数据看板 | 飞书多维表格（视图/分组/统计） | 每周自动汇总指标 | 手动统计并在表格里算 |
| 周报生成 | WorkBuddy | 读数据表 → 出“数据 + 建议”周报 | 手动整理 + AI 润色 |
| 迭代记录 | 同一张迭代表 | 每轮一条记录，字段固定 | 一篇 Markdown |

先把“反馈表”和“迭代表”的字段定死（见[10.1](#tables)），后面每周只是往里填。

## 三、客服自动化 {#service}

### 3.1 FAQ 手册怎么写 {#faq}

来源直接用阶段二～四收集到的真实提问，不要自己猜用户会问什么。

| 类别 | 典型问题 | 答案要求 |
| --- | --- | --- |
| 它是什么 | “这是干什么用的？” | 一句话说明，不用技术名词 |
| 怎么用 | “怎么开始？”“要不要注册？” | 3～5 步，动词开头 |
| 价格 | “多少钱？”“有免费版吗？” | 只讲公开信息，不承诺折扣 |
| 边界 | “能帮我做 XX 吗？” | 明确说“目前不支持”，不模糊 |
| 效果 | “能省多少时间？” | 用你自己或用户的具体经历，不承诺效果 |
| 隐私 | “我的数据你会看到吗？” | 如实说明，越具体越可信 |
| 售后 | “不好用能退吗？” | 明确规则 |

FAQ 手册模板：

```text
# FAQ 手册 v____     更新日期：____

## 一、它是什么
Q：______
A：______

## 二、怎么用
Q：______
A：______

## 三、价格与购买
Q：______
A：______

## 四、能力边界（重要）
Q：你们能帮我做 ______ 吗？
A：目前不支持。原因是 ______。如果你需要这个，可以先告诉我，我会记录。

## 五、数据与隐私
Q：______
A：______

## 六、不在这里的问题
统一回复："这个问题我帮您记录下来，稍后人工回复您。"
```

:::warning 写 FAQ 的同时，一定要配一条“拒答规则”
知识库类应用最危险的行为不是答不好，而是检索不到时自己编。FAQ 写完只是第一步，还必须在人设里写死一句话：

> “如果知识库中没有相关答案，直接回答‘这个问题我帮您记录下来，稍后人工回复您’，不要用你自己的想法回答。”

测试方法：问一个 FAQ 里绝对没有的问题（如“明年会涨价吗”“你们老板是谁”），确认它拒答而不是编。上线后每周抽查 5 条真实对话，这是唯一能发现“它开始编了”的办法。

顺序不能反：先保证它不会瞎答，再考虑让它答得快、答得多。答错的伤害远大于答不上来。
:::

### 3.2 转人工规则 {#escalation}

| 触发情况 | 关键词/信号示例 | Bot 应做的事 |
| --- | --- | --- |
| 付款与退款 | 付、付款、退款、发票、怎么买 | 不给承诺，直接转人工 |
| 投诉与情绪 | 投诉、骗子、骗人、垃圾、太差、差评 | 先安抚，立即转人工并通知你 |
| 涉及金额与合同 | 报价、合作、代理、签合同 | 转人工 |
| 能力边界外 | 提问命中“你们能帮我做 XX 吗”且答案是“不支持” | 明确说“不支持”，可登记需求 |
| Bot 答不上来 | 连续 2 轮未命中知识库（回复里出现“我帮您记录”“不确定”等字样）/ 用户重复问同一个问题第 3 次 / 用户明确说“你答非所问” | 转人工 |
| 涉及隐私与安全 | 索要他人信息、上传敏感材料 | 拒绝并转人工 |

:::warning “置信度低”不能作为触发条件
很多材料会写“置信度低时转人工”，但绝大多数 Agent 编排平台并不把这个数值暴露给你，你没法据此设条件。必须换成你能实际观测到的信号：

| 可观测信号 | 怎么配 / 怎么判 |
| --- | --- |
| 知识库未命中 | 在人设里要求“检索不到时必须输出固定句：我帮您记录，稍后人工回复”，然后在工作流里匹配这句话 → 触发转人工 |
| 关键词命中 | 消息里出现“退款、投诉、骗子、合同、报价、发票”等词 → 直接转 |
| 轮次计数 | 同一用户连续 3 轮未解决问题 → 转 |
| 用户明确要求 | 出现“转人工”“找人”“真人”等词 → 转 |

在这四条里，最可靠的是“关键词 + 未命中固定句”这两条。上线前用[3.3 测试清单](#service-test)逐条验证它们真的会触发。
:::

转人工时对用户说什么（模板）：

> “这个问题我需要人工来回答，我已经帮您记下来了，稍后会有专人联系您。抱歉让你等一下。”
> （如果是投诉类，前面先加一句：“非常抱歉给你带来不好的体验。”）

付款、投诉、对外承诺必须由人处理，不能交给 Bot 自行应答，这是[底线清单](ai-agent-one-person-company-plan.md#guardrails)里“人兜底”的落地。

### 3.3 客服 Bot 上线前的测试清单 {#service-test}

| 测试类型 | 具体怎么测 | 通过标准 |
| --- | --- | --- |
| 常见问题 | 把 FAQ 里每个问题都问一遍 | 优先引用知识库答案，不编造 |
| 超纲问题 | 问一个你和它都没答案的问题（如“明年会涨价吗”） | 明确说“不确定，转人工”，不猜 |
| 边界问题 | 故意问“能打五折吗”“我要投诉你们” | 不擅自答应，走转人工 |
| 多轮连贯 | 连续问 5 轮相关问题 | 不串台、不丢失上下文 |
| 语气检查 | 用挑剔的用户口吻提问 | 不失礼、不油滑、不啰嗦 |
| 出错兜底 | 断网/接口失败时 | 有友好提示，不白屏 |

调优口诀：答非所问 → 补知识库；语气不对 → 改人设；该转向却硬答 → 补转人工规则。

## 四、用户声音分析 {#voice}

### 4.1 分析任务书 {#voice-brief}

```text
【角色】你是用户研究分析师。
【目标】阅读我提供的全部用户反馈（聊天记录、评论、问卷开放题），交付：
  1. 好评集中的 3 类（每类注明来自哪几条反馈编号）；
  2. 吐槽集中的 3 类（同样标注编号，并标注严重程度：阻断使用 / 影响体验 / 吹毛求疵）；
  3. **被提到但产品没做的需求**（≥ 2 条）；
  4. 与我的假设矛盾的证据（**这一节最重要，不许省略**）。
【约束】只使用文件里出现的原话，不得推测、不得合并语义不同的反馈；
        禁止把"挺好的""整体不错"这类客套话归入好评；
        每条结论必须能指到具体反馈编号。
【验收标准】每条结论都能回溯到原始记录；第 3、4 节不得为空。
```

### 4.2 四种常见误判 {#misjudge}

| 误判 | AI 常犯的具体表现 | 人工复核方法 |
| --- | --- | --- |
| 把客气话当满意 | 把“还不错”“挺好用的”列为正面评价 | 只有“主动推荐给别人”“重复使用”“说了具体哪里好”才算正面 |
| 过度聚类 | 把 5 个人说的 5 件不同的事归成“一个共同痛点” | 回原始记录数一遍：只出现在 1 份里的，不能叫“高频” |
| 忽略情绪强度 | 把“有点小问题”和“完全用不了”同等对待 | 给每条吐槽标严重程度：阻断使用 / 影响体验 / 吹毛求疵 |
| 把需求当结论 | 用户说“希望有导出功能”，直接当成必做需求 | 追问“你想拿导出去做什么”——真实需求往往在目的里，而不是功能里 |

### 4.3 反馈表的字段 {#feedback-table}

| 字段 | 说明 |
| --- | --- |
| 编号 | F001、F002…… |
| 日期 | 收到日期 |
| 来源 | 客服对话 / 评论区 / 问卷 / 访谈 / 熟人 |
| 用户标识 | 代号，不用真名 |
| 原话 | 必须原话，不改写 |
| 类别 | 好评 / 吐槽 / 需求 / 疑问 / 咨询 |
| 严重程度 | 阻断使用 / 影响体验 / 吹毛求疵 |
| 涉及功能 | 哪个环节 |
| 是否已处理 | 待处理 / 已改进 / 不处理（写明理由） |

## 五、北极星指标：把“看数据”落到数字上 {#metrics}

### 5.1 三个最小指标与定义方法 {#three-metrics}

| 指标 | 分子 | 分母 | 时间窗 | 怎么数 |
| --- | --- | --- | --- | --- |
| ① 落地页 → 线索转化率 | 留下联系方式的人数 | 打开落地页的独立访客数 | 每周 | 表格里“留资日期”计数 ÷ 落地页后台访问数 |
| ② 试用 → 付费转化率 | 付费人数（或口头承诺付费人数） | 完成过一次完整使用的独立人数 | 每周 | 试用名单表 ÷ 付费名单表 |
| ③ 内容触达 → 咨询数 | 主动来咨询的人数 | 内容总曝光量（或阅读量） | 每条内容 | 反馈表里来源=评论区的记录数 |

数据不足时的替代指标（阶段五早期很常见）：

| 替代指标 | 定义 |
| --- | --- |
| 每周咨询数 | 本周主动来问你的人数（去重） |
| 每周试用人数 | 本周实际用过一次的人数 |
| 每周留存 | 上周用过的人里，这周又用了一次的人数 |

对一人公司，比转化更该盯着的是留存：用过的人里有多少会再来用（以及会不会续费）。

| 指标 | 可落地定义 |
| --- | --- |
| 周留存 | 上周用过的人里，这周又用了一次的人数 ÷ 上周用过的人数 |
| 复购 / 续费 | 已付费的人里，下一周期又付费的人数 ÷ 已付费人数 |

如果你三周下来周留存接近 0，不要急着加内容、加投放，先做[第八章](#stop-loss)的降级判断（换卖点 / 换形态）。把资源投在一个留不住人的东西上，是最常见的浪费。

:::warning 指标定义的三个常见坑
1. 分母不写清。“转化率提升了”，是相对于谁？独立访客还是页面浏览？两个口径能差一倍。
2. 时间窗不一致。上周按 7 天数，这周按 5 天数，比出来没意义。
3. 口径中途改变。表结构变了却继续对比新旧数据。改口径要在迭代记录里注明“本期起口径变更，不与上期直接比较”。
:::

### 5.2 北极星指标卡模板 {#metric-card}

```text
# 北极星指标卡     建立日期：____

## 指标 1：______
- 定义：______（一句话）
- 分子：______    分母：______
- 时间窗：每 ______ 统计一次
- 数据来源：______（哪个表/后台）
- 当前值（基线）：______    日期：____
- 我期望它在 ______ 周内达到 ______

## 指标 2 / 指标 3：（同上）

## 指标 4（最容易被漏掉，但对一人公司最重要）：留存 / 复购
- 定义：______（例：上周用过的人里，这周又用了一次的比例）
- 分子：______    分母：______
- 时间窗：每 ______ 统计一次
- 数据来源：______
- 当前值（基线）：______
- 我期望它在 ______ 周内达到 ______

## 反向指标（防止为了指标牺牲体验）
- 例：投诉数、退订数、客服转人工率上升，说明指标虚高
```

## 六、迭代飞轮：每周只改一个核心问题 {#flywheel}

### 6.1 四步循环 {#four-steps}

| 步骤 | 谁做 | 做什么 | 输出 |
| --- | --- | --- | --- |
| 收集 | AI + 人 | 汇总本周全部用户声音，归类、标严重程度 | 本周问题清单（按 人数 × 严重程度 排序） |
| 判断 | 人拍板 | 对照北极星指标，选出只改一个的问题，并写下“我预期改完哪个指标动” | 本周迭代决定（一句话） |
| 执行 | Agent | 按[阶段三的开发委托模板](phase-3-learning-materials.md#dev-prompt)做改动 | 新版本 + 备份 |
| 验证 | 人 | 看指标有没有动；没动就如实记录并分析原因 | 迭代记录一条 |

一次改 5 个地方的后果是：你永远不知道是哪个改动起了作用。三周下来你会有 3 个数据点，但一个因果都说不出来。一次一个，宁可慢。

### 6.2 怎么判断“改哪个最值钱” {#prioritize}

| 排序维度 | 判断方法 |
| --- | --- |
| 影响人数 | 有多少人遇到这个问题（看反馈表计数） |
| 严重程度 | 是“阻断使用”还是“吹毛求疵” |
| 与指标的关联 | 改它能影响北极星指标吗？改一个跟指标无关的小细节，就是白忙 |
| 改动成本 | 半天能改完的，优先做 |

一张简单的判断表（把候选问题填进去）

| 候选问题 | 影响人数 | 严重程度 | 关联指标 | 成本 | 综合排序 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

### 6.3 迭代记录模板 {#iteration-log}

```text
# 迭代记录 第 ___ 轮        日期：____

## 一、用户说了什么（原话 + 反馈编号）
- "______"    —— F____
- "______"    —— F____
（共 ___ 人提到同一问题）

## 二、判断（人拍板，写清理由）
- 我决定改：______
- 理由是：______（影响 ___ 人 / 属于阻断使用 / 关联指标 ___）
- 我预期改完后：指标 ______ 会从 ______ 变成 ______
- 我**不**改的其他问题及原因：______

## 三、执行（谁做的、做了什么）
- 执行者：□ 我  □ Agent（工具：______）
- 具体改动：______
- 备份版本号：______

## 四、验证（指标对比）
| 指标 | 改动前 | 改动后 | 变化 | 是否达到预期 |
| --- | --- | --- | --- | --- |
| | | | | |

## 五、结论
- 有效 / 无效 / 无法判断（原因：______）
- 如果无效：我的下一个猜想是 ______
- 这次学到的一件事：______
```

“改完指标没动”不是失败，它排除了一个假设，这是真实的信息。把它如实写下来，比把结论写成“效果显著”有用得多。

### 6.4 三周迭代节奏 {#iteration-rhythm}

| 周 | 收集 | 判断 | 执行 | 验证 |
| --- | --- | --- | --- | --- |

## 八、停损判据 {#stop-loss}

### 8.1 提前写下来的判据 {#criteria}

```text
# 停损判据     写下日期：____

## 主判据
连续 ___ 周（建议 3 周）核心指标没有改善 → 执行降级或换向。
"没有改善"的定义：指标 ______ 连续 3 周未超过基线值，且周环比变化在 ±__% 以内。

## 辅助判据（满足任一即触发复核）
- 连续 2 周新增反馈条数 ≤ ___ 条（说明没人关注）
- 连续 2 周没有任何人主动咨询
- 转人工率持续 > ___%（说明产品我没做明白）
- 每周投入时间 > ___ 小时且无正反馈（说明成本失控）

## 触发后我要做的三件事
1. 停下来，用 1 天重新看访谈与反馈（而不是继续改产品）
2. 列出三个降级/换向选项，各写一条"最低成本验证方式"
3. 选一个成本最低的，用 1～2 周验证
```

### 8.2 三种降级/换向方式 {#pivot-options}

| 方式 | 保留什么 | 换掉什么 | 成本 | 什么时候选 |
| --- | --- | --- | --- | --- |
| 换卖点 | 产品、人群 | 价值主张、说辞 | 最低 | 有人用但没人付费；说明价值表达不对 |
| 换人群 | 产品、能力 | 目标用户 | 中 | 有人夸但没人用；说明人群选错 |
| 换形态 | 你验证过的痛点 | 产品形态（如从工具改成服务） | 最高 | 痛点真实但形态不匹配（如用户其实想要“你帮我做”而不是“给我工具”） |

规划里写得很清楚：“硬扛不是坚持，是浪费；知道何时收手，是经营能力，也是学习目标之一。”

判断“该不该换”的一个实用问题：如果再给我三周，我能说清这三周会改什么、为什么这次会不一样吗？如果答案是“继续说不上来”，就是该换的信号。

### 参考答案与解析 {#answer-key}

练习 1（参考答法）

- 定义：本周客服对话中，由 Bot 转给人工处理的对话数占全部对话数的比例；
- 分子：本周触发转人工的对话数；分母：本周客服对话总数（去重到人会话）；
- 时间窗：每自然周（周一 00:00 ~ 周日 24:00）；数据来源：客服平台的对话记录导出；
- 过高（如大于 50%）说明 FAQ 与知识库覆盖不够；过低（接近 0）可能是转人工规则失效，投诉类问题被 Bot 自行应答了。

练习 2

## 十二、本阶段自检清单 {#checklist}

- [ ] FAQ 手册已完成（≥ 15 条，来源是真实提问）；
- [ ] 客服 Bot 上线，或手动 SOP 已写成；
- [ ] 转人工规则 ≥ 6 条，且测试过三类边界问题；
- [ ] 反馈表与迭代表字段已定死，并已开始填写；
- [ ] 北极星指标卡完成：3 个指标各有分子、分母、时间窗、数据来源与基线值；
- [ ] 至少设 1 个反向指标；
- [ ] 完成 ≥ 1 轮用户声音分析，且做过人工复核（剔除了伪高频项）；
- [ ] 完成 2～3 轮迭代，每轮有完整的“收集 → 判断 → 执行 → 验证”记录；
- [ ] 每轮迭代都有“预期指标变化”与“实际变化”的对比；
- [ ] 有 1 个以上完整闭环可作为证据链：“因为用户说了 X，我改了 Y，指标 Z 从 A 变成 B”；
- [ ] 3 份迭代决策周报已完成，每份含 AI 数据与建议 + 你的三行；
- [ ] 停损判据已提前写下；
- [ ] 已对照停损判据做出“继续 / 降级 / 换向”的明确判断（如需要，已执行一次）；
- [ ] 阶段五文件夹整理完毕，复盘三行已写。

最常见的未达标是“没有足够多的真实用户，2 个闭环跑不起来”。处置原则是降低闭环门槛，而不是放弃闭环：

1. 用熟人和阶段二的访谈者凑出 3～5 人的小样本，明确告诉他们“你们就是我的第一批测试用户”；
2. 指标换成“每周试用人数”“每周咨询数”这类数得出来的量，不要硬算百分比；
3. 把“用户提意见 → 我改 → 他再看一眼”当作一个闭环。只要出现过一次完整的“因为他说的我改了，他确认变好了”，这个闭环就成立。

| 反馈表 | `44-反馈表.md` | 自动化后仍要继续填——它是“自动化有没有让体验变差”的证据 |
| 付费证据与留存数据 | 指标卡 + 反馈表 | 阶段六的前提条件：有没有人愿意付钱、留得住吗 |

### 阶段收尾的两行字 {#phase-note}

```text
这三周我花的每 1 小时，大概换回了多少价值：______
我还没算进成本的一笔支出是：______（多半是"我自己的时间"）
```

很多人算成本时只算工具订阅费，忘了算自己投入的时间。这恰恰是一人公司最大的一笔成本。阶段六会教你把这笔账算清楚（[单位经济速算](phase-6-learning-materials.md#unit-economics)）：如果每周投入 10 小时、收入 200 元，那时薪是多少，你能不能接受？现在先把这个问题记在心里。

## 附录 A：常见卡点与对策 {#appendix-trouble}

| 卡点 | 典型现象 | 对策 |
| --- | --- | --- |
| 没有用户反馈 | 反馈表只有 3 条 | 主动问：给每一个试用过的人发一条消息问“哪里最别扭” |
| 反馈太零散 | 说什么的都有 | 先按“阻断使用/影响体验/吹毛求疵”三档分类，再看人数 |
| 指标数字太小 | 分母是 20，分子是 1 | 用小样本可用的替代指标（每周咨询数），不要硬算百分比 |
| 客服 Bot 乱答 | 答得挺顺但内容是编的 | 检查知识库是否开启自动调用；把答案写进 FAQ，人设里禁止编造 |
| 迭代没效果 | 改了两次指标都不动 | 可能是改错了问题。回去做一次完整用户声音分析，重新排序 |
| 想一直改下去 | 改完一个还想改下一个 | 一周一个，写完验证再动下一个 |
| 数据焦虑 | 每天刷新好几遍 | 定一个固定时间看数据（如周日 21:00），其余时间不打开后台 |
