软件大师之路

你在做什么？你有什么愿景？

我的回答是：我在做软件产品，并致力于做出更好的软件产品，成为一名软件大师。

我将从 4 个维度定义我所从事的事业，分别是价值、需求、开发、运维，本项目系统性地记录和分享各个知识点。

同时，我还制作了《高质量软件工作手册》，用于指导软件工程师高效产出高质量的软件。

这四个维度是一条链​

价值（为什么做） → 需求（做什么） → 开发（怎么做） → 运维（交付使用）
   ↑                                                      │
   └────────────────── 真实反馈 ──────────────────────────┘
板块回答的问题核心产出
价值这事值不值得做、为谁做价值主张、度量指标
需求为了让价值发生，系统要做什么需求基线、验收标准
开发用什么原理、结构与手段实现可运行、可维护的系统
运维如何让它持续为用户工作服务级别、故障闭环

这条链有一个重要性质：越靠前的问题，发现得越晚代价越大。价值判断错了，后面所有环节的投入都会成倍浪费；运维是唯一能拿到真实反馈的环节，它的结论必须能流回最前端。

内容组织约定​

  • 层级最深 5 层（板块 / 分组 / 模块 / 子模块 / 知识点），但非必要不加层，优先保证阅读路径短。
  • 不写手写编号，顺序由侧边栏配置控制，插入新内容时不必重排既有编号。
  • 每个目录的 index.md 只做导览——说明本模块管什么、包含哪些子话题、建议的阅读顺序；具体知识点一律独立成文。
  • 一文档一主题：值得展开的内容单独成篇，不值得展开的不进清单。

怎么用这个知识库​

不建议顺序通读，更有效的用法是：

  1. 按问题定位——说不清某个需求该不该做，回价值找判据；不确定某个技术方案行不行，回开发找原理。
  2. 按链条追问——每读一个知识点，向上追问它服务于哪条价值，向下追问它会带来什么运维代价。
  3. 把反馈写回来——真实故障、性能瓶颈、被证伪的假设，都是从运维回流到前端的输入。
