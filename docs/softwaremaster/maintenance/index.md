# 运维：交付使用

前面三个板块都在「把软件做出来」，运维回答的是最后一个问题：**软件真的在为用户工作了吗**。

系统的价值只在运行时产生。代码躺在仓库里、镜像停在仓库里、服务没有流量，都不产生任何价值。运维是把这一切变成现实的环节，也是最容易被工程团队轻视的环节——因为它不出现在交付清单上。

## 本板块管什么

| 分组 | 回答的问题 |
| --- | --- |
| [交付](./delivery/index.md) | 怎么把软件安全地送到生产环境 |
| [运营](./operation/index.md) | 怎么让它持续、稳定、高效地运行 |
| [维护](./maintain/index.md) | 上线之后怎么继续修改它 |

## 三个概念的区别

| 概念 | 关注 | 时间尺度 |
| --- | --- | --- |
| 交付 | 让新版本到达用户 | 一次性事件 |
| 运营 | 保证服务持续可用 | 持续进行 |
| 维护 | 修改已交付的软件 | 按需触发 |

三者常被混为一谈，但它们的动作、责任人与度量完全不同。混在一起会导致「上线之后就没人管」的常见断层。

## 成本的真相

维护成本在软件总成本中的占比远超多数人的预期——大型软件的维护成本可以达到开发成本的 **4 倍**左右。

这个数字有两个直接推论：

1. **交付质量决定长期利润**：可维护性差的系统，会在后续若干年持续吞噬利润。这使[可维护性](../requirement/analysis/nonfunctional/maintainability.md)从「加分项」变成「生存项」。
2. **运维团队需要早期介入**：把运维留到上线之后再参与，等于让最了解运行现实的人最后才知道设计决策。

## 与前面板块的闭环

```
价值 → 需求 → 开发 → 运维
  ↑                    │
  └────── 反馈 ────────┘
```

运维是整条链路上**唯一能获得真实反馈的环节**：用户行为、性能瓶颈、故障模式、成本结构，只有在这里才看得见。

因此运维的产出不只是「服务正常」，还包括**改进输入端的知识**：哪些假设被证伪、哪些需求被误判、哪些架构选择付出了代价。这些反馈如果流不回[价值](../value/index.md)与[需求](../requirement/index.md)，系统就会持续重复相同的错误。
