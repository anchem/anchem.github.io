# 发布

发布决定**什么版本、在什么时候、对多大的用户范围生效**。它是一个业务决策，不是技术动作。

## 发布策略

| 策略 | 特点 | 风险 |
| --- | --- | --- |
| 全量发布 | 一次性对所有用户生效 | 风险最高，出问题影响面最大 |
| 灰度发布 | 按比例或按人群逐步放量 | 需要流量控制与监控能力 |
| 金丝雀发布 | 先放极少流量验证 | 需要能快速对比新旧表现 |
| 蓝绿发布 | 两套环境切换 | 资源成本翻倍，回滚最快 |
| 特性开关 | 代码已部署，功能按需启用 | 需要治理开关生命周期 |

**灰度是性价比最高的手段**：它把「一次大赌注」变成「一系列小赌注」，让问题在影响 1% 用户时暴露，而不是 100%。

## 发布检查单

发布前必须明确回答：

| 问题 | 为什么重要 |
| --- | --- |
| 如何判断发布成功？ | 没有成功标准就无法判断是否该回滚 |
| 如何回滚？需要多久？ | 回滚路径必须提前验证过 |
| 数据变更可否回滚？ | 数据结构变更常常不可逆 |
| 谁在观察？观察多久？ | 无人观察的发布等于没有发布 |
| 影响哪些下游？ | 兼容性破坏会波及调用方 |
| 回滚会不会丢数据？ | 这是最需要提前确认的问题 |

其中**数据变更的回滚**最容易出事：代码可以回退，但已写入的数据格式往往不能。这类变更必须单独设计渐进方案（如双写、兼容读取、分批迁移）。

## 发布节奏

| 节奏 | 优势 | 风险 |
| --- | --- | --- |
| 高频小批 | 问题定位容易，单次风险低 | 需要完善的自动化与监控 |
| 低频大批 | 单次协调成本低 | 变更集中，定位困难，风险高 |

**发布频率本身不是目标**，但它与单次变更的风险成反比。高频小批的收益主要来自「每次变更的规模更小」。

## 什么时候不该发布

- 关键业务高峰期内（除非有明确理由）；
- 缺少回滚路径或未验证回滚；
- 上游依赖处于不稳定状态；
- 没有人在接下来的窗口内观察。

最后一条常被忽略：**无人值守的发布等于把故障发现的责任交给了用户**。

## 实践建议

- 让「部署」与「发布」解耦，用特性开关控制生效范围。
- 固定发布窗口与观察期，把观察作为发布流程的一部分。
- 每次发布记录版本、变更清单、影响范围与观察结论，形成可回溯的发布日志。
- 从最小的风险开始：先内部用户，再小比例外部，最后全量。
- 把回滚演练作为常规动作，只演练部署不演练回滚是最常见的准备不足。
