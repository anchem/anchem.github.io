# 部署

部署是**把构建产物放到目标环境并使其运行**的技术过程。它的核心要求是**可重复**与**可回退**。

## 部署方式

| 方式 | 特点 | 适用 |
| --- | --- | --- |
| 重建 | 停止旧版本，启动新版本 | 可接受短暂中断的系统 |
| 滚动 | 分批替换实例，容量无损 | 无状态服务的主流方式 |
| 蓝绿 | 两套环境切换 | 要求快速回滚 |
| 金丝雀 | 少量实例先跑新版本 | 风险敏感的核心服务 |

选择的关键在于回答两个问题：**能否承受部分实例版本不一致？回滚需要多快？**

## 部署必须处理的问题

### 1. 版本共存的兼容性

滚动与灰度期间，新旧版本会同时运行并共享数据与接口。因此必须保证：

- 新版本能读旧格式数据（**向前兼容**）；
- 旧版本能忽略新版本产生的新字段（**向后兼容**）；
- 接口变更只增不删。

这是「部署期间不会出错」的前提，也是最容易被忽略的前提。

### 2. 数据库变更的顺序

数据变更必须与代码变更解耦，通常分三步：

```
1. 扩展：新增字段 / 表，代码同时兼容新旧
2. 迁移：回填数据，双写或逐步切换
3. 收缩：确认无依赖后删除旧结构
```

**每步之间都要能共存**，不能要求「代码与数据同时切换」——那意味着无法回滚。

### 3. 健康检查与流量接入

- **存活探针**判断是否需要重启，不应依赖外部服务；
- **就绪探针**判断是否可接流量，应当在依赖就绪后才通过。

混用两者会导致启动期被误杀，或未就绪的实例接收到流量。

### 4. 优雅关闭

收到终止信号后应当：停止接收新请求 → 处理完在途请求 → 释放资源 → 退出。

**缺少优雅关闭是数据丢失与脏数据的主要来源之一**，尤其在扩缩容与滚动发布时高频发生。

## 部署的自动化要求

| 要求 | 原因 |
| --- | --- |
| 幂等 | 重复执行不能产生副作用 |
| 原子 | 失败要么整体回退，要么明确停在中间态并可知 |
| 可观测 | 每一步都有日志与状态，便于定位 |
| 与环境无关 | 产物一致，差异来自配置 |

**部署脚本必须具备幂等性**：生产环境中的重试是常态，不幂等的部署脚本会造成灾难性后果。

## 实践建议

- 部署流程固化为脚本或流水线，禁止手工步骤——手工步骤无法重复。
- 部署前检查依赖的可用性；依赖不可用时宁可推迟部署。
- 为部署配置明确的超时与失败处理策略，避免卡在半完成状态。
- 记录每次部署的版本、时间、执行人与结果，这是故障定位的基础信息。
- 把回滚路径与部署路径同等对待，定期演练。
