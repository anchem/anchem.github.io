Linux CPU 运维指南

服务器又报警 CPU 高了？top 打开全是看不懂的数字？本手册用最通俗的语言，帮你从零建立 CPU 运维的知识体系：先搞懂概念，再学会命令，最后能独立定位和解决问题。内容围绕「CPU 消耗」这一主题，覆盖 核心知识点 → 排查命令 → 成因与解法 → 实战案例 → 速查表 完整链路。

新手学习路线​

如果完全没接触过服务器排查，建议按下面的顺序走一遍，大约半天到一天就能掌握核心思路：

  1. 先懂概念，不背命令 — 花一小时读「CPU 核心概念」，重点是理解「负载」和「使用率」的区别、什么是上下文切换。概念不懂，命令输出只是天书。
  2. 学 top，先会看全局 — top 是最常用的命令。学会读前五行统计和进程列表，再学 htop 的交互操作，日常 80% 的场景就够了。
  3. 再学 vmstat / mpstat / sar / pidstat — 这些命令回答更细的问题：系统是 CPU 忙还是等 IO？哪个核在忙？哪个进程在吃 CPU？上下文切换有多频繁？
  4. 套用排查流程，动手解决 — 按「高 CPU 排查流程」里的步骤，拿一台测试机或低峰期服务器实操一遍。对照「常见成因分析」和「解决方案」，练会定位与处置。
  5. 把「速查表」收藏起来 — 上手后不需要整本翻阅，出问题时直接翻「速查表」，场景 → 命令 → 关注指标，一分钟找到下一步。

第一部分 基础入门​

CPU 核心概念​

这一章解决「看不懂」的问题。我们会把 top、vmstat 输出里那些名词——使用率、负载、上下文切换、运行队列、中断——用大白话讲清楚，最后再澄清几个新手最容易犯的认知误区。概念搞懂了，后面学命令就是顺理成章的事。

CPU 是干什么的​

把服务器想象成一家工厂：内存是仓库（放原材料和半成品），磁盘是货架（长期存放），网络是物流（进出货物），而 CPU 就是车间里的工人——所有计算工作，最终都要由工人一件一件做出来。

工人（CPU）的数量、每个工人的手脚快慢（主频、架构），决定了工厂单位时间能处理多少活。当「活儿太多、工人太少」时，就会排队、就会卡顿——这就是我们说的 CPU 忙、CPU 消耗高。

运维关心什么

运维关心的问题就三个：工人忙不忙（使用率）、门口排了多少队（负载）、工人来回换活儿有多频繁（上下文切换）。本章后面就围绕这三点展开。

物理核、逻辑核与「几个 CPU」​

现代 CPU 有物理核和逻辑核之分：一个物理核通过超线程可以模拟成两个逻辑核。对操作系统来说，它只认识「逻辑核」——一个逻辑核在同一时刻只能运行一个任务。

top 第一行的 %Cpu(s)、负载是否超标的判断、mpstat 显示几颗 CPU，全都以逻辑核数量为准。查看本机逻辑核数：

$ nproc
8

$ lscpu | grep -E "^(CPU\(s\)|Core|Thread)"
CPU(s):                               8
Core(s) per socket:                   4
Thread(s) per core:                   2
通俗理解

8 个逻辑核 = 8 个工人。判断「CPU 是否忙」，标准答案就是和 8 这个数比。

CPU 使用率：工人忙的时间占比​

CPU 使用率 = 一段时间内 CPU「忙」的时间比例。忙，又分很多种忙法。top 第三行就是按忙的方式拆开统计的：

%Cpu(s): 68.5 us, 12.3 sy,  0.0 ni, 15.4 id,  2.8 wa,  0.3 hi,  0.7 si,  0.0 st
字段全称通俗含义偏高意味着什么
ususer跑你的业务程序（用户态代码）业务逻辑在大量计算，最常见
sysystem跑操作系统内核代码系统调用、锁、中断处理过多
ninice被调整过优先级的用户程序一般不重要
ididle工人闲着没活干越高说明 CPU 越空闲
waiowait在等磁盘/网络等 IO 完成不是 CPU 的问题，是磁盘太慢！
hihardware irq处理硬件中断（如网卡来包）硬件中断风暴，常见于网卡
sisoftware irq处理软中断（内核调度类任务）网络收包/定时任务过多
ststeal被宿主机「偷走」的时间（虚拟机/容器）云主机超卖，邻居抢占
新手最容易看漏的三点
  • us 高 多半是业务代码问题；sy 高 要查系统层面（锁、中断、系统调用）；wa 高 其实是磁盘慢，别去优化 CPU；st 高 是云平台的事。
  • top 进程列表里 %CPU 是「近一次刷新」的瞬时值且可能超过 100%（多核累加）。判断谁长期吃 CPU，更可靠的是累计列 TIME+。
  • 单看「使用率 100%」不能说明有问题——只要任务确实在正常计算，100% 反而是高效。

平均负载（load average）：门口排队的人数​

top 第一行、uptime 输出的 load average: 2.35, 1.98, 1.62，三个数分别是过去 1 分钟、5 分钟、15 分钟的平均负载。

负载统计的是「正在运行 + 等待运行 + 处于不可中断等待（如等磁盘）」的任务数，可以粗浅理解为工人正在干的活 + 在门口排队等工人的活。

场景负载 vs 使用率原因
CPU 真的忙负载高 且 使用率高计算任务太多，工人满负荷
在等 IO（磁盘慢）负载高 但 使用率不高任务堵在磁盘读写上，CPU 反而不忙
任务排队等待锁/资源负载高 但 使用率不高大量线程阻塞等待，空排队

怎么判断负载算高？ 经验法则：把负载和逻辑核数比。

  • 8 核机器，负载长期接近 8 → CPU 基本满载，业务可能开始排队卡顿；
  • 负载持续高于 8（如 12、16）→ CPU 严重过载，需要扩容或优化；
  • 负载低于核数 → CPU 还有余量。
头号误区：负载高 = CPU 忙

这是新手最常犯的错误。负载里包含等 IO 的任务，所以「负载高 + 使用率低」是磁盘慢或任务阻塞的典型信号。看负载时必须配合 %Cpu(s) 或 vmstat 一起看，不能只看一个数。

另一个要点是看趋势：1 分钟负载比 15 分钟高很多，说明是刚发生的突发问题；三个数都高，说明问题已持续很久。

运行队列：门口正在排队的人​

vmstat 输出的第一列 r，表示正在运行 + 正在排队等 CPU 的任务数（不含等 IO 的任务）。它是「负载」里和 CPU 最直接相关的部分。

  • r 持续大于逻辑核数 → CPU 真的过载，任务在排队；
  • r 远大于核数（如 8 核机器 r=30）→ 严重过载。

vmstat 里还有一个 b（blocked）列，表示被阻塞、在等 IO 或等资源的任务数。b 大且 r 正常，指向 IO 问题。

为什么 r 超过核数会「突然变卡」

排队论告诉我们：当任务到达速率接近处理能力时，等待时间会指数级上升，而不是缓慢增加。直观理解：8 个工人、来了 9 个活，只是 1 个在排队；但活多到 12、16 个时，排队人数越来越多，每个任务的平均等待时间会暴涨——这就是为什么负载从「接近核数」到「超过核数」时，业务响应会断崖式恶化。负载超标的机器，越早处理，恢复越快。

上下文切换：工人频繁换活儿​

一个工人同一时刻只能干一件事。当大量任务轮流使用 CPU 时，每次「换人」都要保存上一个任务的进度、加载下一个任务的进度，这个过程叫上下文切换（context switch）。切换本身几乎不产生价值，但非常消耗 CPU（主要是 sy 时间）。

上下文切换分两种：

类型含义典型原因
自愿切换（voluntary）任务主动让出 CPU，比如在等锁、等 IO、主动 sleep锁竞争、IO 等待、线程过多且频繁阻塞
非自愿切换（nonvoluntary）时间片用完，被系统强制换下去任务太多，CPU 不够分

怎么衡量？vmstat 的 cs 列每秒输出一次切换次数；pidstat -w 可以看单个进程的切换量。经验参考：空闲的普通服务器每秒几千次到几万次；如果持续飙升到几十万次甚至更高，或者相对自己机器基线明显异常，就要警惕「切换风暴」。

一个经典场景

Java 应用线程池配了 500 个线程，实际干活只用 10 个，其余 490 个线程全在抢同一把锁 → 使用率不高、但 cs 爆炸、sy 偏高、应用还卡顿。这种「虚假的繁忙」就是上下文切换惹的祸。

中断与软中断​

硬件（网卡来包了、磁盘读完数据了）需要打断 CPU 让它处理，这就是中断。中断处理分两段：

  • 硬中断（hi）：必须立刻处理的部分，比如先收下网卡发来的包。由硬件信号直接触发。
  • 软中断（si）：可以稍后处理的收尾工作，比如把收到的包交给协议栈处理。由内核在合适时机触发。

高流量、网卡队列没调优、或者某些驱动有问题的机器，si 会长期很高，占掉大量 CPU。查看中断分布可以看 /proc/interrupts。

时间片、优先级与抢占​

时间片：CPU 给每个任务分配的一小段连续执行时间（通常几十毫秒级）。任务轮流使用 CPU，就像几个孩子轮流玩一个玩具，每人玩一小会儿就换人。

抢占（preemption）：时间片用完、或更高优先级的任务到来时，系统强行把当前任务换下去。被换下去的那次切换，就是前面说的「非自愿切换」。

优先级决定了任务排队时「插队」的权利。nice 值越低，优先级越高（越容易抢到 CPU）：

  • nice 范围通常 -20 到 19，普通进程默认 0；普通用户只能把 nice 调高（礼让），调低需要 root；
  • 给某个占资源的任务调高 nice（如 nice -n 10），是让它「礼让」其他任务，常用于应急时保护关键业务；
  • top 进程列表的 PR（priority）和 NI（nice）列对应这两个值。
调度器的角色

内核的 CFS（完全公平调度器）负责分配时间片：任务越多、优先级越低，分到的时间片就越少。所以「任务数暴增」会直接摊薄每个任务获得的 CPU 时间——这是高并发场景下响应变慢的底层原因之一。

本章小结

记住三句话：使用率回答「工人多忙」，负载回答「门口排多长队」，上下文切换回答「换活儿多频繁」。下一章开始，把这些概念和真实命令对上号。

第二部分 命令实战​

命令总览​

排查 CPU 问题不需要背一堆命令。真正的思路只有一条：从宏观到微观逐层收窄——先看整机状态，再看到底是 CPU 忙还是等 IO，然后定位到进程，最后定位到线程甚至代码。这一章给你一张「地图」，后面三章逐个拆解。

排查工具的分层​

把命令按「看的粒度」分层，用的时候就知道下一步该上什么工具：

层级要回答的问题主力命令
第 1 层 · 整机机器整体忙不忙？负载多高？趋势如何？uptime、top 第一行、sar -q
第 2 层 · CPU 细节是 us 高还是 sy 高？是等 IO 还是被抢占？top 第三行、vmstat、mpstat、sar -u
第 3 层 · 进程哪个进程在吃 CPU？吃了多少？top 进程列表、ps --sort=-%cpu、pidstat -u
第 4 层 · 线程/代码进程里是哪个线程？这个线程在干什么？top -H、pidstat -t、perf top、jstack（Java）
记忆口诀

「先看 top 全局，再用 vmstat 看是不是 CPU 的事，mpstat 看哪个核，pidstat 揪出进程，最后 perf / jstack 看它到底在干嘛。」

缺命令怎么办

mpstat / sar / pidstat 属于 sysstat 包：yum install -y sysstat（CentOS 系）或 apt install -y sysstat（Ubuntu 系）。htop 同理单独安装。其他命令系统自带。

一套典型的排查动线​

接到「CPU 报警」工单后，最朴素也最有效的动线如下（详细步骤见高 CPU 排查流程）：

  1. uptime：3 秒看负载，确认问题是否持续；
  2. top：确认是 us 高、sy 高还是 wa 高，找出 CPU 最高的进程 PID；
  3. vmstat 1 5：看 r（运行队列）和 cs（上下文切换），判断是否 CPU 过载或切换风暴；
  4. top -Hp PID：锁定进程内吃 CPU 的线程号；
  5. 按语言深入：Java 用 jstack，其他用 perf top 或 strace，定位到具体代码。
两个新手常踩的坑
  • 只跑一次 top 就下结论。top 的 %CPU 是瞬时值，要连续看几次、或者看 TIME+ 的累计增速；
  • 报警了才想起来没装 sysstat、没有历史数据。平时就应装好并开启 sar 采集，出问题时才能对比基线。

接下来学什么​

命令家族的详细讲解分两批：

  • top / htop：最常用的全局视图，输出逐行解读 + 快捷键；
  • vmstat / mpstat：判断是不是 CPU 的事、哪个核在忙；
  • sar / pidstat：看历史趋势、精确定位到进程和线程；
  • 进阶工具与实践：USE 方法论、火焰图、strace、压测与监控对接（掌握基础后再看）。

top / htop​

top 是排查 CPU 问题的第一入口：打开就能同时看到整机状态和进程排名。这一章把 top 的输出拆成一行一行讲透，再介绍几个高频用法和快捷键，最后说说更友好的 htop。

%CPU 是「最近一次采样」的瞬时值，抖动很大。TIME+ 是开机以来的累计 CPU 时间——一个进程 TIME+ 每秒都在快速增长，才是真正稳定的 CPU 消耗者。排查时两个都看：先按 %CPU 排序找嫌疑，再用 TIME+ 确认它是不是长期吃 CPU。

实战示例：锁定吃 CPU 的 Java 线程​

场景：8 核机器 CPU 报警，业务卡顿。第一步，top -d 1 并按 P，发现 java 进程 PID=4321 的 %CPU 高达 145%（约占了 1.5 个核）。第二步，查看这个进程内部的线程，找出具体是哪个线程在烧 CPU：

htop 的颜色含义

vmstat / mpstat​

top 回答「整体忙不忙」，vmstat 回答「是不是真的 CPU 的事」，mpstat 回答「哪个核在忙」。这两条命令能帮你把问题从「机器层面」下钻到「CPU 层面」。

怎么用 vmstat 快速下结论：记住这张「诊断决策表」，基本能覆盖日常 90% 的场景：

看到的现象初步结论下一步
r 高（>核数）且 us 高CPU 真的过载，业务计算量大top/pidstat 找进程 → 优化代码或扩容
r 高但 us/sy 都不高，wa 高磁盘 IO 瓶颈，任务堵在读写上查磁盘（iostat / iotop），优化 SQL、缓存、日志

所有核都高 → 整体过载，正常扩容即可。个别核 100% 其他核很闲 → 通常是单线程程序、CPU 绑核（taskset）、或网卡中断集中在一个核上。后者要查中断分布并考虑开启多队列。

本章小结

vmstat 帮你做「分诊」：r 高看 CPU、wa 高看磁盘、cs 高看切换、si/so 高看内存。mpstat 帮你做「分核」：确认是全核过载还是单核热点。两条命令配合，问题方向基本就锁定了。

sar / pidstat​

sar 帮你回答「过去一段时间 CPU 是怎么变化的」（历史回溯），pidstat 帮你回答「具体哪个进程/线程在烧 CPU、切换有多频繁」（精准定位）。两条命令都来自 sysstat 包。

sar：历史数据回溯​

先让 sar 开始自动采集：sar 的价值在于出问题之前就在记录。装好 sysstat 后，默认每 10 分钟采集一次，数据存在 /var/log/sa/ 目录。检查采集是否开启（发行版机制不同）：

$ ls /var/log/sa/                  # 有 saXX 文件说明在采集（通用检查法）
sa14  sa15  sa16  sa17

# Ubuntu / Debian：systemd 服务与定时器
$ systemctl status sysstat sysstat-collect.timer

# CentOS / RHEL / openEuler：走 cron 任务
$ cat /etc/cron.d/sysstat
# Run system activity accounting tool every 10 minutes
*/10 * * * * root /usr/lib64/sa/sa1 1 1
血泪教训

很多新人排查时才发现「之前没开采集，现在没有历史数据」。强烈建议所有服务器都装上 sysstat 并开启采集，出问题时才能回溯「CPU 是什么时候开始高的、和哪个发布/变更相关」。

pidstat 是「带 PID 的 sar」，把 CPU 消耗精确到每个进程，再往下能到每个线程。

看所有进程的 CPU 占用（按进程）：

$ pidstat -u 1 5

14:23:06     1001      4321    0.00   12.50    0.00    0.00   12.50     3  java

%wait等待 CPU 的时间占比（在排队）

$ pidstat -t -p 4321 1 3

14:23:06     1001      4321    0.00   12.50    0.00    0.00   12.50     3  java
14:23:06     1001      4356    0.00   88.75    0.00    0.00   88.75     0  |__java

$ pidstat -w 1 3

14:23:06     1001      4321   820.00    150.00    java
14:23:06     1001      5120  2100.00     80.00    app-worker

nvcswch/s每秒非自愿切换次数被强制换下 → 任务太多、CPU 不够分
切换风暴怎么看

vmstat 的 cs 高是「警报」，pidstat -w 是「溯源」：逐进程看谁的 cswch/s 异常高，然后针对它查锁和线程池配置。

  • TIME 列是累计 CPU 时间，和 top 的 TIME+ 一个意思。

如果进程是自家代码、且想直接看到热点函数，用 perf 采样（需要 root 权限）：

第三部分 排查与解决​

高 CPU 排查流程​

前面学的所有命令，在这一章串成一条可以照做的流程。核心原则：从宏观到微观，逐层收窄，先别急着抓线程，先把方向判断对——尤其要先确认「高的是不是 CPU」。

第 0 步：先确认现象与影响面​

动手之前先搞清楚三个问题：

  • 报警来源是什么？监控指标是负载、使用率还是响应时间？数值是多少、持续了多久？
  • 业务受影响了吗？接口变慢、超时、还是只是指标高但业务正常？如果业务正常，可以按常规流程慢慢查；如果业务已受损，先看应急止损。
  • 最近有变更吗？发布、配置、数据量、流量上涨？变更和 CPU 变高的时间点对得上，往往就是直接线索。
变更对比是最高效的手段

用 sar -u -f /var/log/sa/saXX 看最近几天的 CPU 曲线，找到「开始变高」的时间点，和发布记录一对比，一半的问题当场就有答案。

第 1 步：看全局——负载与整体使用率​

用 uptime 快速确认负载，用 top -d 1 看整体：

$ uptime
 14:23:05 up 42 days,  3:12,  2 users,  load average: 7.82, 6.35, 4.21

$ top -d 1
%Cpu(s): 68.5 us, 12.3 sy,  0.0 ni, 15.4 id,  2.8 wa,  0.3 hi,  0.7 si,  0.0 st

看两个数：负载相对核数是否超标、%Cpu(s) 里是 us 高、sy 高还是 wa 高。这里 1 分钟负载 7.82（8 核）且 us 68.5%，CPU 确实在忙——进入下一步。

如果看到的是「负载高但 us/sy/id 都不高、wa 高」，请直接转向swap 抖动 / IO 等待问题，别再纠结 CPU。

第 2 步：分诊——是不是真的 CPU 过载​

用 vmstat 连续采样，判断问题性质：

$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 8  0      0 5120344 123456 14698456    0    0    12    18 3456 28904 65 18 12  5  0
 9  0      0 5109876 123456 14700123    0    0    10    16 3612 31256 68 16 11  5  0

关注：r（是否大于核数）、cs（是否异常高）、us/sy/wa 的分布。r=8~9（8 核）说明任务排队了；cs=3 万左右/秒，暂不算爆炸，继续往下追。

vmstat 特征判断
r 高 + us 高CPU 过载，业务计算量大 → 直接定位进程
r 高 + wa 高磁盘 IO 瓶颈 → 转查 IO
r 高 + b 大 + us/sy/wa 都不高锁/资源等待 → 查线程阻塞
cs 高 + sy 高上下文切换风暴 → 用 pidstat -w 溯源

第 3 步：定位进程——谁在烧 CPU​

top 里按 P 按 CPU 排序，或直接用 pidstat / ps：

$ top -d 1          # 然后按 P
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+  COMMAND
   4321 appuser   20   0 3421568   1.2g  24300 S 145.3   3.8  432:15.6 java

$ ps aux --sort=-%cpu | head -5
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
appuser  4321 145.3  3.8 3421568 123456 ?       Ssl  09:12 432:15 java

锁定 PID=4321（java）。记下 TIME+ 的值，几秒后再看一次，确认它在持续增长——防止误抓瞬时峰值。

第 4 步：定位线程——进程里是哪个线程​

$ top -Hp 4321 -d 1
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+  COMMAND
  4321 appuser   20   0 3421568   1.2g  24300 S  96.3   3.8  430:12.5 java
  4356 appuser   20   0 3421568   1.2g  24300 R  90.1   3.8  128:33.2 java

线程 PID=4356 是「罪魁」。注意线程号是十进制，后面转十六进制用。

第 5 步：深入代码——线程到底在干什么​

按技术栈分路：

  • Java：jstack 4321，找 nid=0x1104（4356 的十六进制，用 printf '%x\n' 4356 转换），看线程状态和栈顶方法；
  • Go / C / C++ 等：perf top -p 4321 看热点函数；必要时 perf record + perf report；
  • Python：py-spy dump --pid 4321 或 py-spy top（无需侵入代码）；
  • 内核态热点：perf 里看到 [kernel] 符号（如自旋锁、中断处理），结合 vmstat 的 sy/in 判断。
$ printf '%x\n' 4356
1104

$ jstack 4321 | grep -A 20 "nid=0x1104"
"pool-3-thread-5" ... nid=0x1104 runnable ...
    java.lang.Thread.State: RUNNABLE
        at com.example.OrderService.calcPrice(OrderService.java:88)
        at com.example.OrderService.process(OrderService.java:120)

到这一步，问题已经具体到文件 + 行号。剩下的交给代码评审和修复。

现场信息采集：一屏命令​

问题处理完前，先把现场证据留下来。下面这组命令可以在几分钟内完成「现场快照」，后续复盘和写报告都靠它：

$ date '+%F %T'                                     # 1. 时间戳（一切证据的锚点）
$ uptime                                            # 2. 负载
$ top -b -n 3 -d 1 | head -60                       # 3. top 快照 3 次
$ vmstat 1 5                                        # 4. 分诊数据
$ mpstat -P ALL 1 3                                 # 5. 按核数据
$ pidstat -u -w -t -p <PID> 1 5                     # 6. 进程线程 CPU+切换
$ ps aux --sort=-%cpu | head -20                    # 7. 进程排序快照
$ cat /proc/<PID>/status                            # 8. 进程状态（线程数、状态）
# Java 场景额外：
$ jstack <PID> > jstack_$(date +%s).txt              # 9. 线程栈

把这些输出保存成文件，连同告警截图、变更记录一起归档。写复盘报告时，这些数据能直接回答「什么时间、什么进程、什么原因」。

1. 真实业务高峰​

特征：us 高、r 高、负载和业务量曲线同步上涨；CPU 高的进程是自家业务进程，线程栈显示在正常处理请求。

确认：用 sar -u -f /var/log/sa/saXX 对比历史，看是否与流量高峰吻合；jstack 看到的栈都是正常业务逻辑。

结论：这不是故障，是容量问题。按扩容与优化处理，必要时限流保护。

2. 死循环 / 空转（最常见代码 bug）​

特征：某个线程 us 长期接近 100%，TIME+ 快速增长；进程总 CPU 可能只占 1 个核，所以「使用率只有十几%」也藏得住，但单线程已经烧满。

确认：top -Hp PID 找到烧满的线程 → jstack 看栈，通常停在某个 while/递归/自旋上，且反复 dump 两次栈位置一样。

$ jstack 4321 | grep -A 30 "nid=0x1104"
    java.lang.Thread.State: RUNNABLE
        at com.example.OrderService.calcPrice(OrderService.java:88)   ← 两次 dump 都停在这里

解法：修代码（退出条件、递归边界）；应急可先重启进程。

3. 频繁 GC（Java 应用）​

特征：us 不高、但应用吞吐量骤降；CPU 整体中高；GC 日志里 Full GC 频繁。GC 线程本身也占 CPU。

确认：

$ jstat -gcutil 4321 1000 10
  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00   0.00  98.72  95.10  96.5   95.0   45210  320.5   1287  1180.3  1500.8   ← O 区 95%、FGC 1287 次

老年代（O）持续 90%+、FGC 次数暴涨，就是内存压力导致的 GC 风暴。

解法：查内存泄漏（MAT/jmap 分析堆）、调堆大小与 GC 参数、加内存。详见JVM 调优。

4. 锁竞争 / 线程大量阻塞​

特征：us 不高、cs 高、sy 偏高，vmstat 的 b 列大于 0；应用却卡顿（任务都在排队等锁）。

确认：pidstat -w 看哪个进程 cswch 高；Java 用 jstack 找大量 BLOCKED / WAITING 状态的线程和锁点：

$ jstack 4321 | grep -c "java.lang.Thread.State: BLOCKED"
247      ← 大量线程堵在同一把锁上

解法：降低锁粒度、用无锁结构、线程池调优、缓存热点数据。

5. 上下文切换风暴​

特征：vmstat 的 cs 每秒几十万次，sy 明显偏高，id 可能不低但系统很「忙」。

确认：

$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  0      0 5120344 123456 14698456    0    0    12    18 3456 289040 10 30 58  2  0
                                                                    ^^^^^^ cs 近 30 万/秒
$ pidstat -w 1 5    # 溯源：哪个进程在疯狂切换
14:23:06   UID       PID   cswch/s nvcswch/s  Command
14:23:07  1001      4321   820.00    150.00    java
14:23:07  1001      5120  2100.00     80.00    app-worker  ← 嫌疑

常见诱因：线程池线程数过多 + 频繁 sleep/等锁空转、频繁的短小系统调用、定时器过多。

解法：线程数调优、避免忙等、合并小请求、调整内核调度参数。详见调度优化。

6. 中断 / 软中断风暴​

特征：top 里 si 或 hi 长期偏高；mpstat 可能显示某个核被中断占满；vmstat 的 in 异常高。常见于：网卡流量巨大且中断集中在单核、驱动 bug、磁盘控制器异常。

确认：看中断分布：

$ cat /proc/interrupts | grep -i eth0 | head -5
           CPU0       CPU1       CPU2       CPU3
 28:   123456789          0          0          0  IR-PCI-MSI  eth0-TxRx-0
 29:           0  987654321          0          0  IR-PCI-MSI  eth0-TxRx-1   ← 中断全压在个别核

解法：开启网卡多队列并让 irqbalance 均衡中断（详见调度与系统层 · 中断优化）；必要时换驱动/硬件。

7. swap 抖动（内存不足连累 CPU）​

特征：vmstat 的 si / so 持续不为 0，wa 升高，CPU 整体「中高但不健康」；应用响应变慢。

确认：free -h 看内存；vmstat 看 si/so；top 里按 M 看哪个进程吃内存。

本质：内存不够，系统把进程内存搬到磁盘（swap），进程要用的再搬回来，磁盘读写拖垮一切。这是「内存问题伪装成 CPU/性能问题」的经典场景。

解法：加内存、优化内存占用、排查泄漏。

8. 日志风暴​

特征：wa 高、bo 高；应用 CPU 中上但明显「事倍功半」；磁盘 IO 忙。常见于：DEBUG 日志全量打开、异常日志刷屏、日志不轮转导致单文件巨大。

确认：看日志文件增长速度和磁盘 IO；iostat -x 1 看磁盘 util。

解法：日志级别调回 INFO、异常日志限流/去重、配置 logrotate 轮转。见日志治理。

9. 定时任务重叠执行​

特征：CPU/负载呈规律性周期脉冲（每天/每小时固定时间高）；sar 历史曲线最明显。

确认：用 sar 找到飙高时间点，对照 crontab：

$ crontab -l
0 2 * * *  /opt/scripts/backup.sh      ← 和 CPU 飙高时间吻合
0 2 * * *  /opt/scripts/analyze.sh     ← 多个大任务都排在 2 点

解法：错峰调度、任务加锁防重入（flock）、拆分大任务。

10. 容器 CPU 限制与抢占​

特征：容器内应用卡、容器内看 CPU 很高，但物理机其他进程都不忙；或 top 里 st 很高。两种子场景：

  • 配额用完（throttled）：容器 CPU 限额（如 2 核）被跑满，内核强制限流，应用变慢但物理机很闲；
  • 邻居抢占（steal）：虚拟机被宿主机上其他 VM 抢 CPU，top 的 st 高。

确认：查容器 cgroup 统计。注意 cgroup v1 与 v2 的路径和字段不同，先确认当前内核用的是哪个版本：

$ stat -fc %T /sys/fs/cgroup
cgroup2fs        ← 输出 cgroup2fs 是 v2；tmpfs 是 v1

cgroup v2（新发行版默认，路径为 cgroup 目录下的 cpu.stat）：

$ cat /sys/fs/cgroup/cpu.stat
usage_usec 180000000
user_usec 150000000
system_usec 30000000
nr_periods 100
nr_throttled 60        ← 60% 的时间窗被限流，配额不够用
throttled_usec 45000000

cgroup v1（老发行版，路径为 cpu 控制器下的 cpu.stat）：

$ cat /sys/fs/cgroup/cpu/cpu.stat
nr_periods 100
nr_throttled 60
throttled_time 45000000000        ← 字段名是 throttled_time（纳秒），不是 throttled_usec

解法：提高容器 CPU 限额、合理设置 request/limit、或把容器调度到空闲宿主机。限流次数（nr_throttled / nr_periods）越高，说明配额不足越严重。

11. 挖矿 / 恶意进程​

特征：陌生进程 CPU 接近 100%；用户名可疑（如 nobody、随机名）；进程名伪装（如 systemd 的变体、奇怪路径）；有异常外联。

确认：

$ ps aux --sort=-%cpu | head -5     # 找陌生高 CPU 进程
$ ls -l /proc/<PID>/exe              # 可执行文件路径是否可疑
$ ss -tnp | grep <PID>               # 是否有异常外联
$ ls -l /proc/<PID>/cwd              # 工作目录

处置：先隔离（断网/停进程），保留现场，再溯源漏洞并修复；不要在生产环境草率删除后不查原因。

排查时先看总览表，对照「你最像哪一行」，再用对应的确认命令验证。特征对上了，解法基本就写在解决方案里。

解决方案​

上一章认识了「病因」，这一章给出「药方」。处理思路分三层：先应急止损（让业务先恢复）→ 再对症根治（修复根因）→ 最后建立预防（监控与基线，让问题不再裸奔）。

1. 应急止损：业务优先​

业务已经受损（超时、不可用）时，先恢复服务，再谈根治。应急手段按影响从小到大排列：

手段做法适用场景
限流 / 摘流量网关限流、把节点从负载均衡摘掉流量突增、容量不足，保留部分服务能力
降低单机负载临时扩容实例、让其他节点分担集群场景最优先考虑
重启应用systemctl restart 服务 / 重启容器死循环、GC 风暴、内存泄漏（治标）
调整进程优先级renice -n 10 -p PID 让可疑进程礼让次要任务抢占资源时，保住关键业务
杀进程kill -9 PID（确认后再执行）挖矿、失控脚本等必须终止的场景
应急的纪律

应急前尽量先抓一份现场（见现场采集命令）；重启和杀进程都不可逆，先确认 PID 确实是目标进程，别杀错。应急只是止血，根因必须后续跟进，否则下次还会犯。

2. 代码层根治（us 高的主战场）​

  • 死循环 / 空转：补退出条件、递归边界、超时控制；用「限次重试 + 退避」替代忙等（busy-wait）；
  • 算法与计算量：热点路径用更高效的算法/数据结构；把重复计算挪到缓存（本地缓存/Redis）；
  • 锁竞争：缩小锁范围、降低锁粒度、读写分离、用无锁结构（如 ConcurrentHashMap、原子类）；
  • IO 误用：日志别放业务热路径；N+1 查询合并；批量读写；
  • 线程模型：线程池大小按「任务类型」设置——CPU 密集任务约等于核数，IO 密集任务可多配但别失控（参考线程数参考）。

3. JVM 层（Java 应用）​

GC 风暴和 JVM 线程问题，重点看四件事：

  • 堆与老年代：jstat -gcutil 里 O 区长期 90%+、FGC 频繁 → 调大堆（-Xmx）或排查泄漏；
  • GC 参数：JDK 8 默认 Parallel GC 适合吞吐型；延迟敏感应用可评估 G1（-XX:+UseG1GC）并设置 -XX:MaxGCPauseMillis；
  • 对象分配：jmap -histo 看对象数排名，揪出「无限增长」的集合。注意：加 :live 会先触发一次 Full GC，生产环境慎用，优先用不带 :live 的 jmap -histo，或在低峰期执行；
  • 线程状态：jstack 里大量 BLOCKED → 锁问题；大量 WAITING → 线程池/连接池配置问题。
$ jmap -histo 4321 | head -20          # 对象直方图（不带 :live，避免触发 Full GC）
 num     #instances         #bytes  class name
   1:      15200000     1216000000  [B
   2:        980000       156800000  com.example.OrderDetail

一份可直接参考的 JVM 启动参数：以 8G 堆、延迟敏感的 Web 服务为例（按实际堆大小和 JDK 版本调整，改参数=改配置，要有评审和回滚预案）：

$ java -Xms8g -Xmx8g \
    -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
    -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/ \
    -Xlog:gc*:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=5,filesize=64m \
    -jar app.jar
  • -Xms = -Xmx：堆初始=最大，避免运行期反复扩缩堆（减少 GC 抖动）；
  • G1 + MaxGCPauseMillis：把 GC 停顿控制在目标内（默认 Parallel GC 偏吞吐，停顿不可控）；
  • OOM 自动 dump 堆 + GC 日志轮转：出事时留下证据；
  • 验证方式：改完后压测对比 FGC 次数与 P99（见sysbench 压测），观察 jstat -gcutil。

4. 调度与系统层​

线程数怎么定（经验值）：

  • CPU 密集任务：约等于核数（甚至核数 + 1）；
  • IO 密集任务：核数 × (1 + 等待时间/计算时间)。宁可少配、用队列排队，也不要配到几百个线程空转抢锁。

进程优先级与绑核：

$ renice -n 10 -p 5120        # 让次要进程礼让（nice 越大越谦让）
$ taskset -pc 2,3 5120        # 绑到 2、3 号核（谨慎使用，可能反而加剧核间不均）

中断均衡与网卡多队列——解决「si 高 + 中断集中在单核」：

$ systemctl start irqbalance    # 让系统自动均衡中断
$ ethtool -l eth0               # 查看网卡队列数（Combined 行）
$ ethtool -L eth0 combined 8    # 开启多队列，配合 RPS/RSS 分散收包到多核

内核参数（谨慎，默认通常够用）：一般不需要调内核。只有确认是调度/换页问题才考虑，且必须小步变更 + 观察 + 可回滚。具体写法：

$ sysctl -w vm.swappiness=10             # 临时生效（重启失效）：内存吃紧时降低换页倾向
$ echo "vm.swappiness=10" >> /etc/sysctl.d/99-cpu.conf   # 永久生效
$ sysctl --system                        # 重新加载配置
$ sysctl vm.swappiness                   # 确认当前值
# 改完观察：vmstat 的 si/so 是否归零、wa 是否回落；异常则改回原值并重载

变更验证与回滚规范：任何「优化」都必须能证明有效、且随时可退。建议遵守：

  1. 改前留基线：记录当前 CPU/负载/业务指标，压测留档（sysbench）；
  2. 小步单变量：一次只改一个参数，改了谁、为什么改、预期效果写清楚；
  3. 验证三看：改后看指标是否改善（对比基线）、业务是否正常、有无副作用（日志、GC、内存）；
  4. 回滚预案：记录原配置；异常时 5 分钟内能恢复（配置文件备份 / 启动参数脚本化）；
  5. 沉淀：有效的调整写入配置管理/发布脚本，避免「手工调优只活在一台机器上」。

5. 日志治理​

  • 生产环境日志级别保持在 INFO 及以上，禁止全量 DEBUG；
  • 异常日志「去重 + 限流」（如 logback 的过滤器，同一错误每分钟只打一条）；
  • 配置 logrotate 轮转 + 保留份数，防止单文件无限膨胀：
# /etc/logrotate.d/app
/var/log/app/app.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
    copytruncate
}

6. 定时任务错峰​

  • 大任务分散到不同时间点，避开整点扎堆（0 点/2 点是重灾区）；
  • 给任务加防重入锁：
$ crontab -l
0 2 * * *  /usr/bin/flock -n /tmp/backup.lock /opt/scripts/backup.sh
  • 超大任务拆分切片，分批执行；监控任务执行时长，超时报警。

7. 容量与架构优化（真实高峰）​

  • 扩容：加实例 / 加核，是最直接的容量手段（先确认是真过载而非其他问题）；
  • 缓存：把重复计算/热点查询缓存起来，减少 CPU 密集操作；
  • 限流与降级：入口限流（Sentinel、网关限流），峰值期保护系统不被打穿；
  • 异步化：非关键路径（短信、通知、报表）异步处理，削峰；
  • 读写分离 / 分库分表：数据库慢查询和连接风暴是 CPU 高的隐形推手。

8. 容器与虚拟化​

  • 容器配额不够（nr_throttled 高）→ 调大 limit、优化资源分配；
  • steal 高 → 联系平台方检查宿主机负载与超卖比例，迁移到空闲节点；
  • 给容器设置合理的 CPU request/limit，避免相互干扰。

Kubernetes 下的具体对应关系（cgroup v2）：

K8s 配置含义对应 cgroup 文件
requests.cpu: 2保障 2 核（调度依据）cpu.weight（份额）
limits.cpu: 4上限 4 核（超过会被限流 throttled）cpu.max（配额）
  • 确认限流：容器内 cat /sys/fs/cgroup/cpu.stat 看 nr_throttled；
  • 调优原则：requests 宁高勿低（调度保证），limits 按真实峰值留 20~30% 余量；CPU 密集应用避免 limits 与核数一致导致频繁限流。

9. 安全处置（挖矿等）​

  1. 隔离：立即断网/停进程，防止扩散和外联；
  2. 取证：保存进程信息、/proc、启动项、crontab、ssh 授权等现场；
  3. 溯源：查清入侵途径——弱口令、未授权服务、漏洞利用；
  4. 加固：改密码、补漏洞、最小化暴露面，并加入安全监控。

10. 预防体系：让问题不再裸奔​

比「会修」更重要的是「早发现」。建议建立以下监控（经验阈值，按自己业务基线校准）：

指标建议监控项经验告警线（仅供参考）
负载load 1/5/15 分钟持续 > 核数 × 0.7 预警，> 核数 告警
CPU 使用率us / sy / wa / st持续 > 85% 告警；wa > 30% 预警磁盘
上下文切换cs / 每秒相对基线翻倍且持续，或 > 10 万/秒
运行队列vmstat r持续 > 核数
进程级TopN 进程 %CPU单进程长时间占满多核告警
业务指标接口响应时间 / 错误率与 CPU 联动分析

同时：所有机器开启 sysstat 采集、保留至少 30 天历史；每次发布后对照 CPU 曲线；把本章和成因章节沉淀成团队的「故障手册」。
