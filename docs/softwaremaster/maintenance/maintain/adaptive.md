# 适应性维护

> 使软件适应运行环境的变化（如操作系统升级、数据库升级、硬件变更、法规变化）。

适应性维护的特点是：**软件本身没有错，是外部世界变了**。

## 常见的外部变化来源

| 类别 | 例子 |
| --- | --- |
| 运行时环境 | 操作系统、语言版本、运行时升级 |
| 中间件与依赖 | 数据库、消息队列、第三方库版本 |
| 平台与基础设施 | 云服务商变更、容器运行时升级 |
| 外部接口 | 上游 API 版本变化、协议升级 |
| 硬件与架构 | 指令集、GPU、存储介质 |
| 法规与合规 | 数据保护法规、行业标准更新 |
| 安全要求 | 加密算法淘汰、基线要求提高 |

其中**依赖与法规**是最高频的两类。

## 为什么适应性维护容易被推迟

它通常**没有直接的用户可见收益**，因此优先级容易被压低。但推迟的代价是累积的：

| 推迟的后果 | 说明 |
| --- | --- |
| 版本跨度变大 | 跨越多个大版本的升级风险显著上升 |
| 失去安全补丁 | 旧版本不再获得修复，暴露面扩大 |
| 被迫紧急升级 | 上游停止支持时必须在短时间内完成 |
| 人才与生态问题 | 过时的技术栈难以招聘与获取支持 |

**技术栈的落后是一种持续累积的风险**，而非稳态。

## 降低适配成本的手段

| 手段 | 作用 |
| --- | --- |
| 依赖隔离 | 通过适配层封装外部依赖，减少直接耦合 |
| 版本锁定 + 定期升级 | 避免随机漂移，同时保持小幅前进 |
| 兼容性测试 | 在升级前验证行为是否变化 |
| 特性开关 | 让新旧行为可以并存与切换 |
| 契约测试 | 保证对外接口变更被及时发现 |

其中**适配层**（防腐层）最关键：把外部依赖隔离在薄薄一层内，替换时只改这一层。参见[软件架构](../../develop/development/architecture/index.md)。

## 与需求中兼容性的关系

适应性维护的具体要求应当来自[兼容性需求](../../requirement/analysis/nonfunctional/compatibility.md)：支持哪些平台、哪些版本、承诺多长时间。没有明确承诺，适应性维护的边界就无法判断。

## 实践建议

- 建立依赖清单与版本跟踪，明确每个依赖的支持周期与升级计划。
- 保持小步升级的习惯：定期做小幅版本更新，避免积累成大跨度迁移。
- 升级前在预发环境做完整回归，尤其是隐含行为变化的依赖。
- 关注上游的废弃通告（deprecation notice），提前规划而非被动响应。
- 把升级所需的环境变更一并纳入[交付](./../delivery/index.md)流程与回滚方案。
