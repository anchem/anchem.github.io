# 预防性维护

> 为了降低未来发生故障的可能性而进行的修改（如重构代码以提高可维护性、更新易过期的库）。

预防性维护的特点是**收益在未来、成本在当下**，因此最容易被推迟——也最容易被积累成无法处理的技术债。

## 典型内容

| 类型 | 具体动作 |
| --- | --- |
| 结构 | 重构、消除重复、拆分过大模块 |
| 测试 | 补充测试覆盖、修复脆弱测试 |
| 依赖 | 更新版本、替换停止维护的依赖 |
| 安全 | 修复扫描发现的问题、淘汰弱算法 |
| 文档 | 补架构决策记录、更新运行手册 |
| 可观测性 | 补充指标、日志、追踪 |
| 容量 | 提前扩容、消除单点 |
| 数据 | 清理无用数据、优化索引 |

## 为什么必须制度化

预防性维护的困境在于：**不做也不会有即时后果**。

| 短期视角 | 长期结果 |
| --- | --- |
| 省下时间做功能 | 修改成本持续上升 |
| 风险无法量化 | 债务持续累积 |
| 无人负责 | 直到系统「改不动」 |

破解方式是把预防性维护**纳入常规流程而非专项活动**：

1. **固定配额**：每次迭代留出一定比例用于技术债与预防性工作。
2. **随需处理**：改动某模块时顺手改善该模块（见[重构](../../develop/development/implementation/refactor/index.md)）。
3. **自动化拦截**：把质量门槛放进[流水线](../../develop/development/engineering/ci-cd.md)，防止新增债务。
4. **显式记账**：把技术债记录为可估算的条目，而不是模糊的「以后再说」。

## 技术债的记录方式

技术债应当像缺陷一样被登记：

| 字段 | 内容 |
| --- | --- |
| 问题 | 具体是什么（不是「代码烂」） |
| 影响 | 导致什么代价（修改慢、易出错、有风险） |
| 触发条件 | 什么情况下会出问题 |
| 处理成本 | 估算的工作量 |
| 不处理的后果 | 时间越久代价有多大 |

其中「**触发条件」与「不处理的后果」是关键**：它们把模糊的债务变成可排序的风险项。一个不会触发的债务，可以安全接受。

## 预防与过度预防

预防性维护同样有过度的一面：

- 为不可能出现的规模做优化；
- 为不会发生的场景增加容错，使代码复杂度上升；
- 提前替换仍被广泛支持且稳定的依赖。

判断标准是**风险的真实性**：有依据的风险（监控数据、行业事故、上游通告）值得预防；凭想象的风险不值得。

## 实践建议

- 把预防性维护纳入迭代计划，而不是等「有空再说」——那个时刻不会到来。
- 优先处理有明确触发条件的债务，而非所有不完美之处。
- 用自动化工具持续发现新增债务，成本远低于事后集中治理。
- 定期评估债务清单，剔除已经不再成立的条目。
- 让预防性工作的成果可衡量（如修改耗时下降、缺陷率下降），以便持续获得投入。
