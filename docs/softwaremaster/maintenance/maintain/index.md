# 软件维护

> 在软件发布后，为纠正缺陷、适应环境变化、改进性能或增加新功能而进行的修改活动。

维护是**基于运营中发现的问题或业务提出的新需求进行的有计划的变更工作**，通常涉及代码或配置的修改。

## 包含内容

| 类型 | 目的 |
| --- | --- |
| [纠错性维护](./corrective.md) | 修复运营中发现的软件缺陷 |
| [适应性维护](./adaptive.md) | 使软件适应运行环境的变化 |
| [完善性维护](./perfective.md) | 改进现有功能或性能 |
| [预防性维护](./preventive.md) | 降低未来发生故障的可能性 |

## 具体对象的维护实践

上面四类是按**变更目的**划分的通用分类，回答「为什么要改」。在具体对象上落地时，还需要针对该对象的特点组织实践，回答「具体怎么做」：

| 框架 | 对象 |
| --- | --- |
| [Linux 服务器维护](./linux-server/index.md) | 生产环境 Linux 服务器的资源观测与故障处置 |

两者是互补关系：通用分类帮你判断一次维护属于哪一类、该走什么流程；对象实践帮你在一台真实的机器上把问题定位出来。

## 【目的】

修复问题、适应变化、提升质量、延长软件生命周期价值。

## 为什么维护成本如此重要

大型软件的维护成本可以达到开发成本的 **4 倍**左右。这个量级意味着：

- 一次「便宜做完」的交付，会在后续若干年持续产生成本；
- 维护工作的效率直接决定产品的长期盈利空间；
- 维护不是「收尾工作」，而是产品生命周期中最长的阶段。

影响维护成本的主要因素：

| 因素 | 影响 |
| --- | --- |
| 可读性 | 理解代码的时间占比最高 |
| 测试覆盖 | 决定改动的信心与回归成本 |
| 文档与记录 | 缺少决策记录会导致重复讨论 |
| 结构耦合 | 决定改动的影响面 |
| 环境影响 | 环境差异导致的故障难以定位 |

这些因素都在[需求](../../requirement/analysis/nonfunctional/maintainability.md)、[设计](../../develop/development/design/index.md)与[实现](../../develop/development/implementation/index.md)阶段被决定——**维护成本是前面所有阶段的最终账单**。

## 维护与重构的关系

维护过程中修改代码时，应当顺手改善阻碍修改的结构，参见[重构](../../develop/development/implementation/refactor/index.md)。若不这样做，维护成本会单调上升，最终达到「改不动」的状态。

## 一条纪律

维护工作应当**有计划、有记录、有验证**，与新增功能同等对待。把维护当作「顺手改一下」的临时任务，会导致改动缺乏回归验证，并逐渐侵蚀系统质量。
