# 完善性维护

> 根据用户反馈或运营数据分析，改进现有功能或性能（非新增功能）。

完善性维护与新增功能的界限在于：**它不扩大系统的能力边界，而是让已完成的能力发挥得更好**。

## 主要方向

| 方向 | 典型动作 |
| --- | --- |
| 性能 | 优化耗时路径、降低资源消耗、改善长尾 |
| 体验 | 减少操作步骤、改善错误提示、加快感知响应 |
| 质量 | 提高准确率、减少误报、增强一致性 |
| 可维护性 | 重构、补测试、补文档 |
| 成本 | 降低单位资源消耗 |

其中**成本优化**常被忽略：随着规模增长，单位成本的改善带来的收益会成倍放大。

## 与其他维护类型的边界

| 类型 | 触发原因 | 是否改变行为 |
| --- | --- | --- |
| 纠错性 | 行为不符合预期 | 修正到预期 |
| 适应性 | 外部环境变化 | 保持不变的行为 |
| 完善性 | 有改进空间 | 在预期内改善 |
| 预防性 | 预判未来风险 | 通常不改变 |

边界不清时，容易把「新需求」伪装成「优化」而跳过需求评估。判断标准是：**它是否引入了系统此前不具备的能力**。是，则属于[需求](../../requirement/index.md)范畴，应当走完整流程。

## 数据驱动的改进

完善性维护的最大优势是**有真实数据作为依据**：

| 数据来源 | 可发现的改进点 |
| --- | --- |
| 性能指标 | 慢接口、长尾请求、资源热点 |
| 用户行为 | 高跳出路径、被反复使用的绕行方案 |
| 工单与反馈 | 高频困惑点、反复出现的误操作 |
| 错误统计 | 集中发生的异常类型 |
| 成本账单 | 异常增长的资源消耗 |

**优先处理「高频 + 高代价」的问题**，而不是声音最大的那个。

## 收益评估

改进类工作的收益往往难以直接测量，容易陷入两种极端：完全不做，或投入过多而收益不明。

实用做法是**先量化问题再动手**：

1. 当前状态是多少？（例如某接口 95 分位 1.2 秒）
2. 目标是多少？（300 毫秒）
3. 改善后影响多少用户与多少请求？
4. 投入成本是多少？

没有第 1 项，就无法证明改进是否发生。**「先测量再优化」是完善性维护最重要的纪律**。

## 实践建议

- 建立问题清单并排序，避免「谁喊得响就先做谁」。
- 改进前记录基线，改进后用同一口径验证。
- 与控制变量配合（如 A/B 对比），避免把外部变化误判为改进效果。
- 与[重构](../../develop/development/implementation/refactor/index.md)结合：改善性能或体验时，顺手处理阻碍修改的结构问题。
- 定期回看已完成改进的实际效果，效果不达预期的应当复盘改进方法而非继续追加投入。
