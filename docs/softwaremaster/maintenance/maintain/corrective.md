# 纠错性维护

> 修复在运营中发现的软件缺陷（Bug）。

纠错性维护是四类维护中**最紧急、也最不可预期**的一类，它的来源是运营阶段暴露的真实问题。

## 处理流程

```
发现 → 分级 → 临时处置 → 根因定位 → 修复 → 验证 → 复盘
```

其中**临时处置与根因修复应当分开**：

| 动作 | 目标 | 时间要求 |
| --- | --- | --- |
| 临时处置 | 恢复服务（回滚、降级、绕行） | 分钟到小时级 |
| 根因修复 | 消除缺陷本身 | 天到周级 |

把两者混为一谈，会导致「为了尽快修根因而延长故障时间」。参见[故障处置](../operation/incident.md)。

## 缺陷分级

不是所有缺陷都同等紧急。分级依据：

| 维度 | 说明 |
| --- | --- |
| 影响范围 | 多少用户、多少数据受影响 |
| 严重程度 | 功能不可用、结果错误、还是体验受损 |
| 是否有绕行方案 | 有绕行方案的可降级处理 |
| 是否会恶化 | 数据损坏类问题会持续扩大 |

其中**数据损坏**应当被视为最高优先级：它有累积效应，且事后修复成本随时间上升。

## 修复的质量要求

纠错性维护最容易犯的错误是**只修表象**：

| 反模式 | 后果 |
| --- | --- |
| 加 if 判断绕过错误条件 | 问题在别的路径上重现 |
| 只修复当前触发路径 | 同一根因的其他表现继续存在 |
| 不补测试 | 问题可能再次引入 |
| 不检查同类代码 | 同一缺陷模式在别处普遍存在 |

**每个缺陷修复都应当产出一条自动化测试**。这是防止回归的唯一可持续方式，也让防护网随项目逐步增厚。

## 缺陷的根因分类

复盘时区分根因类型，有助于找到系统性改进点：

| 根因 | 改进方向 |
| --- | --- |
| 需求理解偏差 | 需求评审与验收标准 |
| 设计缺陷 | 架构评审、质量属性分析 |
| 实现错误 | 测试覆盖、代码审查、静态分析 |
| 环境差异 | 环境治理、配置管理 |
| 变更引入 | 发布策略、灰度与回滚能力 |
| 依赖变化 | 依赖治理与版本锁定 |

## 实践建议

- 修复前先确认能否复现，无法复现的修复无法验证。
- 一次只改一个变量，改完立即验证——多变量同时修改会使结论失效。
- 补测试后再提交修复，把它作为流程的一部分而非可选项。
- 定期统计缺陷分布，识别问题集中的模块，对其实施专项[预防性维护](./preventive.md)。
- 对重复出现的同一类缺陷，从工具或流程层面解决，而不是反复人工修补。
