# 容量与性能

容量管理保证系统**跟得上增长**。它的难点不是扩容本身，而是**在正确的时间扩正确的资源**。

## 容量的三个问题

1. **当前余量多少**：距离饱和还有多远？
2. **何时会饱和**：按当前增长趋势，还有多久？
3. **如何扩展**：扩容的手段、所需时间与成本？

只回答第一个问题是最常见的不完整：知道现在还有余量，但不知道何时用完，也就无法安排提前扩容。

## 容量规划的基本方法

| 步骤 | 内容 |
| --- | --- |
| 明确业务指标 | 用户数、请求量、数据量、峰值特征 |
| 建立资源模型 | 每单位业务量消耗多少资源 |
| 测量实际水平 | 用压测与生产数据校准模型 |
| 留出冗余 | 按峰值而非均值准备，并考虑故障时的容量损失 |
| 设定触发线 | 达到多少余量时启动扩容 |

**冗余必须按「部分故障时仍能承载峰值」来设计**：如果一个可用区故障后剩余容量无法承载，那这个冗余就不是真正的冗余。

## 性能瓶颈的层次

| 层次 | 常见瓶颈 |
| --- | --- |
| 计算 | CPU 饱和、锁竞争、GC 停顿 |
| 内存 | 堆不足、缓存无上限、内存泄漏 |
| IO | 磁盘带宽、随机访问、日志写入 |
| 网络 | 带宽、连接数、跨区延迟 |
| 依赖 | 数据库连接池、第三方接口配额 |
| 架构 | 单点、无法水平扩展的有状态组件 |

**扩容之前必须先定位瓶颈**。盲目增加应用实例在瓶颈位于数据库时毫无作用，只会把压力更集中地打到数据库上。

更关键的是：**有些组件无法通过加实例解决**（时钟、序列号生成、强一致存储），必须在架构层面处理。

## 弹性伸缩

| 方式 | 特点 |
| --- | --- |
| 手动扩容 | 可预测、成本可控，响应慢 |
| 定时伸缩 | 适合有固定波峰的业务 |
| 自动伸缩 | 响应快，需要稳定的触发指标 |
| 弹性 + 预留 | 混合模式，兼顾成本与响应 |

自动伸缩的关键是**触发指标的选择**：CPU 使用率在 IO 密集场景下会失真，应当选用更贴近瓶颈的指标（队列深度、延迟、并发数）。

同时要处理**伸缩的滞后**：实例启动需要时间（镜像拉取、预热、JIT 编译），在突发流量下往往来不及。因此需要预留热容量或提前扩容。

## 压测的有效性

压测容易失真，常见原因：

| 问题 | 后果 |
| --- | --- |
| 数据规模与生产不符 | 小数据下很快，生产规模下不可用 |
| 流量模型不符 | 忽略读写比例、热点分布、突发性 |
| 忽略下游依赖 | 压测环境的下游能力与生产不同 |
| 未预热 | JIT、连接池、缓存均未进入稳定态 |
| 只测单组件 | 无法发现链路上的瓶颈 |

**压测的价值主要在于发现瓶颈位置与验证扩容手段，而不是得到一个绝对容量数字。**

## 实践建议

- 把容量纳入[容量相关的监控指标](./monitoring.md)与定期评审，而不是等出事才关注。
- 建立增长趋势与饱和预测，提前规划而非被动扩容。
- 明确记录每个组件的扩容方式与所需时间，形成可执行的扩容预案。
- 关注成本：容量规划的目标是「够用」，不是「最多」——见[云计算成本约束](../../develop/foundation/cloud/index.md)。
- 定期做容量演练，验证扩容路径在紧急情况下确实可用。
