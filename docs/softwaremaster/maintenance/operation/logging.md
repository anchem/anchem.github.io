# 日志

日志是**事后回溯的唯一凭证**。指标告诉你「出了问题」，日志告诉你「问题是什么」。

## 日志的三个层次

| 层次 | 内容 | 用途 |
| --- | --- | --- |
| 业务日志 | 关键业务动作与决策 | 业务复盘、对账、审计 |
| 应用日志 | 请求处理、状态变化、异常 | 故障定位 |
| 系统日志 | 进程、内核、资源事件 | 环境层问题 |

三者用途不同，不应混在同一份日志里。

## 结构化是前提

日志必须是**结构化**的（通常是键值对或 JSON），而不是自然语言句子。原因很简单：只有结构化日志才能被可靠地检索、聚合与告警。

```
差：处理订单失败，订单号 12345
好：{"event":"order_process_failed","order_id":"12345","reason":"payment_timeout","trace_id":"abc"}
```

结构化日志让「按订单号查全部相关日志」「统计某原因的错误量」从人工搜索变成一次查询。

## 必须携带的上下文

| 字段 | 作用 |
| --- | --- |
| 追踪标识 | 串起跨服务链路，这是最有价值的字段 |
| 时间戳（含时区） | 与指标、变更事件对齐 |
| 服务与实例 | 定位是单实例问题还是全局问题 |
| 业务标识 | 订单号、用户号等，便于按业务维度追溯 |
| 级别 | 用于过滤与告警 |
| 环境 | 区分生产与测试 |

**追踪标识的缺失是跨服务排查最大的障碍**。它应当在请求入口生成并透传到所有下游调用与日志中。

## 日志级别

| 级别 | 用途 |
| --- | --- |
| ERROR | 需要人工介入的失败 |
| WARN | 可自动恢复但值得关注的异常 |
| INFO | 关键状态变化与业务动作 |
| DEBUG | 排查用细节，生产默认关闭 |

**常见反模式**：把可预期的业务失败（如参数校验不通过）记为 ERROR。这会污染错误率指标，并让真正的错误淹没在噪音里。

## 隐私与安全

日志是数据泄露的高发渠道，因为它通常被广泛可读、长期保存、跨系统传输。硬性要求：

- 禁止记录口令、令牌、密钥、证件号、银行卡号；
- 个人敏感信息必须脱敏；
- 日志平台的访问权限按敏感级别控制；
- 日志保留期限与[数据保留策略](../../requirement/analysis/nonfunctional/privacy.md)一致。

## 成本治理

日志成本随规模迅速增长，且往往是可观测性支出中最大的一块：

- 高基数字段（如完整 URL、用户输入）会造成存储与索引爆炸；
- 无节制的 DEBUG 日志在生产被误开启时会放大数倍；
- 保留期过长会持续产生费用。

做法是**分级保留**：近期全量便于排查，长期只保留聚合与关键事件。

## 实践建议

- 从第一天就使用结构化日志并携带追踪标识，事后补代价极高。
- 建立统一的字段命名规范，让跨服务的日志可以联合查询。
- 日志写入不能阻塞主流程，必须有缓冲与丢弃策略——日志拖垮服务是真实发生过的故障。
- 明确日志的保留期与抽样策略，把成本纳入容量规划。
- 定期用「模拟排查」验证日志是否够用：给定一个故障场景，能否仅凭日志定位。
