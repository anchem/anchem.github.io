# 故障处置

故障处置的目标是**在最短时间内恢复服务**，而不是找到根因。两者是不同阶段的任务，混在一起会同时拖慢双方。

## 处置流程

```
发现 → 响应 → 止血（恢复服务） → 定位根因 → 修复 → 复盘 → 改进
```

### 关键纪律：先止血，后定位

生产故障中，**恢复优先于理解**。常见做法：

| 手段 | 说明 |
| --- | --- |
| 回滚 | 最快最可靠的手段，前提是提前验证过 |
| 扩容 | 应对容量与饱和问题 |
| 降级 | 关闭非核心功能保住核心链路 |
| 隔离 | 摘除异常实例或依赖 |
| 限流 | 保护系统不被打垮 |

**回滚是首选**：绝大多数故障与最近的变更有直接关系。在不确定原因时，回滚到已知良好状态往往比继续排查更有效。

## 角色与协作

| 角色 | 职责 |
| --- | --- |
| 处置负责人 | 决策、协调、对外沟通 |
| 操作执行 | 执行恢复动作 |
| 沟通 | 同步进展、维护状态更新 |
| 记录 | 保留时间线与证据 |

小团队中一人可兼多角，但**必须明确谁是决策者**。无明确决策者时，故障处置会退化为多人并行尝试、互相覆盖对方的改动，反而延长恢复时间。

## 沟通的原则

- 固定节奏更新状态，即使没有进展也要更新（「仍在排查」也是有价值的信息）；
- 区分「已确认的事实」与「推测」，避免把猜测当作结论传播；
- 对外沟通与内部技术讨论分开，避免混淆。

## 复盘

复盘的目标是**改进系统**，不是追究责任。判断一条复盘是否有效，看它是否产出了可验证的改进项。

有效的复盘包含：

| 内容 | 说明 |
| --- | --- |
| 时间线 | 从第一个异常信号到恢复的完整过程 |
| 影响 | 影响的用户、时间、业务损失 |
| 根因 | 技术根因与流程根因通常都存在 |
| 触发因素 | 什么变更或条件引发了它 |
| 侥幸项 | 哪些环节本可能更糟但没有 |
| 改进项 | 有归属、有期限、可验证 |

**「侥幸项」是最有价值的部分**：如果某次故障只差一点就更严重，说明存在尚未被处理的隐患。

## 从故障中提炼的三类改进

1. **可观测性**：这次是否及时发现？告警是否准确？
2. **可恢复性**：恢复手段是否有效？回滚是否顺利？
3. **可避免性**：如果设计时改变了什么，这次故障是否不会发生？

第三条会回到[架构](../../develop/development/architecture/index.md)与[需求](../../requirement/analysis/nonfunctional/index.md)层面——这正是运营反馈流向输入端的主要通道。

## 实践建议

- 所有恢复手段必须**提前演练过**。未演练的预案在真实故障中大概率不可用。
- 维护运行手册，覆盖常见故障的处置步骤，让值班者不必依赖记忆。
- 记录完整的处置时间线，这是复盘与改进的唯一依据。
- 把每次故障转化为至少一项自动化防护（测试、检查、告警）。
- 明确「什么时候可以停止排查」——恢复服务后，根因分析可以在脱离紧急状态后进行。
- 复盘对事不对人。追究个人责任的复盘会摧毁上报意愿，让下一次故障被隐藏更久。
