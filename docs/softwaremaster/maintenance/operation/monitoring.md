# 监控与告警

监控回答「系统现在是否正常」；告警回答「不正常时该叫醒谁」。两者的失效方式完全不同：监控失效是看不见问题，告警失效是被噪音淹没。

## 监控的三个层次

| 层次 | 关注 | 例子 |
| --- | --- | --- |
| 用户视角 | 用户是否得到服务 | 请求成功率、端到端延迟、转化率 |
| 服务视角 | 服务是否健康 | 接口错误率、队列深度、依赖延迟 |
| 资源视角 | 底层是否吃紧 | CPU、内存、磁盘、连接数、带宽 |

**必须从用户视角开始**。资源指标全绿但用户请求全部失败的情况非常常见——例如配置错误、依赖不可用、证书过期，这些都不会体现在 CPU 与内存上。

## 需要采集的四类信号

| 信号 | 用途 |
| --- | --- |
| 指标 | 趋势与容量判断 |
| 日志 | 细节与事后回溯 |
| 追踪 | 跨服务链路定位 |
| 事件 | 变更、发布、扩缩容的上下文 |

**事件信号最容易被遗漏**，但它常常是解释指标突变的关键——同一条延迟曲线，在「刚发布」和「流量自然的峰值」两个语境下的含义完全不同。

## 指标选择的原则

- **用分位数而非平均值**：平均值会掩盖长尾，而长尾影响大量用户。
- **服务级别指标优先**：从用户体验出发定义指标，而不是从实现出发。
- **成对监控**：延迟配错误率、吞吐配资源消耗。单指标优化极易损害另一方面。
- **关注趋势而非瞬时值**：慢速劣化（内存缓慢增长、磁盘逐渐填满）只能从趋势中发现。

## 告警设计的纪律

| 原则 | 说明 |
| --- | --- |
| 可行动 | 每条告警都有明确的处置动作 |
| 面向症状 | 基于用户体验告警，而非基于内部实现细节 |
| 有优先级 | 区分「立即处理」与「工作时间处理」 |
| 有归属 | 明确谁负责，无归属的告警会被忽略 |
| 去噪 | 抑制级联告警：依赖故障时上游应聚合而非逐个告警 |
| 有阈值依据 | 阈值应当来自 SLO 或容量分析，而非拍脑袋 |

**告警门槛的常见错误是过敏感**：为了「不漏掉问题」而设置低阈值，结果是团队对告警脱敏。宁可先少后补——漏报可以修复，误报造成的信任损失很难恢复。

## 三个必须监控的东西

1. **错误预算消耗速度**：比瞬时错误率更能反映问题的紧迫程度。
2. **关键依赖的健康度**：外部依赖故障是内部系统不可用的常见原因。
3. **变更后的一段时间窗口**：发布期间的指标对比是发现问题的最高效手段。

## 实践建议

- 每个服务上线前必须定义：SLO、关键指标、告警规则与值班归属。
- 建立从告警到处置手册的链接，让值班者不必依赖记忆。
- 定期审查告警质量：哪些从未触发、哪些触发后无人处理、哪些总是误报。
- 把变更事件与监控图表关联展示，定位效率会显著提升。
- 混沌工程式的主动演练，用于验证监控能否真的发现故障——未被验证的监控体系只有在真出事时才知道是否有效。
