# 盈利能力

盈利能力是商业价值最硬的证据：**收入减去全部成本**之后还剩多少。软件项目尤其容易在这一步翻车，因为成本结构不直观。

## 成本构成

| 类别 | 内容 | 特点 |
| --- | --- | --- |
| 研发成本 | 人力、工具、设备 | 一次性为主，但会随维护无限延长 |
| 运营成本 | 服务器、带宽、第三方服务 | 随用户量线性增长 |
| 维护成本 | 修缺陷、适配环境、偿还技术债 | **最常被严重低估** |
| 获客成本 | 市场、销售、渠道 | 决定规模化的可行性 |

维护成本的量级需要特别警惕：大型软件的维护成本可以达到开发成本的四倍左右。一个「便宜做完」的系统，如果可读性与可测试性差，会在后续若干年里持续吞噬利润。这也是[需求](../../requirement/index.md)阶段就要约束非功能性需求的原因。

## 盈利的三个杠杆

1. **提价**：靠差异化与转换成本，而非功能堆砌。
2. **降本**：靠架构与自动化。自动化测试、持续集成、可观测性建设的回报，最终都体现在运维人力上。
3. **提效**：缩短从想法到上线的周期。周期越短，试错次数越多，单位投入换回的信息量越大。

## 常见的伪盈利

- **补贴换增长**：收入依赖持续补贴，补贴停止即流失，本质是租来的利润。
- **砍研发保利润**：短期利润改善，长期维护成本上升，是典型的透支。
- **只看单价不看总成本**：选了便宜的方案，却把复杂度转嫁给人力。

## 实践建议

- 把技术债显式记入账：一个模块的重构需求应当能对应到可估算的维护成本。
- 评估技术方案时，把「未来三年的维护人力」纳入成本对比，而不只比一次性的开发工时。
