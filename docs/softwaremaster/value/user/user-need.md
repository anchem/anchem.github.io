# 用户需求洞察

用户很少能准确表达自己的需求。他给出的往往是**已经想好的解决方案**，而不是问题本身。洞察的任务就是把解决方案还原成问题。

## 经典案例

「用户想要更快的马」是方案，「用户想更快地到达目的地」才是问题。抓着方案走，你会得到一匹更快的马；抓住问题，才可能得到汽车。

## 还原问题的提问方式

| 用户说的 | 追问方向 |
| --- | --- |
| 「你们没有 XX 功能」 | 你上次想做这件事是什么场景？当时怎么绕过去的？ |
| 「这个太慢了」 | 慢到什么程度开始影响你？那时你正在做什么？ |
| 「我随便看看」 | 你现在最常用的是哪个替代方案？为什么不是我们？ |

关键是把话题从**功能**拉回到**场景**，从**评价**拉回到**行为**。行为比评价可靠得多。

## 三类证据的可靠性

1. **已经付过代价的行为**（最可靠）：付费、迁移数据、专门花时间写脚本绕过。
2. **正在使用替代方案的行为**：用 Excel、用竞品、用人工流程。
3. **口头表达的需求**（最不可靠）：容易受提问方式引导，且本人不承担成本。

## 实践建议

- 访谈中记录「原话」而不是「结论」，原话里的细节才是线索。
- 同一个问题至少收集三方视角（直接使用者、管理者、运维者），三者的诉求经常冲突，冲突本身就是设计输入。
- 警惕「我自己就是用户」：熟悉业务的人往往已内化了大量隐性知识，无法代表新手。
