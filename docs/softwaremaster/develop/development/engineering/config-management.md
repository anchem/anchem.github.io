# 配置管理

配置管理保证**同一份构建产物可以在不同环境中以不同参数运行**，同时保证敏感信息不泄露。

## 核心原则：构建一次，到处部署

不同环境不应当重新构建，只应当注入不同的配置。原因：

- 重新构建会引入不可控差异，破坏「测试过的就是发布的」这一前提；
- 环境差异导致的故障最难排查。

**构建产物必须与环境无关**，环境差异全部通过外部配置表达。

## 配置分层

| 层次 | 内容 | 变更频率 |
| --- | --- | --- |
| 构建期常量 | 与代码一起编译，几乎不变 | 极低 |
| 环境配置 | 地址、端口、容量、连接数 | 低 |
| 运行时开关 | 功能开关、限流阈值、降级策略 | 高 |
| 密钥 | 凭据、令牌、证书 | 中 |

分层的目的在于**区分变更的审批与传播路径**：运行时开关需要能快速生效而不重启，密钥需要严格管控而不落盘。

## 密钥管理

**密钥绝不能出现在代码库或镜像中**——它们会被历史记录、日志、镜像层带走。正确做法：

- 集中存储于密钥管理服务或配置中心；
- 运行时按需注入，权限最小化；
- 支持轮换，且轮换过程不需要改代码；
- 访问留痕，可审计。

同时要保证密钥不进入日志与错误堆栈——这是最常见的泄露路径。

## 配置变更的风险

配置变更常常比代码变更更危险，因为它**缺少同等的测试与评审**，却能瞬间影响全部实例。

应做到：

- 配置变更有记录、有评审、可回滚；
- 支持灰度生效，而不是全局同时切换；
- 启动时校验配置合法性，错误配置应当**快速失败**而不是带着默认值跑起来；
- 监控配置项与运行行为的关联，能回答「这次变更改了哪个配置」。

## 实践建议

- 环境之间配置差异越小越好。差异本身就是缺陷的温床。
- 为配置项设置明确的默认值与校验规则，避免「配置项少写一个导致启动用错值」。
- 配置模板纳入[版本管理](./version-control.md)，实际取值不纳入。
- 定期清理废弃配置项，未使用的配置是理解系统时的噪音。
