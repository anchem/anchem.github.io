# 版本管理

版本管理是所有协作的基础设施：它记录**谁在什么时候因为什么改了什么**。它不只是工具，还是团队协作方式的直接体现。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| 提交 | 一次原子变更，附带说明 |
| 分支 | 独立的开发线 |
| 合并 | 把一条线的变更引入另一条 |
| 变基 | 把提交重放到新的基点上，获得线性历史 |
| 标签 | 对某个提交的稳定引用，通常对应发布 |

## 分支策略

| 策略 | 特点 | 适用 |
| --- | --- | --- |
| 主干开发 | 所有人提交到主干，靠特性开关隔离 | 持续交付能力成熟 |
| 特性分支 | 每个功能一条分支，合入前评审 | 通用，团队规模中等 |
| Git Flow | 多条长期分支，区分开发与发布 | 版本化交付、多版本并行维护 |

**长期分支是成本的来源**：分支存活越久，与主干的差异越大，合并冲突与集成风险越高。缩短分支寿命是最有效的实践之一。

## 提交信息的价值

提交信息是唯一随代码一起演进、且不会过期的文档。一条合格的提交信息回答**为什么**，而不是重复**做了什么**（做了什么可以从 diff 看出）。

```
修复订单金额在并发确认下的重复扣减

原因：确认操作缺少幂等校验，重试时重复执行。
方案：新增基于订单号的唯一约束，并在服务层返回已有结果。
影响：需对存量重复数据进行一次清理，见脚本 xxx。
```

## 需要纳入版本管理的东西

- 源码、构建脚本、配置模板、数据库迁移脚本；
- 基础设施定义（基础设施即代码）；
- 文档（与代码同仓或同流程，保证同步演进）。

**不应纳入的**：密钥、凭据、大体积二进制产物。

## 实践建议

- 提交保持小而完整：一个提交解决一件事，便于回溯与回滚。
- 让提交信息能被检索：关联需求编号或问题编号，形成[需求追踪](../../../requirement/management/traceability.md)的一环。
- 用钩子自动化检查格式与提交信息规范，不要依赖人工纪律。
- 分支合并前必须同步主干，避免长期偏离。
- 禁止对已发布的历史做变基改写，那会破坏其他人的本地仓库。
