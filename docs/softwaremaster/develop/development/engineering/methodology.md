# 开发方法论

方法论是**组织工作的框架**。它的价值不在于被完整执行，而在于提供一套共同语言，让团队能讨论和调整自己的过程。

## 主要方法论

| 方法论 | 核心做法 | 适用场景 |
| --- | --- | --- |
|  Scrum | 固定迭代、角色分工、定期回顾 | 需求不确定、需要快速调整 |
| 看板 | 可视化流动、限制在制品、优化周期 | 运维、持续任务、需求零散 |
| 极限编程 | 结对编程、测试驱动、持续集成 | 质量要求极高的核心模块 |
| 精益 | 识别并消除浪费 | 瓶颈在流程而非技术 |
| 规模化框架 | 多团队对齐与依赖管理 | 大型组织协调 |

## 三个最有效的具体实践

从所有方法论中提炼，真正持续有效的做法并不多：

1. **限制在制品（WIP）**：同时在办的事情越多，单件的完成时间越长。这是排队论的直接结论，也是改善交付速度最有效的手段。
2. **缩短反馈周期**：包括代码评审时长、流水线时长、发布频率。反馈越慢，返工代价越大。
3. **定期回顾并真正改变一件事**：回顾的价值在于产生行动，而不是产生会议纪要。

## 编码规范与评审

这是方法论中最容易形式化的部分，也最容易形式化失效：

- **规范**应当是自动化的：能被工具检查的规则不要靠人工记。格式问题用格式化工具一次性解决，把评审精力留给设计问题。
- **评审**的目标是发现缺陷与传播知识，而不是证明评审者更聪明。小批量、快速评审的效果远优于积压后集中评审。

## 需要警惕的形态化陷阱

| 现象 | 问题 |
| --- | --- |
| 每日站会变成汇报会 | 失去了协调与暴露障碍的作用 |
| 估算变成承诺 | 估算被当作考核依据后必然失真 |
| 回顾没有后续 | 团队会停止提出问题 |
| 度量变成目标 | 见[古德哈特定律](../../../value/measurement/metrics.md) |

## 实践建议

- 先解决最大的瓶颈，而不是全面引入方法论。局部改善通常会被整体瓶颈吞掉。
- 任何流程都要能回答「它缩短了哪个反馈周期」。答不上来的流程应当被简化。
- 让流程的调整权留在执行者手上，这比任何方法论都更能维持流程的有效性。
