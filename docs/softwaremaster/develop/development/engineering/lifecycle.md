# 开发生命周期

生命周期描述软件从构思到退役的完整过程。**没有一种模型是通用的**，选择取决于需求变化的频率与交付风险。

## 常见模型

| 模型 | 特点 | 适用 |
| --- | --- | --- |
| 瀑布 | 阶段严格串行，文档驱动 | 需求稳定、合规要求强 |
| 迭代 / 增量 | 多轮小交付，逐步完善 | 需求不完全明确 |
| 敏捷 | 短周期、持续反馈、拥抱变化 | 需求快速演变 |
| 精益 | 消除浪费，拉式生产 | 瓶颈在流程而非技术 |
| DevOps | 开发与运维一体化，持续交付 | 需要高频发布 |
| 持续交付 | 随时可发布，发布是业务决策 | 自动化能力成熟 |

## 关键区分：迭代 vs 增量

- **增量**：分批交付功能，每一批都是可用的。
- **迭代**：反复精化同一部分，逐步逼近目标。

实践中二者常结合使用。理解这个区别的价值在于：明确当前是「还没做」还是「做得不够好」，对应的动作完全不同。

## 常见的三种失败形态

| 形态 | 表现 | 根因 |
| --- | --- | --- |
| 大爆炸式交付 | 长时间无产出，最后集中上线 | 反馈周期过长 |
| 永不稳定期 | 一直在做，始终不具备发布条件 | 缺少完成定义 |
| 交付即结束 | 上线后无人负责 | 生命周期缺少运维与退场阶段 |

## 「完成」必须有定义

一个任务是「完成」还是「接近完成」，是项目中最常见也最昂贵的模糊地带。**完成的定义应当是可检验的**，通常包含：代码已合入、测试已通过、已部署到目标环境、可观测性已接入、文档已更新。

## 实践建议

- 把发布与部署解耦：部署是技术动作，发布是业务决策。掌握这个能力后，交付节奏会显著改善。
- 让每个阶段都有明确的、可检验的产出，避免「差不多完成了」。
- 为退场设计流程：功能下线、数据处置、依赖清理都应当有明确动作。
