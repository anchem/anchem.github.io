文档

文档的目的是降低理解成本。判断一份文档是否有价值，只需问一句：它让谁少花了多少时间。

值得写的文档​

不是所有信息都值得成文。高价值文档集中在几类：

类型内容特点
架构决策记录为什么选了 A 而不是 B长期价值最高，防止重复讨论
接口契约输入、输出、错误、兼容承诺可被机器校验，演进最慢
上手指南环境搭建、第一件事怎么做直接决定新人效率
运行手册常见故障的处置步骤事故时唯一有用的文档
领域术语表业务词汇的准确定义成本极低、收益极高

架构决策记录（ADR）值得特别强调：它记录的是「当时的约束与权衡」，这类信息无法从代码中恢复。系统中最难回答的问题往往是「为什么当初要这样做」。

不值得写的文档​

  • 与代码重复的说明（注释、字段解释）——必然会过期；
  • 描述「怎么做」但依赖具体工具版本的步骤；
  • 没有指定读者的泛化设计文档。

让文档不腐化的三个手段​

  1. 就近维护：文档与它描述的对象放在一起（同仓库、同目录），改动时更容易同步。
  2. 可执行优先：能用脚本、测试、示例代码表达的，就不要用自然语言。可执行的文档不会过期。
  3. 明确负责人与复审周期：无人负责的文档默认已经过期。

注释的边界​

代码注释应当解释为什么，而不是做什么：

// 差：把计数器加一
count++;

// 好：此处必须先自增再校验，顺序颠倒会导致并发下重复计费
count++;
validate(count);

过多的注释本身是一种代码坏味道——它通常说明代码无法自解释。

实践建议​

  • 写文档前先明确读者与用途。读者不明的文档会被所有人略过。
  • 优先写「决策记录」与「运行手册」，这两类文档的缺失代价最高。
  • 把文档评审纳入变更流程，与代码一起合并。
  • 允许删除过期文档。过期的文档比没有文档更糟——它会误导人。
