# 系统分析与设计

系统分析与设计是**从问题域走向解空间**的过程：先弄清系统要做什么，再决定它由什么构成。

## 分析阶段：理解问题

产出是**问题域的结构**，而不是技术方案。

| 动作 | 目的 |
| --- | --- |
| 识别核心业务用例 | 确定系统必须支撑的行为 |
| 建立领域概念 | 统一语言，界定关键对象 |
| 明确边界 | 什么在系统内、什么依赖外部 |
| 识别约束 | 容量、合规、既有系统、时间与预算 |

关键纪律：分析阶段**不要提前决定技术方案**。一旦开始讨论框架与中间件，分析就变成了设计，而问题域的理解会被技术偏好污染。

## 设计阶段：构造解空间

### 从质量属性出发划分结构

结构划分的依据不应是「技术分层」的惯性，而应是**质量属性**：

- 需要独立扩缩的部分 → 划成独立部署单元；
- 需要独立演化的部分 → 划成独立模块；
- 变化频率差异大的部分 → 分离；
- 强一致要求的部分 → 聚在一起。

### 关键输出

| 输出 | 内容 |
| --- | --- |
| 上下文视图 | 系统与外部系统的边界与交互 |
| 容器 / 组件视图 | 主要可部署单元与职责 |
| 数据视图 | 核心数据实体、归属与流转 |
| 关键场景 | 用端到端场景验证结构是否成立 |
| 决策记录 | 关键取舍及其理由 |

其中**关键场景**是最有效的验证手段：挑出若干最重要、最苛刻的业务流，让它们穿过设计好的结构。场景走不通的地方，就是结构的问题所在。

## 常见错误

- **按技术分层切分**：所有业务逻辑集中在一个「服务层」，导致任何业务改动都要动同一处代码。
- **过早引入分布式**：在没有明确的扩缩或团队边界需求时拆分服务，等于凭空引入网络与一致性问题。
- **忽略数据归属**：模块划分清晰但共享同一套表，边界在数据层被彻底破坏。
- **无场景验证**：结构看起来很合理，但没有任何端到端场景被真正推演过。

## 实践建议

- 先画出「谁调用谁、数据存在哪里」，再讨论技术选型。
- 用[质量属性场景](./quality-attributes.md)把模糊的非功能性需求变成可验证的设计目标。
- 对每个划分决策问一句：**如果这部分要独立变化，代价是多少？**
