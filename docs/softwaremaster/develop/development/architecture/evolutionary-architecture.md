# 演进式架构

演进式架构的核心主张是：**不要试图一次设计到位，而是把「支持变化」这件事本身设计进去**。

## 为什么不能一次设计到位

- 需求会变，且变化方向无法预测；
- 规模会变，量级差异会推翻原有假设；
- 团队会变，组织结构的变化会反映到系统结构中。

因此架构的目标不是「画出一张最终的图」，而是**让这张图可以被持续修改**。

## 三个支撑要素

| 要素 | 含义 |
| --- | --- |
| 增量变更 | 用一系列小步替换大重写，每一步系统都可用 |
| 适应度函数 | 把架构约束写成可自动化的检查 |
| 恰当的耦合 | 按变化维度组织边界，让变化被限制在局部 |

### 适应度函数

这是演进式架构最具操作性的概念：**把架构约束变成自动化测试**。

| 约束 | 可自动化的检查 |
| --- | --- |
| 模块间不得循环依赖 | 依赖分析工具 |
| 领域层不得依赖基础设施 | 包依赖规则检查 |
| 接口响应时间上限 | 性能基准测试 |
| 对外接口保持向后兼容 | 契约兼容性检查 |
| 单模块复杂度上限 | 静态分析阈值 |

约束一旦自动化，架构侵蚀就会被及时拦住——**架构退化通常不是因为某个大错误，而是因为没有检测机制而持续累积的小偏离**。

## 可逆与不可逆决策

| 类型 | 例子 | 策略 |
| --- | --- | --- |
| 可逆 | 内部实现、框架选择、模块划分 | 快速试错，不必过度论证 |
| 难逆 | 数据模型、对外协议、多租户模型 | 充分评估，明确演进路径 |

**把决策成本与决策速度匹配起来**，是演进式架构的实操要点。对可逆决策反复论证，与对不可逆决策草率决定，是同一类错误。

在难逆决策上，应当额外设计**演进路径**：数据如何迁移、协议如何兼容、新旧如何并存。

## 与其他内容的关系

- 演进能力本身是[可演进性](../../../requirement/analysis/nonfunctional/evolvability.md)需求在架构上的兑现；
- 增量变更依赖[持续交付](../engineering/ci-cd.md)与[自动化验证](../verification/index.md)的支撑。

## 实践建议

- 为每条架构约束找一个可自动执行的检查，纳入流水线。
- 把大重写拆成可交付的增量，反对「停下来重写」——重写期间业务不会停。
- 定期评估边界是否仍然合理：业务变化后，旧的边界常常已经成为阻碍。
- 记录每次决策的约束背景，否则未来的人会以为它是理所当然的。
