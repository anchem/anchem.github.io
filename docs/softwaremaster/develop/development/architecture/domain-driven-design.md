# 领域驱动设计

领域驱动设计（DDD）主张**用业务领域的结构决定软件的结构**。它的核心价值不是模式集合，而是建立业务与技术共用的**统一语言**。

## 两个空间

| 空间 | 内容 | 关注点 |
| --- | --- | --- |
| 问题空间 | 业务领域、子域、核心域 | 业务价值在哪里 |
| 解空间 | 限界上下文、模块、聚合 | 如何组织实现 |

**核心域是应当投入最强资源的地方**，其他子域（通用域、支撑域）应当尽量使用成熟方案或采购。把精力平均分配是常见错误。

## 限界上下文

限界上下文是 DDD 最重要的概念：**同一个词在不同上下文中可以有不同的含义**。

例如「商品」在销售上下文里包含价格与促销，在仓储上下文里包含体积与重量，在售后上下文里包含保修条款。试图建一个统一的「商品」实体，会让三个上下文的规则互相污染。

限界上下文的价值在于：**它是边界，也是自治单元**。它决定：

- 哪部分可以独立演化；
- 哪部分可以独立部署；
- 哪部分可以独立拥有数据。

这与微服务的边界划分直接相关——**好的服务边界通常就是限界上下文**。

## 战术模式

| 模式 | 用途 |
| --- | --- |
| 实体 | 有身份标识、生命周期内身份不变 |
| 值对象 | 由属性定义、不可变 |
| 聚合 | 一致性边界，通过聚合根访问 |
| 领域服务 | 不属于单个对象的重要规则 |
| 领域事件 | 表达已发生的事实，用于解耦与协作 |
| 仓储 | 屏蔽持久化细节 |

## 主要的实用价值

1. **划分边界**：提供了一套从业务出发划分模块的依据，优于按技术分层。
2. **统一语言**：减少业务与技术之间的翻译损耗。
3. **保护业务规则**：把规则集中表达，而不是散落在各层的服务方法里。

## 适用的边界

DDD 的收益与**业务复杂度**正相关。在业务规则简单的系统（如以增删改查为主的管理后台）中引入完整 DDD，会带来大量抽象却没有相应收益。

判断标准：**业务规则是否复杂到需要被显式建模**。若规则简单，简单的分层结构更合适。

## 实践建议

- 从建立术语表开始，而不是从画聚合开始。
- 先划分限界上下文，再考虑服务拆分；顺序颠倒会得到「分布式单体」。
- 聚合设计以「一致性边界」为准，而不是以「数据关系」为准。聚合过大是并发冲突的根源。
- 领域模型不应暴露给外部，对外用[接口契约](../design/api-design.md)隔离。
