# 质量属性

质量属性是**架构设计的输入与验收标准**。没有明确的质量属性，架构讨论就只能停留在「看起来是否优雅」这种无法判定的层面。

## 从需求到设计目标

[非功能性需求](../../../requirement/analysis/nonfunctional/index.md)是业务语言，需要翻译成架构语言：

| 需求表述 | 架构目标 |
| --- | --- |
| 系统要快 | 定义延迟分位目标、热点路径、缓存策略 |
| 系统要高可用 | 明确冗余级别、故障域、恢复时间目标 |
| 系统要能扩展 | 确定扩缩维度（无状态化、分片键） |
| 系统要好维护 | 定义模块边界、依赖规则、测试覆盖 |

## 质量属性场景

把模糊目标变成可验证设计的有效手段是**六要素场景描述**：

```
来源 → 刺激 → 环境 → 制品 → 响应 → 响应度量
```

例子：

> 促销活动期间（环境），大量用户（来源）同时提交订单（刺激），订单服务（制品）应当在 1 秒内返回结果（响应），且错误率低于 0.1%（响应度量）。

完整的场景描述可以直接转化为测试用例与监控指标，**这是质量属性最实用的落地形式**。

## 质量属性的相互制约

| 组合 | 冲突点 |
| --- | --- |
| 性能 vs 可维护性 | 特化优化降低可读性 |
| 安全 vs 易用性 | 校验与验证步骤增加摩擦 |
| 可用性 vs 一致性 | 分区时的经典取舍 |
| 可扩展 vs 简单性 | 分布式带来固有复杂度 |
| 灵活 vs 性能 | 抽象层有运行时开销 |

**必须显式排序**：当两个属性冲突时，哪个优先。排序不明确时，团队会在不同场景下做出一致性不一的决策，最终得到既不好用也不安全的系统。

## 架构决策记录

每条针对质量属性的决策都应记录下来：

```markdown
## 决策：订单服务采用读写分离

背景：读请求量为写的 20 倍，主库压力集中在查询上。
取舍：放弃强一致的读，接受主从延迟（约 50ms）。
代价：需处理「下单后立即查询不到」的体验问题。
重新评估条件：从库延迟超过 500ms，或写比例上升到 1:3 以上。
```

**「重新评估条件」是关键字段**——它把架构从一次性决策变成可管理的持续过程。

## 实践建议

- 为每个高优先级质量属性写出至少一个完整场景，并配套监控指标。
- 明确排序，并把排序结果写进架构文档，供后续所有决策引用。
- 定期用监控数据回看质量属性是否达标，而不是等故障来证明。
- 警惕「全都重要」：全部重要的质量属性等于没有优先级。
