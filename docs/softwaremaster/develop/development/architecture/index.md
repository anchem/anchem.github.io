# 软件架构

架构是**难以撤回的设计决策**。它决定了系统的骨架：由哪些部分组成、边界划在哪里、各部分如何交互。架构的目标不是「正确」，而是**在给定的质量属性约束下做出可接受的取舍**。

## 架构决策的本质

每一份架构决策都是**在质量属性之间的取舍**：

| 倾向一侧 | 代价 |
| --- | --- |
| 性能 | 复杂度、可维护性下降 |
| 可扩展 | 运维成本、一致性复杂度上升 |
| 简单 | 应对变化的能力受限 |
| 灵活 | 抽象成本、理解成本上升 |

**不存在全都占优的方案**。因此架构决策必须显式记录：当时的约束是什么、放弃了什么、什么条件下应当重新评估。这些信息无法从代码中恢复，参见[架构决策记录](../engineering/documentation.md)。

## 两条判断准则

1. **边界是否对应变化**：好的边界把「一起变化的东西」放在一起，把「独立变化的东西」分开。边界划错，改动必然扩散。
2. **耦合是否显式**：隐式耦合（共享数据库、全局状态、约定式协议）是最难治理的，因为它在代码里看不见。
