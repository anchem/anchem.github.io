# 软件设计

设计关注**模块内部的结构**：如何组织代码、如何划分职责、如何定义接口。它的目标是让代码在持续修改中保持可控。

## 设计的中心问题

设计的一切努力都在处理同一个问题：**耦合**。

| 耦合类型 | 表现 | 危害 |
| --- | --- | --- |
| 内容耦合 | 直接访问对方内部数据 | 改动必然互相影响 |
| 公共耦合 | 依赖全局状态 | 无法独立测试与推理 |
| 控制耦合 | 传标志位控制对方行为 | 职责边界模糊 |
| 数据耦合 | 只通过参数传递数据 | 最健康 |

好的设计**不是消除耦合，而是让耦合发生在稳定的位置**——依赖抽象、依赖契约，而不是依赖实现细节。

## 一个实用的判断方法

衡量设计好坏，有一个非常朴素的测试：**做一次典型的需求变更，需要改动多少个文件、几个模块？**

- 改动集中在少数文件 → 边界合理；
- 改动横穿多个模块 → 职责划分有问题；
- 改动需要修改公共代码 → 抽象层级有问题。

这比任何设计原则清单都更直接有效。
