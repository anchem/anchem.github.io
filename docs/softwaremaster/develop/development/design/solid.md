# 设计原则

设计原则是对「什么样的结构更容易修改」的经验总结。它们不是定律，而是**权衡的提示**。

## SOLID 五项

| 原则 | 含义 | 违反的信号 |
| --- | --- | --- |
| 单一职责 SRP | 一个模块只有一个变化理由 | 修改一处需求要动同一个类的多个方法 |
| 开闭原则 OCP | 对扩展开放，对修改关闭 | 每加一种类型就改一遍 if-else |
| 里氏替换 LSP | 子类型可替换父类型而不破坏行为 | 子类抛出父类没声明的异常、覆盖后行为不符 |
| 接口隔离 ISP | 不强迫依赖不需要的接口 | 实现类里大量空方法 |
| 依赖倒置 DIP | 依赖抽象而非实现 | 高层模块直接依赖具体框架或数据库类 |

### 最实用的两条

**单一职责**：它的操作化定义是「变化的理由数」。一个类如果要为不同的业务原因而修改，它就承担了多个职责。

**依赖倒置**：它让核心业务逻辑不依赖外部技术。做到这点后，数据库、消息队列、外部 API 都可以被替换，也让测试变得容易——这也是[可测试性](../../../requirement/analysis/nonfunctional/testability.md)的主要来源。

## 其他常用原则

| 原则 | 含义 |
| --- | --- |
| DRY | 避免重复知识（不是避免重复代码） |
| KISS | 保持简单 |
| YAGNI | 不要实现当前不需要的东西 |
| 迪米特法则 | 只与直接朋友通信，避免长长的调用链 |
| 组合优于继承 | 减少实现绑定 |
| 高内聚低耦合 | 结构与依赖的总目标 |

**DRY 常被误用**：它要消除的是「知识的重复」（同一条规则写在两处），而不是「代码的形似」。两段看起来相似但变化原因不同的代码，强行合并会制造出错误的耦合——这本身就会导致[发散式变化](../implementation/refactor/code-smell.md)。

## 原则的代价

每条原则都需要额外的抽象与间接层，而抽象有明确的成本：

- 增加理解成本（跳转层级变多）；
- 增加调试难度（调用链变长）；
- 可能损害性能（间接调用的开销）。

因此原则的适用取决于**变化是否真的会发生**。在稳定的、确定不会扩展的地方引入抽象，是纯粹的负债。

## 实践建议

- 用原则解释问题，而不是用原则评判代码。「这里违反了 SRP，因为……所以改动会扩散」比「这里违反 SRP」有说服力。
- 先让代码工作，再在设计压力出现时重构——参见[重构](../implementation/refactor/index.md)。
- 对不确定是否需要扩展的地方，选择更简单的写法，等第二个实际场景出现再抽取抽象。
