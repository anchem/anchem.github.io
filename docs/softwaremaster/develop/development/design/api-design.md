# API 设计

API 是系统的**对外契约**。它的生命周期远长于实现，一旦发布就难以修改——因此设计时应把「未来如何演进」作为首要约束。

## 契约的三个维度

| 维度 | 内容 |
| --- | --- |
| 功能 | 提供什么操作、语义是什么 |
| 数据 | 请求与响应的结构、必填与可选 |
| 质量 | 幂等性、超时、限流、错误语义 |

三者中**质量维度最常被省略**，却直接决定调用方能否正确使用。

## 设计原则

### 1. 语义优先于形态

命名与结构应当反映业务语义，而不是内部实现。API 一旦暴露实现细节（如表结构、内部枚举），实现就被冻结了。

### 2. 幂等性显式化

调用方一定会重试。必须让调用方能判断「重试是否安全」：

| 方法 | 幂等 |
| --- | --- |
| GET / PUT / DELETE | 是 |
| POST | 通常否，需显式设计去重机制 |

对非幂等操作，提供**去重标识**（如客户端生成的请求 ID），是保证重试安全的实用做法。

### 3. 只增不删的兼容策略

- 新增字段必须是可选的，且旧调用方可以忽略；
- 不得删除或重命名字段；
- 不得修改字段语义或单位；
- 枚举必须为未知值预留兜底分支；
- 废弃要有明确周期与通告机制。

详见[兼容性需求](../../../requirement/analysis/nonfunctional/compatibility.md)。

### 4. 错误是契约的一部分

错误响应应当包含：**稳定的错误码、面向调用方的说明、可否重试的提示、用于排查的追踪标识**。

把内部异常信息直接暴露给调用方，既无法帮助调用方处理，也构成信息泄露风险。

### 5. 分页、限流与容量要在契约中体现

调用方需要知道如何遍历大数据集、遇到限流该如何退避。缺少这些约定的 API 会被以压垮服务的方式使用。

## 版本策略

| 方式 | 特点 |
| --- | --- |
| URL 版本 | 直观、易路由，但会产生多个并行入口 |
| 请求头版本 | 保持 URL 干净，调试稍麻烦 |
| 无版本 + 严格兼容 | 最理想，需要极强的兼容纪律 |

多数系统的实际做法是：**优先保持兼容，只在无法兼容时才引入新版本，并给出明确的废弃时间表**。

## 实践建议

- 接口先在文档中定义并评审，再写实现。契约先行能显著减少返工。
- 为接口编写契约测试，并纳入流水线，让兼容性破坏在合并前被发现。
- 为每个接口明确超时、重试、限流语义，并在文档中写明。
- 对外接口与内部接口分开设计：内部接口可以更灵活，但同样需要边界。
- 把[质量属性](../architecture/quality-attributes.md)目标关联到接口，否则设计无验收标准。
