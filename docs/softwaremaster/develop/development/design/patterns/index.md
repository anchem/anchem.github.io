# 设计模式

设计模式是**针对重复出现的设计问题的命名方案**。它的首要价值不是提供代码模板，而是提供**共同词汇**——说「这里用策略模式」比描述三遍结构要快得多。

## 分类

| 类别 | 关注 | 包含 |
| --- | --- | --- |
| [创建型](./creational.md) | 对象的创建方式 | 工厂、单例、建造者、原型 |
| [结构型](./structural.md) | 对象与类的组合方式 | 适配器、装饰器、代理、组合、外观、享元、桥接 |
| [行为型](./behavioral.md) | 对象间的职责分配与通信 | 策略、观察者、模板方法、责任链、状态、命令、迭代器等 |

## 使用模式的三条纪律

1. **先有问题，再找模式**。反过来（先决定用某个模式再找用途）是过度设计的典型来源。
2. **模式是语言，不是目标**。代码中不需要出现模式的名字，只需要结构正确。
3. **语言特性会消除部分模式**。函数作为一等公民时，策略与命令常退化为函数参数；有泛型与闭包的语言中，若干模式会自然消失。

## 模式背后的问题

抛开具体形态，模式解决的问题集中在几类：

| 问题 | 对应模式族 |
| --- | --- |
| 创建逻辑复杂或需延迟决定类型 | 创建型 |
| 需要在运行期组合行为 | 结构型 |
| 需要在对象间分配职责、降低耦合 | 行为型 |

识别出问题类别，比记住所有模式更重要。

## 与设计原则的关系

模式通常是[设计原则](../solid.md)的具体应用结果。例如策略模式是实现开闭原则的常见手段，依赖倒置则是几乎所有模式背后的共同结构。因此**掌握原则比掌握模式更根本**。

## 一条提醒

模式是「常见问题的成熟解法」，不是「更高级的设计」。过度使用模式会得到大量间接层，理解成本显著上升而收益有限——这是设计中最常见的一种负债。
