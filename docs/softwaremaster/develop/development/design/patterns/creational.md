# 创建型模式

创建型模式处理**对象如何被创建**，目标是把「创建什么」与「怎么创建」解耦。

## 主要模式

| 模式 | 解决的问题 | 使用信号 |
| --- | --- | --- |
| 工厂方法 | 让子类决定实例化哪个类 | 分支决定类型，且会持续增加类型 |
| 抽象工厂 | 创建一系列相关对象 | 需要成套替换实现（如同一套 UI 组件） |
| 建造者 | 分步构造复杂对象 | 构造参数多且可选组合多 |
| 原型 | 通过复制创建新对象 | 创建成本高，且差异小 |
| 单例 | 保证全局唯一实例 | 有真实共享状态，需要注意并发与测试 |

## 使用要点

### 工厂的价值在类型会增长时

如果类型是固定的几种且不会增加，一个 switch 是最清晰的选择。工厂的价值出现在**新增类型时不需要修改调用方**——这正是开闭原则的体现。

### 建造者解决的是参数爆炸

当一个构造函数有七八个参数、其中多数可选时，调用方极易传错顺序。建造者用链式调用把「概念上的一组参数」显式化，可读性显著提升。

### 单例是最需要克制的模式

它的问题在于制造**全局可变状态**：

- 难以在测试中替换或隔离；
- 并发访问需要额外同步；
- 隐式依赖，使依赖关系在代码中不可见；
- 生命周期难以控制。

多数情况下，把对象交给**依赖注入容器**管理，效果等同于单例但保留可替换性，是更好的选择。

## 实践建议

- 优先使用语言与框架提供的创建机制（依赖注入、构造函数重载、可选参数），再考虑手写模式。
- 创建逻辑本身也是业务逻辑，应当有测试覆盖。
- 需要延迟创建且创建昂贵时，明确考虑线程安全与失败后的重试策略。
