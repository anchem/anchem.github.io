# 软件安全

安全与其他质量属性最大的区别是：**存在主动的、会持续尝试的对手**。因此安全不能被当作上线前的加固环节，而必须贯穿架构、设计与实现。

## 三条基本认识

### 1. 安全是设计问题，不是补丁问题

事后加固通常只能挡住已知的攻击方式。权限模型、信任边界、数据分级必须从设计阶段确定——这些是**架构级决策**，事后修改代价极大。

### 2. 所有输入都不可信

包括来自内网服务、数据库、配置、消息队列的输入。**信任边界之外的任何数据都需要校验**，而边界往往比直觉更靠内。

### 3. 默认拒绝

权限、端口、功能都应当默认关闭，按需开放。默认允许的系统，其安全强度取决于「是否有人记得关上」。

## 需求到实现的链条

```
安全需求（做得多安全） → 安全设计（边界与威胁模型） → 安全编码（具体防护） → 安全验证（测试与扫描）
```

这条链条的起点是[安全需求](../../../requirement/analysis/nonfunctional/security.md)。**没有明确的安全需求，后续环节都无从判断是否达标。**

## 常见的错误观念

| 观念 | 问题 |
| --- | --- |
| 内网是安全的 | 内网一旦被突破，横向移动几乎无阻 |
| 加密了就安全了 | 加密只解决信道问题，业务逻辑漏洞依然存在 |
| 我们没什么值得攻击的 | 攻击者要的是资源与跳板，而非目标本身的价值 |
| 安全是安全团队的事 | 安全团队无法审查每一行代码，实现者才是最后一道防线 |
| 隐藏实现即安全 | 实现细节会被观察，安全不能依赖保密 |
