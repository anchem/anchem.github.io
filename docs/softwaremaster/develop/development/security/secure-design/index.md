# 安全设计

安全设计在**动手写代码之前**识别并消解威胁。设计阶段消除一个威胁的成本，远低于上线后修补。

## 包含内容

- [威胁建模](./threat-modeling.md)：系统地找出威胁并决定如何应对

## 设计阶段要确定的事

| 事项 | 内容 |
| --- | --- |
| 资产 | 有什么值得保护：数据、算力、信誉、可用性 |
| 信任边界 | 哪些部分之间不允许相互信任 |
| 身份与授权模型 | 谁能做什么，规则定义在何处 |
| 数据分级 | 哪些数据敏感、需要何种保护等级 |
| 密钥与凭据 | 如何生成、存储、轮换 |
| 审计 | 哪些操作必须留痕，保留多久 |
| 失败行为 | 拒绝时给出什么响应，是否会泄露信息 |

其中**授权模型**最常被遗漏：很多系统在实现阶段由开发者各自即兴判断权限，导致规则不一致且存在缺口。

## 三条设计原则

### 最小权限

进程、服务、账户、数据库连接，都只应拥有完成当前职责所必需的权限。权限过大的问题在于它不产生即时故障，因此不会被发现，直到被利用。

### 默认拒绝

未明确允许的一律拒绝。默认允许的系统，其安全性取决于「是否有人记得关闭」，这是不可靠的假设。

### 纵深防御

假定任何一层都可能被突破，因此需要多层独立防护。单层防护的失效等同于完全失守。

## 边界划分的实际建议

**按数据的敏感级别划分边界，而不是按功能划分。** 同一边界内可以共享信任，跨边界必须显式校验与鉴权。

这带来一个实用推论：**不要把高敏感数据与低敏感功能放在同一个信任域内**。数据库、消息队列、内部接口都应当遵循这一原则。
