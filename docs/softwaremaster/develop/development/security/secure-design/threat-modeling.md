# 威胁建模

威胁建模是一个结构化的问题：**这个系统会被怎么攻击，我们如何应对**。

## 四个步骤

```
1. 建模系统  →  画数据流，标出信任边界
2. 找出威胁  →  沿边界逐项推演
3. 评估风险  →  影响 × 可能性
4. 决定对策  →  消除 / 缓解 / 接受 / 转移
```

### 1. 建模系统

画出数据流图，标出：外部实体、进程、数据存储、数据流方向，以及**信任边界**（数据从不可信区域进入可信区域的位置）。

信任边界是关键——**大部分漏洞出现在跨边界的输入处理上**。

### 2. 找出威胁

按边界与数据流逐项推演。常用提问框架：

| 维度 | 提问 |
| --- | --- |
| 身份 | 能否伪造？能否冒用他人身份？ |
| 数据 | 能否读取、篡改、删除不该动的数据？ |
| 授权 | 能否访问超出权限的资源？ |
| 流程 | 能否跳过必要的步骤？ |
| 资源 | 能否耗尽资源（算力、存储、带宽、配额）？ |
| 痕迹 | 攻击能否不被发现？日志是否可被篡改？ |
| 依赖 | 上游被攻破会怎样？供应链是否可信？ |

按**资产**而非按**功能**列威胁，覆盖更完整。

### 3. 评估风险

风险 = 影响 × 可能性。避免两个极端：

- 不做评估，对所有威胁同等对待，导致资源错配；
- 只评估技术可能性，忽略业务影响。

### 4. 决定对策

| 对策 | 含义 |
| --- | --- |
| 消除 | 去掉产生威胁的设计（最优） |
| 缓解 | 增加控制手段降低可能性或影响 |
| 转移 | 通过保险、外包、合规责任转移 |
| 接受 | 明确记录并承认残余风险 |

**「接受」必须被显式记录**，而不是被遗忘。记录时写明：风险是什么、为什么接受、谁批准的。

## 何时做

| 时机 | 原因 |
| --- | --- |
| 新系统设计阶段 | 成本最低，可消除而非修补 |
| 架构重大变更 | 引入新的边界与依赖 |
| 新增敏感数据处理 | 合规与泄露风险 |
| 集成新的外部系统 | 引入新的信任边界 |
| 发生安全事件后 | 检验模型是否遗漏 |

## 一条实用提醒

威胁建模**不需要专家或复杂工具**。几个人、一张白纸、一小时，围绕数据流与信任边界提问，就能发现大部分高风险问题。

形式化程度应当与系统重要性匹配——对内部小工具做完整威胁建模，投入产出比很低。

## 实践建议

- 让开发、运维、业务方共同参与。不同视角能发现不同类别的威胁。
- 输出应当是可执行的**行动项**（加校验、改权限、补审计），而不是文档。
- 把结论中的关键防护转化为自动化测试或配置检查。
- 定期重做：系统与威胁环境都在变化，一次性的模型会过期。
