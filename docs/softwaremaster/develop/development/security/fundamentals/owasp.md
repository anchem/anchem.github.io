# 常见漏洞类别

安全漏洞的成因高度集中。理解这几类**根因**，比记住漏洞清单更有价值。

## 主要类别与根因

| 类别 | 根因 | 典型形态 |
| --- | --- | --- |
| 注入类 | 数据被当作代码执行 | SQL 注入、命令注入、模板注入、日志注入 |
| 认证与会话缺陷 | 身份可被伪造或猜测 | 弱口令、会话固定、令牌不过期 |
| 访问控制缺失 | 权限校验缺失或可绕过 | 越权访问、水平越权、直接对象引用 |
| 敏感数据暴露 | 数据未加密或过度暴露 | 明文存储、日志泄漏、错误信息泄露 |
| 配置错误 | 默认配置不安全 | 开放调试接口、默认口令、权限过宽 |
| 依赖与组件缺陷 | 使用有漏洞的第三方组件 | 未更新、传递依赖引入风险 |
| 输入校验不足 | 信任了外部输入 | 反序列化、文件上传、路径穿越 |
| 业务逻辑缺陷 | 规则被绕过 | 价格篡改、重复领取、并发刷单 |

**注入类漏洞的根本解法只有一条：数据与代码分离**。参数化查询、安全的模板引擎、避免字符串拼接执行命令——这些做法的共同点是让数据永远不被解释为指令。

## 访问控制是最常见的缺失

身份认证（你是谁）与授权（你能做什么）是两件事，**大量系统只做了前者**。

实践中的高频问题：

- 只在前端隐藏了入口，后端接口没有校验；
- 校验了「是否登录」但未校验「是否有权访问这个资源」；
- 通过 ID 直接访问资源而未经归属校验（水平越权）。

防御原则是**在服务端对每个请求做显式授权检查**，并采用「默认拒绝」策略。

## 业务逻辑漏洞

这类漏洞无法靠通用扫描发现，因为它需要理解业务语义：

| 形态 | 例子 |
| --- | --- |
| 参数篡改 | 修改价格、数量、折扣 |
| 重复提交 | 重复领取优惠、重复下单 |
| 时序竞争 | 并发请求绕过余额检查 |
| 流程跳过 | 直接调用最后一步接口 |

应对手段主要是**服务端重新校验、幂等设计、并发控制**，参见[事务](../../../foundation/database/transaction.md)与[并发](../../../foundation/distributed/concurrency.md)。

## 防御的总体思路

1. **输入校验**：白名单优于黑名单；在边界处统一校验。
2. **输出编码**：按输出上下文正确转义，防止跨站脚本。
3. **最小权限**：进程权限、数据库权限、接口权限都按需授予。
4. **纵深防御**：假定任一层会被突破，多层重叠。
5. **默认安全**：安全配置作为默认值，而非需要额外开启的选项。
6. **及时更新**：依赖与运行时的漏洞需要持续跟踪与修复。

## 实践建议

- 把安全检查左移：静态分析、依赖扫描、密钥扫描纳入[流水线](../../implementation/build.md)。
- 在[威胁建模](./../secure-design/threat-modeling.md)中按业务场景列举滥用方式，而不是只对照漏洞清单。
- 对外错误响应不暴露内部细节，同时保留完整的服务端日志与追踪标识。
- 定期进行渗透测试，它发现的业务逻辑缺陷通常是自动化工具无法覆盖的部分。
