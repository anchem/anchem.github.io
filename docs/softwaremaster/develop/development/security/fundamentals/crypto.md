# 密码学应用基础

工程中使用密码学的目标不是「发明方案」，而是**正确地使用成熟原语**。

## 四类原语与各自职责

| 原语 | 性质 | 用途 |
| --- | --- | --- |
| 对称加密 | 可逆，加解密同密钥 | 加密数据（快，适合大数据量） |
| 非对称加密 | 可逆，公钥加密私钥解密 | 密钥交换、数字信封 |
| 哈希 | 单向、定长、抗碰撞 | 完整性校验、口令存储、指纹 |
| 消息认证码 / 签名 | 完整性 + 来源认证 | 防篡改、防伪造 |

**最常见的概念混淆**：

| 混淆 | 后果 |
| --- | --- |
| 加密 = 完整性保障 | 密文可被篡改而无法察觉 |
| 哈希 = 加密 | 哈希不可逆，不能用于数据保密 |
| 签名 = 加密 | 签名不提供机密性，只提供来源与完整性 |

## 使用要点

### 1. 永远不要自己实现算法

包括「自己组合标准算法」。密钥派生、填充、模式选择、随机数使用，每一处都是陷阱。使用经过审计的成熟库，并关注其是否仍在维护。

### 2. 模式选择

| 模式 | 说明 |
| --- | --- |
| ECB | **禁用**，相同明文块产生相同密文，泄露结构 |
| CBC | 需要随机 IV，且必须配合完整性校验 |
| 认证加密（GCM 等） | **推荐**，同时提供机密性与完整性 |

默认应选择**认证加密模式**，它避免了「忘记做完整性校验」这类高频错误。

### 3. 口令存储

口令**绝不能**用可逆加密或裸哈希存储。正确做法是使用**慢哈希**（专门的密码派生函数），并配合随机盐：

- 盐防止彩虹表与相同口令产生相同哈希；
- 慢哈希让离线爆破的成本显著上升；
- 迭代/成本参数应随硬件发展定期提高。

### 4. 随机数

安全相关的随机值（密钥、令牌、盐、IV）**必须使用密码学安全的随机源**。普通伪随机数生成器可被预测，是常被忽略的严重漏洞。

### 5. 密钥管理

密钥的**生命周期**比算法更重要：

| 环节 | 要求 |
| --- | --- |
| 生成 | 使用安全随机源 |
| 存储 | 密钥管理服务，不入代码、镜像、日志 |
| 分发 | 加密信道，最小范围 |
| 使用 | 最小权限，用完即弃 |
| 轮换 | 定期且有流程，不依赖代码改动 |
| 销毁 | 有明确流程与验证 |

密钥泄露的后果是**全部加密失效**。因此密钥管理常是整个方案中最薄弱的环节。

## 常见错误清单

- 使用 ECB 模式；
- 固定 IV 或使用可预测的 IV；
- 用哈希做完整性校验而不带密钥（无法防篡改）；
- 用时间戳或可预测值作为令牌；
- 错误信息泄漏内部细节（如「用户不存在」vs「密码错误」）；
- 加密方案自研，或组合方式偏离标准。

## 实践建议

- 使用成熟库的**高层 API**（如认证加密、密码派生的封装），而不是逐个原语自行组合。
- 密钥通过密钥管理服务注入，禁止写入代码、配置库与镜像。
- 传输与存储分别使用合适的方案：传输靠协议层，存储靠应用层加密。
- 保留 AES 之外的演进路径，为未来算法替换预留接口。
- 定期做依赖与算法强度审查，淘汰过时算法。
