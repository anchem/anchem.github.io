安全编码

安全编码把安全设计落实为具体的代码约束。它的核心是在正确的边界处理正确的输入。

通用措施​

措施说明
参数化数据与代码分离：查询、命令、模板都不拼接
输入校验白名单优先；在边界统一校验，不信任任何外部输入
输出编码按输出上下文（HTML、URL、JSON、SQL）转义
最小权限数据库账号、服务账号、文件权限按需授予
密钥外置通过密钥管理服务注入，不入代码与镜像
错误信息收敛对外不暴露内部细节，对内保留追踪标识
日志脱敏禁止记录口令、令牌、证件号、卡号
依赖治理持续扫描与更新，移除无用依赖
限流与配额所有对外接口设置边界
事务与幂等关键操作防重放、防并发绕过

最容易出错的几处​

1. 只在前端做校验​

前端校验改善体验，不构成安全措施。任何校验都必须在服务端重复执行。

2. 只校验「是否登录」​

登录态与资源权限是两回事。每次访问具体资源都必须校验归属与权限。

3. 反序列化不可信数据​

反序列化可能触发任意代码执行或对象构造。对外部输入应使用安全的格式与严格的类型约束。

4. 路径拼接​

未校验的文件名可能导致路径穿越，读写到预期之外的位置。应当校验规范化后的路径是否仍在允许目录内。

5. 日志与异常泄漏​

堆栈信息、SQL 语句、内部地址出现在对外响应中，为攻击者提供了地图。

6. 敏感信息进入日志平台​

日志通常被广泛可读、长期保存、跨系统传输，是数据泄露的高发渠道。

与并发相关的问题​

某些安全问题只在并发下出现：

  • 重放：同一请求被重复提交，用于重复领取或绕过限制；
  • 检查与使用之间的窗口（TOCTOU）：校验通过后状态被改变；
  • 竞态绕过：并发请求同时通过余额或配额检查。

对策是服务端重新校验 + 幂等设计 + 数据库约束，而不是依赖应用层的先检查后写入。

实践建议​

  • 把可自动化的检查纳入流水线：依赖漏洞扫描、密钥扫描、静态分析、配置基线。
  • 在代码审查中显式检查安全项：输入处理、权限校验、日志内容。
  • 为安全措施编写测试：越权访问应当被拒绝，非法输入应当被拦截——这类测试能防止安全控制被后续改动无意破坏。
  • 保持依赖更新并移除不用的依赖：未使用的依赖只带来风险，不带来价值。
  • 任何「临时」的安全绕过都必须有明确的移除计划与负责人。
