代码坏味道

坏味道是结构问题的信号，不是错误。它提示「这里可能值得调整」，但是否重构仍需结合成本与收益判断。

下面 22 种坏味道按名称、现象与处理方向排列，可以当作一份检查清单使用。

一、命名与重复​

1. 重复代码​

同一段逻辑或同一条知识出现在多处。这是最基础也最昂贵的坏味道——修改时必然遗漏一处。

方向：抽取函数、上移方法到共同父类、抽取公共模块。注意区分「代码形似」与「知识重复」：变化原因不同的形似代码不应合并。

2. 异曲同工的类​

两个类的职责相似，但方法名或签名不同，导致无法互换使用。

方向：统一命名与签名，抽取共同接口，或索性合并。

二、规模​

3. 过长函数​

函数长到无法一眼看完，内部混杂多个抽象层次。

方向：以「做什么」为单位抽取函数；用查询替代临时变量；分解条件表达式与循环。

4. 过大的类​

一个类承担了过多职责，字段被不同方法分组使用。

方向：按职责拆分为多个类；抽取类内聚的字段与被它们使用的方法。

5. 过长参数列​

参数过多，调用方容易传错位置，且参数间常有隐含的成组关系。

方向：引入参数对象；用建造者组织可选参数；把相关参数提升为对象。

三、耦合与依赖​

6. 依恋情结​

一个方法大量访问另一个类的数据，说明它「待错了地方」。

方向：把方法搬到它真正依恋的类中。

7. 狎昵关系​

两个类过度访问彼此的内部细节，边界形同虚设。

方向：抽取共同部分、用委托替代直接访问、明确公开接口。

8. 过度耦合的消息链​

出现形如 a.getB().getC().getD() 的长链，调用方被迫了解整条对象关系。

方向：用隐藏委托提供直接入口；把链式导航封装为方法。

9. 中间人​

一个类的大部分方法只是简单转发，没有自己的价值。

方向：移除中间人，让调用方直接访问目标；或保留有价值的少量委托。

10. 不完美的库类​

第三方库功能不足，又无法直接修改。

方向：使用引入外来方法（扩展方法或包装类）补足，并把这类代码集中在统一位置，便于将来替换。

四、变化与抽象​

11. 发散式变化​

一个类因为多种不相关的原因被反复修改，说明它承担了多个职责。

方向：识别变化的维度，按维度拆分。

12. 散弹式修改​

一个很小的功能变更要求同时修改大量分散的位置。

方向：把散落的相关逻辑集中到一处；用多态替代分散的条件分支。

13. 平行继承体系​

每新增一个子类，都必须在另一个继承体系中也新增对应子类。

方向：让一个体系引用另一个体系，用组合替代平行继承。

14. 夸夸其谈未来性​

为「将来可能需要」预留的抽象、参数与钩子，实际上从未被使用。

方向：删除。保留未被使用的灵活性是纯粹的负债。

15. 过度耦合的结构分支​

同一组条件判断在多处重复出现（典型形态是反复出现的 switch 或 if-else 链）。

方向：用多态或策略替代；把分支集中到工厂或映射表。

五、数据与类型​

16. 数据泥团​

若干个字段总是一起出现（三四个字段成组出现在多个参数列表或类中）。

方向：抽取为独立对象，把这些字段的校验与操作一并纳入。

17. 基本类型偏执​

用基本类型表达有语义的概念（金额用字符串、状态用整数、电话用字符串），导致校验逻辑散落各处。

方向：引入值对象，把校验与行为封装进去。

18. 纯稚的数据类​

类只有字段与访问方法，没有行为，所有逻辑都在外部使用它。

方向：把与之相关的方法搬进类内；若它确实只是数据传输对象，则明确其定位并保持简单。

19. 令人迷惑的暂时字段​

某些字段只在特定条件下有值，其他时候为空，导致代码充满条件判断。

方向：把只在特定场景使用的字段抽取为独立对象；或引入空对象替代判空。

20. 冗赘类​

存在价值不足的类：做得太少、已在别处被替代、或只是为了对称而存在。

方向：内联合并，或降级为简单结构（如值对象、记录类型）。

21. 被拒绝的遗赠​

子类只使用父类的一小部分，或继承后必须禁用父类的大部分行为。

方向：用组合或委托替代继承；重新梳理继承关系。

22. 过多的注释​

注释大量存在以解释代码「做什么」，往往说明代码无法自解释；或存在已被注释掉的死代码。

方向：先改代码让注释变多余，再删除冗余注释。保留的注释应当解释为什么。

怎么用这份清单​

  • 不必逐条检查。优先处理影响改动成本最高的几条：重复代码、过长函数、发散式变化、散弹式修改。
  • 坏味道是线索而非判决。某些看似「坏」的结构在特定约束下是合理的，例如为性能而刻意保留的重复。
  • 重构前必须有测试防护网；没有测试时，重构的风险远大于收益。
