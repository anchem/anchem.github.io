# 重构

> 简单说，重构就是在**不改变代码外在行为**的前提下，对代码进行修改，以改进程序的内部结构，比如获得更好的可读性、可维护性、可扩展性等。

## 为什么应该重构

不做重构的短期收益是「省时间」，长期代价是**修改成本单调上升**。具体表现为：

| 现象 | 后果 |
| --- | --- |
| 理解代码的时间超过修改时间 | 交付周期变长 |
| 改动的影响面不可预测 | 回归风险上升，不敢改动 |
| 同一条规则写在多处 | 修改必然遗漏，产生不一致 |
| 测试难以编写 | 只能靠手工回归，反馈周期变长 |

这些代价最终都会体现在[维护成本](../../../../value/business/profitability.md)上——大型软件的维护成本可以达到开发成本的四倍左右。

## 不改变外在行为

这是重构的定义性约束，也是它区别于「重写」和「修改功能」的地方：

| 活动 | 是否改变行为 | 目的 |
| --- | --- | --- |
| 重构 | 否 | 改善结构 |
| 修缺陷 | 是（修正错误行为） | 让行为符合预期 |
| 加功能 | 是（增加行为） | 扩展能力 |
| 重写 | 通常是 | 更换实现 |

**不要在同一时间段内既重构又改功能**。混在一起会导致出问题时无法判断是结构改动还是行为改动引入的，也让审查变得困难。

## 何时做重构

重构不需要专门的「重构阶段」，它应当是**日常开发的一部分**：

1. **添加功能时**：发现结构阻碍了新功能的加入，先调整结构再加。
2. **修缺陷时**：缺陷的根因常是结构问题，顺手处理能避免复发。
3. **代码审查时**：把审查中发现的坏味道作为重构输入。
4. **定期专项**：对积累较深的技术债，安排有计划的重构。

其中第 1 条最重要——**「让添加功能变容易」是重构最实际的动机**。
