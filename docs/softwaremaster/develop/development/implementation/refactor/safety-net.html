测试防护网

重构的定义是「不改变外在行为」。要在修改结构的同时确认行为未变，唯一可行的办法是自动化测试。

为什么测试是前提而非可选项​

没有测试时，重构只能靠手工验证。这带来三个问题：

  1. 验证不完整：只能覆盖想到的路径，边界与异常分支全靠运气。
  2. 成本随规模上升：每次重构都要全量手工回归，实践中会选择跳过。
  3. 不敢重构：风险不可控时，理性的选择是不改，于是债务持续累积。

因此**「这个模块没有测试」实际上是「这个模块不能安全重构」**。

重构需要什么样的测试​

不是所有测试都对重构友好：

测试类型对重构的作用
单元测试定位精确、执行快，最适合支撑重构
集成测试覆盖跨模块协作，数量可以少但要关键
契约测试保证对外行为不变，重构时的安全边界
端到端测试覆盖面广但慢且脆，不适合高频运行

关键是测试要针对行为而不是实现：断言外部可观察的结果，而不是内部调用顺序。过度依赖实现细节的测试会在重构时大面积失败，反而成为阻碍。

从没有测试开始​

已有系统通常不具备完善的测试。实用的推进路径：

  1. 从即将重构的部分开始补测试，而不是全面铺开。
  2. 先写「特征测试」：记录现有行为（包括看起来不对的行为），作为改动前的基线。
  3. 从最外层的稳定接口开始：接口比内部实现更稳定，测试的寿命更长。
  4. 优先覆盖分支与边界，而不是追求覆盖率数字。

覆盖率是诊断指标，不是目标——为了指标而写的测试不会带来信心。

防护网之外的保障​

测试不是唯一手段，配套措施能进一步降低风险：

手段作用
小步提交出问题时能精确回退到出错的步骤
类型检查与静态分析编译期发现结构性错误
灰度发布让问题在影响范围小时暴露
可观测性上线后快速发现行为偏差

实践建议​

  • 重构前先确认防护网是否足够。不足时，先补测试，再重构。
  • 保持测试快速：慢测试会让人跳过它，防护网即刻失效。
  • 定期审视测试的脆弱性：频繁因为无关改动而失败的测试需要重构或删除。
  • 把「为新功能补测试」作为常规要求，防护网靠日常积累而不是专项建设。
