# 重构工具

工具能显著降低重构的成本与风险。**用工具做机械性改动，把人的精力留给判断性工作**。

## 工具能可靠完成的事

| 类型 | 说明 |
| --- | --- |
| 语义重命名 | 跨文件、跨模块的重命名，不会漏改 |
| 提取函数 / 变量 | 自动分析数据流与依赖 |
| 内联 | 反向操作 |
| 搬移与提取类 | 自动调整引用与可见性 |
| 修改签名 | 同步更新所有调用点 |
| 安全删除 | 确认无引用后再删除 |

这些操作的特点是**确定性**：它们的正确性可以被工具保证，人工执行则必然有遗漏风险。

## IDE 的价值

现代 IDE 已内置大量重构能力。关键是要认识到：**手动查找替换 ≠ 重构**。

| 操作 | 安全性 |
| --- | --- |
| 查找替换文本 | 可能误改字符串、注释、同名不同作用域的符号 |
| 语义重命名 | 只改指向该符号的引用 |

在跨模块的项目中，用文本替换做重命名是常见的低级事故来源。

## 静态分析工具

| 用途 | 说明 |
| --- | --- |
| 坏味道检测 | 复杂度、重复度、过长函数等 |
| 依赖分析 | 循环依赖、层次违规、包依赖规则 |
| 重复代码检测 | 识别结构性重复（而非文本重复） |
| 覆盖率统计 | 判断防护网是否足够 |
| 变更影响分析 | 定位改动的波及范围 |

把这些检查纳入流水线后，代码质量的**劣化会被及时拦截**，而不是等积累到必须专项治理。

## 自动化重构的边界

工具擅长机械变换，**判断仍需要人**：

- 该不该抽这个抽象，取决于业务语义与未来的变化方向，工具无法判断；
- 命名是否准确反映职责，只能由人决定；
- 是否值得重构，取决于成本收益，属于工程判断。

因此工具的正确用法是：**用工具消除机械劳动，把时间投入到结构判断上**。

## 实践建议

- 团队统一 IDE 与格式化配置，避免因工具差异产生无意义的改动噪音。
- 重构时使用工具而非手工编辑；这一步的纪律能避免大量隐蔽错误。
- 把静态检查纳入[流水线](../build.md)，让架构约束可以被自动验证——参见[演进式架构](../../architecture/evolutionary-architecture.md)。
- 定期清理检测结果中的存量问题，避免报告淹没在大量历史告警里而失去作用。
