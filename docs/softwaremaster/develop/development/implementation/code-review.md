# 代码审查

代码审查同时实现两个目标：**发现缺陷**与**传播知识**。后者常被忽略，却对团队长期能力影响更大。

## 有效的审查关注什么

| 优先级 | 关注点 |
| --- | --- |
| 高 | 正确性：边界条件、并发、错误处理、资源释放 |
| 高 | 接口与契约：是否破坏兼容、语义是否清晰 |
| 中 | 结构与耦合：职责是否单一、依赖方向是否合理 |
| 中 | 可测试性：是否便于验证 |
| 中 | 安全：输入校验、权限、敏感信息 |
| 低 | 命名与风格（**应当由工具自动完成**） |

把精力花在低优先级项上是审查效率低下的主要原因。格式、命名规范这类可自动化的内容应当交给工具，审查只处理工具判断不了的部分。

## 审查效能的关键变量

### 单次规模

审查质量随变更规模迅速下降。**小块审查**（数百行以内）能发现更多问题，且意见更容易被接受。大块审查往往只得到风格层面的评论，真正的问题被淹没。

实践做法是把大改动拆成一系列可独立理解的小提交，而不是一次性合并。

### 反馈速度

审查等待时间会阻塞提交者，进而影响交付节奏。长时间挂起的审查还会让上下文丢失，导致返工。**缩短审查响应时间是投入产出比很高的优化**。

### 审查意见的表达

- 区分「必须修改」与「建议讨论」，让提交者知道哪些是阻塞项；
- 解释理由而不是只给结论：「这里会有并发问题，因为……」比「改用锁」更有价值；
- 区分事实与偏好：个人风格偏好不应成为阻塞项。

## 哪些内容应当用工具而非人工

| 内容 | 工具 |
| --- | --- |
| 格式与命名 | 格式化与静态检查工具 |
| 通用缺陷模式 | 静态分析 |
| 依赖漏洞 | 依赖扫描 |
| 复杂度与重复度 | 质量度量 |
| 覆盖率 | 测试报告 |

**能被自动检查的规则不要靠人工**——人工检查既不稳定也不经济。

## 需要警惕的审查形态

- **橡皮图章**：无实质意见直接通过，通常源于审查负担过重；
- **风格之争**：大量讨论格式而无人关注逻辑；
- **个人偏好固化**：审查变成「按我的写法来」，抑制了团队多样性；
- **只审新代码不审改动影响**：忽略了既有调用方是否受影响。

## 实践建议

- 控制单次变更是小步的，必要时拆分提交。
- 提交者先自查并写清改动背景与验证方式，能显著提升审查效率。
- 把可自动化的检查全部下沉到流水线。
- 跟踪审查响应时间，把它作为工程效能指标之一。
- 定期回看：哪些缺陷在审查中漏过、哪些意见反复出现——前者说明审查盲区，后者说明缺少自动化或缺少共识。
