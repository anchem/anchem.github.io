# 编译构建

构建把源码转换为**可交付的产物**。它看似只是工具链问题，实则直接影响交付的一致性与可复现性。

## 构建的三个目标

| 目标 | 含义 |
| --- | --- |
| 正确 | 产物包含正确的代码与依赖 |
| 一致 | 每次构建得到相同结果（可复现构建） |
| 高效 | 增量构建、并行构建、缓存复用 |

其中**一致性与高效性常常冲突**：缓存能加速，但也可能引入不一致。原则是**缓存必须基于内容哈希，而不是时间戳**。

## 依赖管理

依赖是构建中最容易出问题的一环：

| 问题 | 后果 |
| --- | --- |
| 版本范围过宽 | 构建结果随时间漂移，同一份代码昨天能跑今天报错 |
| 传递依赖冲突 | 运行时出现难以定位的错误 |
| 依赖体积膨胀 | 产物变大、启动变慢、安全面扩大 |
| 未锁定版本 | 无法复现历史构建 |

做法：

1. **锁定全部传递依赖版本**，生成可提交的锁定文件；
2. **统一版本管理**，同一依赖在整个工程内保持一致；
3. **定期更新并扫描漏洞**，而不是长期不动或随时升级；
4. **裁剪无用依赖**，每次引入依赖都要评估其传递依赖与体积。

## 构建产物与环境

**构建一次，到处部署**：产物必须与环境无关，环境差异通过外部配置注入。在不同环境重新构建会引入不可控差异，破坏「测试过的就是发布的」这一前提。

## 增量与缓存

- 增量构建依赖**正确的依赖图**：依赖声明不全时，会出现「改了一个文件但产物没更新」的假成功。
- 分布式缓存能显著缩短构建时间，但必须保证缓存键包含全部影响产物的输入（源码、编译参数、依赖版本、环境变量）。
- 构建应当是**确定性**的：并行度与执行顺序不应当影响产物内容。

## 实践建议

- 让本地构建与流水线使用同一套命令与配置，避免「本地能过、流水线不过」。
- 构建脚本纳入[版本管理](../engineering/version-control.md)，与源码一同评审。
- 产物包含可追溯信息（版本号、提交哈希），便于定位线上问题。
- 把构建时长作为指标持续优化，它对反馈周期的影响是乘性的。
