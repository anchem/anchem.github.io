# 编程语言

语言是表达设计的工具。**语言提供的抽象能力，直接决定了什么样的设计能够被自然地表达。**

## 语言特性如何影响设计

| 特性 | 影响的模式 |
| --- | --- |
| 一等函数 | 策略、命令、回调可退化为函数参数 |
| 泛型 | 减少类型转换与运行时检查 |
| 闭包 | 简化状态携带，也易造成隐式捕获 |
| 不可变性 | 从根本上消除部分并发问题 |
| 类型系统 | 编译期发现错误的能力范围 |
| 模式匹配 | 替代大量分支与类型判断 |
| 空安全 | 减少空指针类缺陷 |
| 垃圾回收 | 免除手动内存管理，引入停顿与内存占用问题 |

**关键认识：模式不是永恒的。** 很多设计模式的存在是为了绕过语言的限制，当语言补齐对应能力时，模式会自然消解。

## 语言选择的考量维度

| 维度 | 说明 |
| --- | --- |
| 表达力 | 能否直接表达领域概念 |
| 生态与库 | 常见问题是否有成熟方案 |
| 运行特性 | 启动速度、内存占用、并发模型 |
| 团队熟悉度 | 学习成本与招聘难度 |
| 工具链 | 构建、调试、静态分析、性能剖析的成熟度 |
| 长期维护 | 语言与运行时的演进稳定性 |

**团队熟悉度的权重常被低估**：一门更先进但团队不熟悉的语言，会在相当长时间内让交付质量与速度同时下降。

## 并发模型的主要差异

| 模型 | 代表 | 特点 |
| --- | --- | --- |
| 线程 + 共享内存 | Java、C++ | 灵活但易错，需处理竞态 |
| 事件循环 | JavaScript、Node | 单线程无竞态，不适合 CPU 密集 |
| Actor / 消息 | Erlang、Akka | 无共享，天然分布 |
| CSP / 协程 | Go、Kotlin | 轻量并发，用通信替代共享 |
| 函数式不可变 | Haskell、Clojure | 从结构上消除共享状态 |

选择并发模型，本质是选择**把并发复杂度放在语言层还是应用层**。

## 实践建议

- 选语言看团队与生态，而不是看热度。语言替换的迁移成本通常被严重低估。
- 语言特性要用足：用不可变减少状态、用类型避免运行时错误、用泛型减少重复。
- 关注语言的**空值语义与错误处理机制**，这两处决定了系统边界的健壮程度。
- 多语言并存会显著增加构建、依赖与运维复杂度，应当有明确理由。
