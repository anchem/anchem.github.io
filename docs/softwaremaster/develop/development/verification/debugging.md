# 调试技术

调试是**从现象回溯到原因**的过程。它的效率差异极大：有人几分钟定位，有人几天无果，区别在于方法而非运气。

## 系统性的排查流程

```
复现 → 定位 → 缩小范围 → 验证假设 → 修复 → 回归
```

每一步都不可跳过：

| 步骤 | 关键动作 | 跳过的后果 |
| --- | --- | --- |
| 复现 | 找到稳定复现路径，记录环境与输入 | 无法验证修复是否有效 |
| 定位 | 确定问题在哪个层次（前端、服务、数据库、网络、内核） | 盲目修改无关代码 |
| 缩小范围 | 二分法排除，逐步逼近 | 靠猜，效率极低 |
| 验证假设 | 用最小改动确认原因 | 修了表象，根因仍在 |
| 修复 | 改根因而非症状 | 问题复发 |
| 回归 | 补测试，确保不再出现 | 同类问题反复发生 |

**「先复现」是最常被跳过却最不该跳过的一步**。不能复现的问题，其修复无法被验证。

## 二分法的应用

二分是定位范围最有效的手段：

- **代码二分**：注释掉一半逻辑，看问题是否消失；
- **版本二分**：在提交历史中二分，定位引入问题的提交；
- **数据二分**：逐步缩小输入数据范围；
- **环境二分**：对比正常与异常环境的差异（配置、版本、网络、时钟）。

版本二分尤其高效——它把「哪里出错」转化为「哪次改动出错」，直接指向原因。

## 需要先排除的常见陷阱

| 假设 | 现实 |
| --- | --- |
| 「代码逻辑肯定没问题」 | 问题常在最不可能的地方 |
| 「一定是这个原因」 | 未经验证的假设会消耗大量时间 |
| 「改一下就试试」 | 多变量同时改变会使结论失效 |
| 「日志里没报错就是没异常」 | 异常可能被吞掉，或日志级别不对 |

## 一份排查检查表

- 问题**什么时候开始**的？之前有什么变更（代码、配置、依赖、数据、流量）？
- 影响**范围**是全局还是局部？可以定位到用户、区域、实例还是时间窗口？
- 现象是否**稳定复现**？触发条件是什么？
- 各层指标是否一致？（应用日志、HTTP 状态、数据库、系统资源、网络）
- 是否与**时间**相关？（定时任务、缓存过期、证书到期、时钟偏移、连接池回收）

时间相关性极常被忽略，却解释了很大比例的「偶发」问题。

## 实践建议

- 一次只改一个变量，改完立即观察。
- 用可观测性工具（日志、指标、追踪）缩小范围，而不是只依赖断点调试。
- 修复后务必补一条测试，把这次的经验固化为防护网。
- 记录排查过程与结论：同类问题再次出现时，这份记录能节省大量时间。
- 排查生产问题时优先恢复服务，再定位根因——恢复与定位可以并行。
