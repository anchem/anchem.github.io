# 测试替身

测试替身（test double）用来**替代真实依赖**，使测试能够隔离、快速、可重复地运行。

## 五种类型

| 类型 | 作用 | 使用场景 |
| --- | --- | --- |
| 桩（Stub） | 返回预设值 | 提供输入，不关心是否被调用 |
| 假对象（Fake） | 有简化的真实实现 | 内存版仓储、内存队列 |
| 模拟（Mock） | 验证交互是否发生 | 需要确认「确实调用了」 |
| 间谍（Spy） | 记录调用并保留真实行为 | 需要观察又不想改变行为 |
| 哑对象（Dummy） | 仅用于填充参数 | 参数不被使用 |

**桩与模拟的区别是本质的**：桩关注**状态**（提供了什么数据），模拟关注**行为**（发生了哪些交互）。

## 一个重要的实践倾向

**优先使用桩和假对象，谨慎使用模拟。**

原因是模拟断言的是「实现做了什么」（调用了哪个方法、几次、什么顺序），这会把测试与实现细节焊死：

- 重构时，行为没变但调用方式变了 → 测试大面积失败；
- 测试变成了实现的镜像，不再独立表达期望。

断言「最终状态或返回值」的测试生命力更长，因为它只依赖对外契约。

## 局部假对象与内存实现

对仓储、消息队列、外部服务这类依赖，编写**内存版实现**通常比模拟更有价值：

| 优势 | 说明 |
| --- | --- |
| 可复用 | 多个测试共用，无需重复配置 |
| 行为更真实 | 能暴露真实的数据访问问题 |
| 支持集成测试 | 可作为集成测试的轻量替代 |

代价是需要维护，且可能与真实实现行为产生偏差——因此关键路径仍需少量针对真实依赖的集成测试。

## 需要警惕的问题

| 问题 | 后果 |
| --- | --- |
| 过度模拟 | 测试全部通过但系统仍不可用 |
| 模拟了不属于自己的类型 | 依赖第三方接口细节，升级时大面积失败 |
| 模拟配置与真实行为不符 | 测试提供虚假信心 |
| 每个测试单独配置大量替身 | 测试冗长难读 |

第一条最严重：**如果所有协作者都被替换掉，测试实际上只验证了「代码调用了预期的调用」**，而真实集成的问题完全未被覆盖。

## 实践建议

- 优先为**外部边界**（网络、数据库、时钟、随机、文件系统）引入替身，而不是为内部类。
- 对外部接口做一层薄封装，然后再替换封装而不是直接替换第三方库。
- 断言状态优于断言交互；必须验证交互时，选择最关键、最稳定的那一次。
- 关键集成路径保留真实依赖的集成测试，避免陷入「全绿但不可用」。
- 时间与随机必须可注入，这是让测试可重复的前提。
