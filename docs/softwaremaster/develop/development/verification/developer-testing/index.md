# 开发者测试

开发者测试指**由代码作者编写并长期维护**的自动化测试。它与独立测试团队的工作互补：前者保证实现正确与可持续修改，后者关注整体质量与用户视角。

## 为什么开发者必须写测试

| 原因 | 说明 |
| --- | --- |
| 修改的信心 | 没有测试时，改动只能靠运气 |
| 设计反馈 | 难以测试的结构通常也是耦合过重的结构 |
| 活的文档 | 测试描述系统实际行为，且不会过期 |
| 回归防护 | 唯一能低成本反复执行验证的手段 |

其中**设计反馈**最常被忽略：写测试时的困难（要 mock 大量依赖、无法构造输入）本身就是设计问题的信号，而且是在改代码之前发现的。

## 测试应当满足的性质

| 性质 | 含义 |
| --- | --- |
| 快速 | 慢测试会被跳过 |
| 独立 | 不依赖执行顺序与其他测试的状态 |
| 可重复 | 任何环境任何时间结果相同 |
| 自验证 | 通过失败即可判断，无需人工比对 |
| 及时 | 与代码同步编写，而不是事后补 |

## 一个常见的误解

「测试越多越好」不成立。**维护测试本身有成本**，过度脆弱的测试会成为负担：

- 与实现细节绑定的测试，重构时大面积失败；
- 重复覆盖同一逻辑的测试，只增加维护量；
- 只断言「没有抛异常」的测试，几乎不提供信息。

测试的规模与粒度应当由**风险**决定：核心业务规则与复杂边界值得密集覆盖，样板代码不值得。

## 与其他层次的关系

开发者测试是[测试层次](./../index.md)的基础层：它提供最快的反馈与最精确的定位。上层测试（集成、端到端）应当只覆盖下层测不到的部分。
