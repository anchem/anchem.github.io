# 单元测试

单元测试验证**最小的可测试单元**（通常是一个函数或类）的行为。它的价值在于快速反馈与精确定位。

## 一条好测试的结构

```
准备（Arrange） → 执行（Act） → 断言（Assert）
```

三段职责清晰，读者能立刻看出「在什么前提下、做了什么、期望什么」。若测试中这三段混杂多轮，通常说明它验证了太多内容，应当拆分。

## 测试命名

测试名应当描述**行为与前提**，而不是实现方法：

| 差的命名 | 好的命名 |
| --- | --- |
| testCalculate | 订单金额为负时抛出参数异常 |
| testProcess2 | 已支付的订单不允许再次支付 |
| testGetUser | 用户不存在时返回空而非抛异常 |

测试名是失败信息的一部分——失败时最先看到的就是它，所以命名质量直接影响排查效率。

## 该测什么

| 优先测 | 说明 |
| --- | --- |
| 业务规则与判断逻辑 | 核心价值所在，出错代价最高 |
| 边界与异常路径 | 空值、零、最大最小、越界、并发 |
| 曾经出过问题的地方 | 每个缺陷都应当留下一条测试 |
| 复杂的条件组合 | 分支爆炸处最易出错 |

**不必刻意测**：只有 getter/setter 的数据类、框架自身行为、样板式转发代码。

## 断言的原则

- **断言行为与结果**，而不是内部调用顺序。后者会把测试与实现绑定，阻碍重构。
- **一个测试可以有多条断言**，但应当只验证「一件事」。多条断言验证同一件事是正常的。
- 避免断言「不抛异常」这类弱断言，它几乎不提供信息。

## 隔离与依赖

单元测试必须隔离外部依赖（数据库、网络、文件、时间、随机数），否则会变慢、变脆。做法见[测试替身](./test-double.md)。

特别注意**时间与随机性**：直接调用系统时钟或随机数生成器会让测试不可重复。应当把时间与随机源作为依赖注入，在测试中固定。

## 覆盖率怎么用

覆盖率是**诊断指标**，不是目标：

- 低覆盖率明确说明测试不足；
- 高覆盖率**不能说明测试有效**——执行过一行代码不等于验证了它的行为；
- 覆盖率下降的趋势值得关注，绝对值意义有限。

## 实践建议

- 测试与代码同源同仓，改动时一并更新。
- 每个修复的缺陷都补一条测试，这是防护网增厚的唯一可持续方式。
- 保持单个测试快速（毫秒级），整个套件才能在每次提交时运行。
- 定期清理过时测试：测试代码同样需要维护，遗留的坏测试会消耗信任。
- 若某个类极难测试，先审视它的设计（依赖是否过多、职责是否混杂），而不是先加 mock。
