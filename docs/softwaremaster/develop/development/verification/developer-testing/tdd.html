测试驱动开发

测试驱动开发（TDD）的核心主张是：先写测试，再写实现。它的主要收益不在测试本身，而在它迫使设计在编码前被想清楚。

红 - 绿 - 重构​

红：写一个失败的测试，定义期望行为
绿：用最简单的方式让它通过
重构：在测试保护下改善结构

三步必须严格轮转，尤其是**「用最简单的方式让它通过」**——跳过这一步会导致一次性写出复杂实现，失去 TDD 的主要价值。

真正的收益​

收益说明
设计反馈前置不可测试的设计在写第一行实现前就暴露
需求澄清写测试时必须明确输入输出与边界
防护网自然形成测试是先写的，不会「以后补」
调试成本降低失败范围小，原因明确
避免过度设计只实现让测试通过所需的代码

其中前两条最容易被低估。「这个类怎么测」这个问题本身就等价于「这个类的职责是否清晰」。

常见的误解与反对​

反对意见回应
写测试拖慢开发短期慢，长期快；节省的是调试与回归的时间
不适合探索性开发对未知领域可先做技术验证（spike），确认后再 TDD
不适合 UI / 外部集成这类场景用其他手段（契约测试、端到端测试）
覆盖率必须很高覆盖率是副产品，不是目标

TDD 并非普适。在算法实现、界面交互、与外部系统的首次集成等场景中，先探索再补测试是合理的。关键在于承认：在需要长期维护的核心逻辑上，测试先行通常优于事后补写。

与测试后行的对比​

维度测试先行测试后行
设计反馈编码前获得编码后（可能已固化）
测试完整性边界在实现前被明确容易只覆盖实现过的路径
心理阻力需先接受失败更直觉
适用逻辑明确、需长期维护探索性、原型

实践建议​

  • 从「缺陷修复」开始实践：先写一个能复现缺陷的失败测试，再修复。这是最自然的入手方式。
  • 一次只处理一个行为，保持小步。步子大了就退化成「先写实现再补测试」。
  • 测试失败时不要追加实现，先回退；红灯不断加代码是常见反模式。
  • 把 TDD 用在核心业务逻辑与复杂条件上，不必强求覆盖所有代码。
  • 团队内不必强推。比 TDD 更重要的是「测试与代码同步」，而不是测试的书写顺序。
