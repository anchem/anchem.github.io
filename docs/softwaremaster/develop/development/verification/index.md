# 软件验证

验证回答一个问题：**我们凭什么相信这个系统是对的**。没有验证的交付，本质上是在把风险转嫁给用户。

## 验证的两个维度

| 维度 | 问题 | 手段 |
| --- | --- | --- |
| 验证（Verification） | 我们做得对不对？（符合规格） | 单元测试、评审、静态分析 |
| 确认（Validation） | 我们做的是对的东西吗？（符合需求） | 验收测试、可用性测试、灰度验证 |

**二者不能互相替代**。做对了错误的东西，与做错了正确的东西，同样是失败——只是失败得更晚、代价更大。

## 测试的层次

```
单元测试 → 集成测试 → 契约测试 → 端到端测试 → 验收测试
快、稳定、定位精确  ←→  慢、脆弱、覆盖面广
```

层次设计的关键是**在正确的层次验证正确的事情**：

| 验证什么 | 合适的层次 |
| --- | --- |
| 业务规则与算法 | 单元测试 |
| 模块协作与数据访问 | 集成测试 |
| 对外接口不变 | 契约测试 |
| 关键用户流程 | 端到端测试（少量） |
| 需求是否被满足 | 验收测试 |

**过度依赖端到端测试是最常见的策略失误**：它慢、脆、定位困难，且失败原因需要人工排查。合理结构应当是「大量单元测试 + 适量集成测试 + 少量端到端测试」。

## 一条纪律

**测试的价值在于提供修改的勇气**，而不在于覆盖率数字。让团队敢于改动、敢于重构的测试才有意义；为了指标凑出来的测试只是负担。
