# 质量保障

质量保障（QA）关注的是**质量如何被系统性地保证**，而不仅是「测出多少缺陷」。

## 质量策略的构成

| 层次 | 手段 |
| --- | --- |
| 预防 | 需求评审、设计评审、编码规范、类型检查 |
| 检测 | 单元 / 集成 / 契约 / 端到端测试、静态分析、安全扫描 |
| 验证 | 验收测试、灰度发布、A/B 验证 |
| 反馈 | 缺陷分析、质量度量、回顾改进 |

**越靠前的手段成本越低**，这也是「测试左移」的核心逻辑：把质量活动前移，缺陷在更早阶段被拦截，修复成本呈数量级下降。

## 测试策略的核心决策

测试层次的比例应当由**风险与成本**决定，而不是套用固定比例：

| 判断 | 倾向 |
| --- | --- |
| 业务规则复杂、变化频繁 | 加强单元测试 |
| 外部依赖多、集成风险高 | 加强集成与契约测试 |
| 关键用户流程、合规要求 | 保留少量端到端测试 |
| 系统庞大、端到端慢 | 用契约测试替代大部分端到端 |

其中**契约测试的价值常被低估**：它验证服务间的接口约定，能在不需要启动完整环境的情况下挡住绝大多数集成问题。

## 测试数据的治理

测试失败的常见原因不是代码问题，而是数据问题：

- 数据被其他测试修改，导致顺序依赖；
- 测试数据与生产分布差异大，覆盖不到真实场景；
- 使用真实生产数据带来合规风险。

做法：**每个测试自建数据、自清理**；需要真实分布时使用脱敏后的样本；避免测试之间共享可变数据。

## 质量度量

| 指标 | 用途与风险 |
| --- | --- |
| 缺陷逃逸率 | 最有价值的指标——衡量防线是否有效 |
| 缺陷分布 | 定位问题集中的模块 |
| 缺陷修复时长 | 反映响应能力 |
| 测试覆盖率 | 诊断工具，不能当目标 |
| 回归失败率 | 反映测试的脆弱程度 |
| 变更失败率 | 反映发布质量 |

**缺陷逃逸率特别值得关注**：它衡量的是「本该被拦截却漏到线上的缺陷比例」。这个指标的改善直接反映了质量体系的有效性。

注意[古德哈特定律](../../../value/measurement/metrics.md)：任何指标一旦成为考核目标，就会被以扭曲的方式优化。

## 缺陷分析

单个缺陷的修复只解决一次问题，**缺陷分析解决一类问题**：

1. 为什么没在更早阶段发现？（防线缺失还是失效？）
2. 同类问题在其他模块是否也存在？
3. 需要在流程或工具上做什么改变？

针对「重复出现的同类缺陷」和「逃逸到生产的缺陷」做分析，投入产出比最高。

## 实践建议

- 质量活动尽可能自动化并前置到流水线，人工只做工具做不了的部分。
- 让质量指标可见，但只用于改进，不用于考核个人。
- 把每次事故与逃逸缺陷转化为一条可自动验证的测试。
- 定期审视测试套件的健康度：慢测试、脆弱测试、长期失败的测试需要清理。
