# 编译过程

编译把源码翻译为目标代码，其价值是**把问题逐步转换到更容易分析与优化的形态**。

## 各阶段职责

| 阶段 | 输入 → 输出 | 主要问题 |
| --- | --- | --- |
| 词法分析 | 字符流 → 记号流 | 识别单词与字面量 |
| 语法分析 | 记号流 → 语法树 | 判断结构是否合法 |
| 语义分析 | 语法树 → 带类型的中间表示 | 类型检查、作用域、名称解析 |
| 中间表示 | 高层 → 低层 IR | 与目标机器解耦 |
| 优化 | IR → 更优 IR | 不变式提升、内联、向量化 |
| 代码生成 | IR → 目标代码 | 寄存器分配、指令选择 |

## 可被工程复用的思想

编译技术并非只用于编程语言。以下问题都可以借用同一套方法：

| 业务问题 | 编译技术的对应 |
| --- | --- |
| 查询语句解析与执行 | 语法分析 + 中间表示 + 优化 |
| 规则引擎 | 语义分析 + 求值策略 |
| 配置校验 | 语法与语义检查 |
| 模板渲染 | 解析 + 代码生成 |
| DSL 设计 | 全套流程 |

**把领域问题表达成 DSL 再用编译器思路处理**，是降低复杂业务逻辑维护成本的常用手段。

## 优化的边界

编译器优化受两个限制：

1. **语义不变**：任何优化都不能改变可观察行为。因此编译器不会删除有副作用或可能抛异常的代码。
2. **可见范围**：跨模块、跨动态分派、跨编译单元的分析成本高，往往不做。

这意味着**性能关键路径上，结构清晰的代码更容易被优化**。过度抽象（大量间接层、反射、动态派发）会让优化器无能为力。

## 实践建议

- 使用性能分析工具确认热点，再判断是否值得为此调整代码结构。
- 理解「未定义行为」的含义：它会让优化器做出反直觉的推理，是隐蔽 bug 的常见来源。
- 关注编译与构建配置（优化级别、内联策略），它们对性能的影响常被低估。
