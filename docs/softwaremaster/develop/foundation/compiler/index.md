# 汇编及编译原理

这一学科回答：**我写的代码最终变成了什么**。它决定了性能分析的下限与语言语义的边界。

## 包含内容

- [汇编与机器模型](./assembly.md)：指令、寄存器、调用约定
- [编译过程](./compilation.md)：从源码到可执行文件的阶段划分与优化

## 为什么工程上需要它

| 场景 | 需要的知识 |
| --- | --- |
| 定位「看起来一样但快十倍」的两段代码 | 优化器行为、内存访问模式 |
| 理解语言特性（闭包、泛型、异常）的真实开销 | 编译期与运行期的实现机制 |
| 排查崩溃与内存越界 | 调用栈、寄存器与栈帧布局 |
| 判断某种优化是否可能 | 编译器能做什么、不能做什么 |

## 编译的基本阶段

```
源码 → 词法分析 → 语法分析 → 语义分析 → 中间表示 → 优化 → 目标代码
```

每一阶段的存在都有明确目的：把问题逐层转换到更适合分析的形态。这也是**分词、解析、规则引擎**这类业务问题的通用解法——它们本质上都是编译技术的应用。

## 一条实用建议

不必精通汇编，但要建立两个直觉：

1. **内存访问比计算贵得多**，尤其在缓存未命中时；
2. **编译器远比大多数人想象的聪明，但只在它能看到全貌时**——跨模块、跨动态调用的优化能力有限。

这两个直觉能解释绝大多数「性能与预期不符」的现象。
