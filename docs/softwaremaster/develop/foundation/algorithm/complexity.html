复杂度分析

复杂度是衡量算法代价的共同语言，它让方案比较在写代码之前就能进行。

三个维度​

维度含义常见写法
时间复杂度操作次数随规模的增长O(n)、O(n log n)、O(n²)
空间复杂度额外内存随规模的增长O(1)、O(n)
IO 复杂度磁盘 / 网络访问次数的增长常被忽略，却往往是瓶颈

在数据量超过内存时，IO 复杂度比时间复杂度更有解释力。一次随机磁盘访问的开销约等于数百万次 CPU 指令，因此顺序扫描常常击败「更聪明」的随机访问算法。

要区分三种情况​

情形含义
最好情况通常没有参考价值
平均情况需要假设输入分布，常与实际不符
最坏情况工程上最重要——它是容量规划与安全边界的依据

哈希表的平均 O(1) 与最坏 O(n) 是同一个结构的两种现实：在攻击者可控制输入的场景下，必须按最坏情况设计。

摊销分析​

某些操作偶尔很贵，但均摊到每次很便宜（如动态数组扩容）。摊销复杂度描述这类结构，但它不保证单次操作的上限——对延迟敏感的系统仍需要关注最坏单次耗时，否则会出现周期性抖动。

常数因子不可忽略​

复杂度描述的是增长趋势，不是绝对速度。在 n 较小（比如几百）时，O(n²) 的简单实现常常快于 O(n log n) 的复杂实现，因为前者的常数因子小得多。

实践建议​

  • 先估算规模：n 是 10³、10⁶ 还是 10⁹？规模决定了可接受的复杂度上限。
  • 把 IO 访问次数作为独立指标测量，不要只看 CPU 时间。
  • 对延迟敏感路径关注最坏单次耗时，对吞吐敏感路径关注摊销与平均。
  • 复杂度分析用于排除方案，而不是用于选出最优方案——筛完之后仍需实测。
