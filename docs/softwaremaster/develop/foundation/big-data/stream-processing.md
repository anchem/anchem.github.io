# 流处理

流处理对**持续到达的数据**做增量计算，核心挑战不是吞吐，而是**时间与状态的语义**。

## 三个必须定义的语义

### 1. 时间用哪一个

| 时间 | 含义 |
| --- | --- |
| 事件时间 | 事情实际发生的时间 |
| 处理时间 | 系统处理到它的时间 |

二者可能相差很大（网络延迟、设备离线）。**用处理时间做窗口统计，会在乱序数据下产生错误结果**，这是流处理最经典的坑。

### 2. 迟到的数据怎么办

- **丢弃**：简单，但结果不完全。
- **允许迟到窗口**：在窗口内等一段时间再输出。
- **水位线（watermark）**：用「认为不会再有更早数据」的标记决定何时触发计算。
- **回填**：先出近似结果，事后用批处理修正。

### 3. 投递语义

| 语义 | 含义 |
| --- | --- |
| 至多一次 | 可能丢 |
| 至少一次 | 可能重复 |
| 精确一次 | 恰好一次（需要状态与幂等配合） |

「精确一次」在实践中依赖**端到端幂等**：要么写出时可去重，要么计算可重放。仅靠框架保证是不够的。

## 状态管理

有状态计算（窗口聚合、去重、连接）需要保存状态，而状态需要：

- **持久化**：故障后可恢复；
- **可伸缩**：并行度变化时能重新分片；
- **有界**：必须有清理策略，否则状态无限增长。

状态大小往往是流处理系统真正的能力上限，而不是吞吐。

## 实践建议

- 明确定义事件时间语义与迟到处理策略，并写进需求。
- 有状态算子必须设置状态过期时间，避免无界增长。
- 为下游写入设计幂等键，这是实现端到端精确一次的实用路径。
- 监控消费延迟（lag）而不只是吞吐，它才是「是否跟上数据」的真实指标。
- 流处理与批处理的口径必须由同一份逻辑定义，否则指标会分裂成两套数字。
