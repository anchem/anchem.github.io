# 非关系型数据库

NoSQL 不是一个技术，而是**一组针对特定数据模型与规模需求的选择**。它的价值在于用放弃某些能力，换取另一些能力。

## 主要类型

| 类型 | 数据模型 | 强项 | 典型场景 |
| --- | --- | --- | --- |
| 键值存储 | key → value | 极高吞吐、极低延迟 | 缓存、会话、计数 |
| 文档数据库 | 半结构化文档 | 模式灵活、嵌套自然 | 内容管理、异构数据 |
| 宽列存储 | 稀疏多维表 | 海量写入、按行键范围扫描 | 时序、日志、监控 |
| 图数据库 | 节点与边 | 多跳关系遍历 | 社交、风控、知识图谱 |
| 全文检索 | 倒排索引 | 分词与相关性排序 | 搜索 |

## 关键取舍

### 放弃强一致，换取可用与扩展

多数 NoSQL 采用最终一致，牺牲了「读到的必然是最新数据」。这要求应用层能容忍脏读，或者显式处理冲突。**这个代价必须被业务接受，而不是被工程师替业务决定**。

### 放弃连接，换取水平扩展

数据分散在多个节点后，跨节点连接成本极高且不稳定。因此 NoSQL 普遍要求**按访问模式设计数据模型**——把查询所需的数据预先聚合在一起（反范式到极致）。

代价是：需求变化时数据模型可能要重建。这是 NoSQL 最容易被低估的成本。

### 模式灵活性是双刃剑

「无需预先定义模式」意味着写入阶段省事，但**读取时代码必须处理所有历史形态**。实践中良好的做法是在应用层维持显式版本号与兼容读取逻辑。

## 如何选择

先问三个问题：

1. 数据之间的关系是否复杂，需要多跳查询？
2. 是否存在强一致要求（金额、库存、权限）？
3. 规模是否真正超出单机关系数据库的能力？

三个答案都是「否」时，关系数据库通常是更省心的选择——成熟的事务支持、查询灵活性与运维生态，是难以替代的。

## 实践建议

- 采用 NoSQL 前明确写出：放弃了一致性的哪一部分，业务如何容忍。
- 键设计决定一切：它决定了数据分布、查询能力与热点风险。
- 为数据模型变更准备迁移方案，这是最终一致场景下最容易被忽略的工程负担。
