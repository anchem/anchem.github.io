# 存储引擎

存储引擎决定**数据在磁盘上如何组织、如何被读取与写入**。同一套 SQL 在不同引擎上的性能特性可能完全不同。

## 两种基本结构

| 结构 | 写入方式 | 读 | 写 | 适用 |
| --- | --- | --- | --- | --- |
| B+ 树 | 原地更新 | 快（对数级查找） | 随机写，较慢 | 读多写少、范围查询 |
| LSM 树 | 追加写 + 后台合并 | 需合并多份，较慢 | 顺序写，很快 | 写多读少、时序数据 |

**这是理解「为什么有些数据库写得快、有些读得快」的关键**：

- B+ 树把数据组织成有序页面，读一次就能定位；但写入需要找到页并修改，产生随机 IO。
- LSM 树先把写入追加到内存表，批量刷成有序文件，写入极快；但读取需要检查多份文件，且后台合并（compaction）会消耗 IO 与空间。

LSM 的「写放大」与「读放大」是两个必知代价：合并操作会周期性占用大量磁盘带宽，是延迟毛刺的常见来源。

## 页与缓存

数据库以**页**为单位管理磁盘与内存之间的数据交换，页大小固定。因此：

- 单行很小但列很多的表，读取时仍会加载整页，开销被放大；
- 页缓存命中率直接决定性能，而缓存能否命中取决于**访问的局部性**。

## 预写日志

为同时获得「快速写入」与「崩溃后可恢复」，几乎所有引擎都使用预写日志（WAL）：

1. 先把变更顺序追加到日志并刷盘；
2. 再异步更新实际数据结构。

崩溃后通过重放日志恢复。这解释了 fsync 频率对写入性能的巨大影响——**持久性保证的强度直接换成延迟**。

## 实践建议

- 按读写比例选型：写密集场景关注 LSM 的合并压力，读密集场景关注索引与缓存命中。
- 关注写放大与空间放大指标，尤其是在 SSD 上，它们直接影响寿命与成本。
- 大字段（大文本、二进制）单独存放或使用对象存储，避免撑大热数据页。
- 定期关注存储引擎的后台任务（合并、清理）与磁盘 IO 的竞争关系，这是延迟抖动的常见根因。
