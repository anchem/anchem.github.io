# 事务

事务把**多个操作捆绑成一个不可分割的逻辑单元**，是并发环境下保证数据正确的核心机制。

## ACID

| 特性 | 含义 | 实现手段 |
| --- | --- | --- |
| 原子性 A | 全部成功或全部失败 | 日志与回滚 |
| 一致性 C | 满足业务约束 | 约束、触发器、应用逻辑 |
| 隔离性 I | 并发事务互不干扰 | 锁与多版本并发控制 |
| 持久性 D | 提交后不丢失 | 预写日志与刷盘 |

注意「一致性」在 ACID 中指的是**约束不被破坏**，与分布式领域的「一致性」（多副本数据相同）不是同一个概念——这是沟通中最常见的术语混淆之一。

## 隔离级别与异常

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 否 | 可能 | 可能 |
| 可重复读 | 否 | 否 | 可能 |
| 串行化 | 否 | 否 | 否 |

隔离级别越高，正确性越强，**并发度越低**。工程上需要在两者间显式取舍，而不是无脑用最高级别。

### 容易被忽略的两种异常

- **丢失更新**：两个事务读同一行，各自修改后写回，后写者覆盖前者。这是最隐蔽也最常见的问题。
- **写偏斜**：两个事务各自检查条件后写入，单独看都合法，合起来破坏约束。可重复读无法防止它。

这两类问题不会因为「用了事务」就自动消失，需要显式的锁或版本检查。

## MVCC 与并发控制

多数现代数据库采用多版本并发控制（MVCC）：读操作访问快照，不阻塞写；写操作创建新版本。

它的好处是读写互不阻塞；代价是**需要清理旧版本**（如 PostgreSQL 的 vacuum），否则存储会持续膨胀。同时，长事务会拖住版本回收，是线上膨胀问题的常见根因。

## 实践建议

- 事务尽可能短，绝不在事务内做远程调用或等待用户输入。
- 明确每个事务的隔离级别，不要依赖默认值——不同数据库默认值不同。
- 对「读 - 改 - 写」模式使用显式锁或条件更新（乐观锁），不要假设隔离级别会替你处理。
- 用唯一约束承担并发去重的职责，这比应用层判断可靠得多。
- 分布式场景下事务会升级为[分布式一致性](../distributed/consistency.md)问题，方案完全不同。
