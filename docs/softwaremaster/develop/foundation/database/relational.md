# 关系模型

关系数据库以**表**为基本单位，用集合论与一阶逻辑作为理论基础，通过 SQL 声明式地表达查询。

## 核心概念

| 概念 | 含义 | 工程意义 |
| --- | --- | --- |
| 关系（表） | 行的集合 | 无固有顺序，不要依赖隐式排序 |
| 主键 | 唯一标识行 | 必须有稳定主键，否则无法可靠更新 |
| 外键 | 引用完整性 | 保证引用有效，但会引入锁与耦合 |
| 范式 | 减少冗余的分解规则 | 降低写异常，但增加连接成本 |
| 视图 | 命名的查询 | 解耦读接口与物理结构 |

## 范式与反范式

范式化的目标是消除冗余、避免更新异常。但**查询性能靠连接实现，连接是有代价的**，因此在读多写少的场景中，常见做法是**有意反范式**：

- 冗余存储派生字段，避免运行时计算与连接；
- 冗余存储快照值（如订单里的下单时价格），保证历史数据不随主数据变动。

反范式的代价是**一致性责任转移给应用**。必须显式写出保持同步的机制（事务内更新、事件驱动、定期对账），否则会产生长期的数据不一致。

## 索引

索引是关系数据库性能的核心：

| 要点 | 说明 |
| --- | --- |
| 本质 | 用额外空间与写放大，换取查找速度 |
| 结构 | 通常为 B+ 树，支持范围查询与顺序扫描 |
| 复合索引 | 遵循最左前缀原则，列顺序决定可用范围 |
| 覆盖索引 | 查询所需列都在索引中，避免回表 |
| 代价 | 每个索引都增加写入与存储成本 |

**索引不是越多越好**：每加一个索引，写入就多一次维护，且优化器需要更多时间选择。索引数量应当由实际查询模式决定。

## 实践建议

- 先明确访问模式（查询条件、排序、分页方式），再设计索引。
- 用执行计划而不是直觉判断查询是否走索引；扫描行数是关键指标。
- 分页注意深翻页问题：偏移量大时性能骤降，改用基于游标（键值）的分页。
- 表结构变更要考虑在线执行与回滚路径，大表加索引用不当会锁表。
