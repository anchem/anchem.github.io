# HTTP

HTTP 是应用层最广泛使用的协议：**请求 - 响应**模型，无状态，以文本语义描述资源操作。

## 核心语义

| 要素 | 含义 |
| --- | --- |
| 方法 | 语义化动作：GET 读取、POST 创建、PUT 替换、PATCH 局部更新、DELETE 删除 |
| 状态码 | 结果分类：2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误 |
| 首部 | 元数据：内容类型、缓存、认证、追踪 |
| 报文主体 | 实际数据 |

**方法语义决定幂等性**：GET、PUT、DELETE 应当幂等，POST 通常不幂等。这直接决定了失败时能否安全重试——这是[可靠性](../../../requirement/analysis/nonfunctional/reliability.md)设计的直接输入。

## 演进要解决的核心问题

HTTP 的每个版本都在解决特定瓶颈：

| 版本 | 解决的问题 | 手段 |
| --- | --- | --- |
| HTTP/1.1 | 连接复用 | 持久连接、管线化（受限） |
| HTTP/2 | 队头阻塞、首部冗余 | 多路复用、首部压缩、服务端推送 |
| HTTP/3 | TCP 层队头阻塞、握手延迟 | 基于 QUIC（UDP） |

主线始终是**减少往返与减少阻塞**。

## 缓存机制

缓存是性能优化中性价比最高的手段之一，前提是语义正确：

- **强缓存**：有效期内不请求服务端，最快但更新不及时；
- **协商缓存**：带校验条件询问，服务端可返回「未修改」，节省带宽；
- 缓存键必须包含所有影响响应的维度，否则会串数据——这是线上事故的常见来源。

## 实践建议

- 接口设计为幂等，让重试安全。非幂等操作需要显式的去重标识。
- 明确错误码语义：客户端错误与服务端错误的处置方不同，混用会误导调用方做出错误的重试决策。
- 为请求链路加上统一的追踪标识，跨服务排查时至关重要。
- 缓存策略要显式设计失效路径，而不是依赖超时兜底。
