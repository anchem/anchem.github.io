# TCP/IP

TCP/IP 是互联网的通信基础：IP 负责把数据包送到目标地址，TCP 在此之上提供可靠、有序的字节流。

## 分层

| 层 | 职责 | 典型协议 |
| --- | --- | --- |
| 应用层 | 业务语义 | HTTP、DNS、SMTP |
| 传输层 | 端到端连接与可靠性 | TCP、UDP |
| 网络层 | 寻址与路由 | IP、ICMP |
| 链路层 | 物理介质上的传输 | 以太网、WiFi |

## TCP 的关键机制

### 三次握手

建立连接需要一次往返。这是纯开销，对短连接场景是显著成本——这也是长连接池被广泛使用的原因。

### 拥塞控制

TCP 会根据丢包调整发送速率。这个机制意味着：

- **丢包会显著降低吞吐**，且恢复需要时间；
- 网络轻微拥塞时，表现不是「变慢一点」，而是速度骤降后缓慢爬升。

### 重传与超时

TCP 保证可靠，但它用**时间**换来可靠性。重传超时通常是秒级，远大于正常的毫秒级往返。因此应用层的超时设置应当高于 TCP 的重传时间，否则会出现「TCP 还在重试，应用已经放弃」的浪费。

## TCP 与 UDP 的取舍

| 维度 | TCP | UDP |
| --- | --- | --- |
| 可靠性 | 保证到达与顺序 | 不保证 |
| 延迟 | 重传带来抖动 | 无重传，稳定低延迟 |
| 适用 | 通用业务 | 实时音视频、游戏、遥测 |

关键认识：**在实时场景中，「过期的数据」比「丢失的数据」更糟**。视频帧晚到 500ms 已经无用，此时不重传反而更好。这解释了实时协议为什么基于 UDP 自行实现可靠性策略。

## 实践建议

- 使用连接池复用连接，避免握手与慢启动的重复成本。
- 区分「连接超时」与「读超时」，两者含义与排查方向不同。
- 排查慢请求时先确认问题在连接建立、传输，还是应用处理。
- 对延迟敏感的场景考虑减少往返次数（批量、缓存、就近接入），而不是单纯增加带宽。
