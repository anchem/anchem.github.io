# 容器编排

编排系统管理**多节点上的大量容器**：调度、扩缩、升级、自愈与网络。它的核心思想是**声明式收敛**。

## 声明式收敛模型

```
期望状态（声明） → 控制器持续比较 → 实际状态（观测） → 修正差异
```

用户只描述「要几个副本、什么镜像、多少资源」，系统负责让现实向描述靠拢。这让自愈成为默认行为：容器挂了会自动重建，节点下线会自动迁移。

**代价是「错误也会被忠实执行」**：一个错误的副本数或探针配置会被系统迅速扩散到整个集群。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| 调度 | 把容器放到合适的节点，考虑资源、亲和性与约束 |
| 服务发现 | 用稳定标识访问动态变化的实例集合 |
| 副本管理 | 维持期望实例数 |
| 滚动升级 | 分批替换实例，保证服务不中断 |
| 健康检查 | 存活探针（是否重启）与就绪探针（是否接流量） |
| 配置与密钥 | 外置注入，与镜像解耦 |
| 资源配额 | 请求值与上限，决定调度与隔离 |

## 有状态服务

编排系统对无状态服务很自然，对有状态服务则需要额外机制：

- **稳定标识**：需要固定网络标识与持久卷绑定；
- **有序操作**：集群组件的启动、升级、扩缩需要顺序保证；
- **数据安全**：实例迁移必须保证卷绑定正确，避免挂载到错误数据。

实践中常见的做法是把有状态负载交给托管服务或专用 Operator，而不是自行编排。

## 实践建议

- 资源请求值决定调度结果，上限决定隔离程度，两者都要基于实测设置。
- 存活探针不要检查外部依赖——依赖抖动会导致全量重启，把小故障放大成大事故。
- 部署必须配置**最大不可用**与**最大超出**，控制升级期间的容量损失。
- 配置优雅关闭宽限期，使其大于应用的实际清理时间。
- 为关键服务配置中断预算，避免维护操作一次性带走过多副本。
