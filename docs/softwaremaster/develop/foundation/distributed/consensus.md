# 共识

共识是让多个节点**对某个值达成一致**的算法。它是分布式系统中最基础也最困难的问题之一：在节点可能崩溃、网络可能分区的条件下，仍要保证一致性。

## 为什么需要共识

| 场景 | 需求 |
| --- | --- |
| 领导者选举 | 确定唯一的主节点 |
| 配置管理 | 所有节点看到相同配置 |
| 分布式锁 | 保证互斥 |
| 原子广播 | 所有节点以相同顺序应用操作 |
| 分布式事务提交 | 各参与方对结果达成一致 |

它的一个关键用途是**构建顺序**：一旦操作顺序被所有节点一致确认，副本状态就自然一致。

## 基本约束

- **多数派**：节点数通常取奇数，决议需要超过半数同意。这保证了任意两个多数派必有交集。
- **容错能力**：2f+1 个节点可以容忍 f 个节点故障。
- **任期 / 纪元**：用单调递增的编号区分不同领导者，防止过期领导者继续发号施令。
- **日志复制**：先写到多数派，才算提交。

核心权衡始终是**一致性 vs 可用性**：无法与多数派通信时，系统必须拒绝写入而不是接受可能冲突的写入。

## 与最终一致的关系

共识是**强一致**的基础设施，成本高（至少一次网络往返，且需要多数派在线）。因此它适合承载元数据、配置、领导者选举这类小数据量、关键性强的状态，**不适合作为海量业务数据的写入路径**。

## 实践建议

- 优先使用成熟实现，不要自行实现共识算法——它的正确性极难自证。
- 把共识的使用范围限制在元数据层，业务数据走更轻的方案。
- 关注共识组的大小：节点越多，写入延迟越高，容错能力提升有限。
- 明确分区时的行为：拒绝写入并提供明确错误，比静默接受更安全。
- 共识系统自身需要监控：选举频次、提交延迟、日志复制落后程度都是关键指标。
