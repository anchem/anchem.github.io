# 并发与并行

并发是**同时处理多个任务**的能力，并行是**同时执行多个任务**。前者是结构问题，后者是资源问题。

## 并发问题的三个根源

| 根源 | 说明 |
| --- | --- |
| 原子性缺失 | 「读 - 改 - 写」被其他操作插入 |
| 可见性缺失 | 一个线程的写入对另一线程不可见（缓存与重排） |
| 有序性缺失 | 编译器和 CPU 会重排指令 |

三者共同产生竞态条件。**「看起来没问题」的并发代码，往往只是在特定时序下没出错。**

## 主要解决手段

| 手段 | 原理 | 代价 |
| --- | --- | --- |
| 互斥锁 | 串行化临界区 | 阻塞、死锁风险、上下文切换 |
| 原子操作 | 硬件级不可分割指令 | 竞争激烈时自旋开销大 |
| 无锁结构 | CAS 循环 | 实现复杂，ABA 问题，内存回收难 |
| 不可变数据 | 消除共享可变状态 | 可能带来额外分配 |
| 消息传递 | 用通信替代共享 | 需要设计消息协议 |
| 函数式 / 单线程事件循环 | 从结构上避免并发 | 不适合 CPU 密集任务 |

**最简单有效的方案往往是「不共享」**：把状态限制在单个线程或单个 actor 内，通过消息传递协作。这消除了大量竞态的可能性。

## 死锁的四个必要条件

互斥、持有并等待、不可抢占、循环等待。破坏任意一条即可避免死锁。实践中最可行的是**统一加锁顺序**（破坏循环等待）与**设置超时**（限制持有并等待的时长）。

## 实践建议

- 优先设计无共享结构，而不是先用锁再优化。
- 临界区尽可能小，绝不在持锁期间做 IO 或等待外部服务。
- 并发容器优先于自行加锁——成熟实现已经处理了大量细节。
- 并发 bug 不可复现是常态：需要靠压力测试、竞态检测工具与代码审查，而不是靠「本地跑不出来」。
- 线程池大小、队列容量都必须显式设置上限；无界队列会把过载转化为内存耗尽。
