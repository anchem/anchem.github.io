# 一致性

这里的一致性指**多副本之间的数据一致**，与[数据库事务](../database/transaction.md)中的 ACID 一致性不是同一个概念。

## CAP 定理的正确理解

CAP 说的是：在网络分区（P）发生时，必须在一致性（C）与可用性（A）之间取舍。

关键点常被误读：

- **P 不是可选项**。分布式系统必然面临分区，所以真正的选择只有「分区时选 C 还是选 A」。
- **CAP 只在分区期间生效**。分区之外，系统可以同时具备一致性与可用性。
- 因此更有实用价值的是 **PACELC**：分区时选 A 或 C；否则（E，else）在延迟（L）与一致性（C）之间取舍。

PACELC 更贴近现实：即使没有分区，**追求强一致也要付出延迟代价**，因为需要跨节点协调。

## 一致性谱系

| 模型 | 保证 | 代价 |
| --- | --- | --- |
| 强一致 | 读到的必然是最新写入 | 延迟高，可用性受分区影响 |
| 顺序一致 | 所有节点看到相同顺序 | 协调成本 |
| 因果一致 | 有因果关系的操作有序 | 需维护依赖关系 |
| 最终一致 | 停止写入后副本会收敛 | 存在不一致窗口，需处理冲突 |

工程上的常见策略是**按数据分类处理**：金额、库存、权限用强一致；计数、推荐、统计用最终一致。

## 冲突解决

最终一致系统必须定义冲突解决规则：

- **最后写入胜出**：简单，但依赖时钟，可能丢失更新。
- **版本向量 / 逻辑时钟**：能识别并发写，交由应用合并。
- **CRDT**：用可交换、可结合的数据结构让合并自动收敛，适合计数、集合、序列。

## 实践建议

- 明确每类数据的一致性要求，并在设计文档中写出取舍理由。
- 单调读（不倒退）与读己之写是用户体验层面最低限度的一致性保证，通常应当满足。
- 最终一致必须配套对账机制：无法收敛时如何发现与修复。
- 不要用「加个重试」来掩盖一致性问题——重试改变的是概率，不是正确性。
