# 云原生

云原生不是一组具体技术，而是**假设环境不可靠、变化频繁**而设计应用的一套方法。

## 核心主张

| 主张 | 含义 |
| --- | --- |
| 以容器为交付单元 | 应用与环境打包在一起，见[容器技术](../container/index.md) |
| 声明式管理 | 描述期望状态，由系统持续收敛 |
| 面向失败设计 | 实例会被回收、网络会抖动、节点会下线 |
| 无状态优先 | 状态外置，使实例可随时替换 |
| 自动化运维 | 部署、扩缩、恢复都由系统执行 |
| 可观测 | 日志、指标、追踪是应用的一部分 |

## 为什么「面向失败」是第一原则

云上的实例生命周期是**短暂且不可预期**的。这带来几个强制要求：

- **优雅关闭**：收到终止信号后要停止接新请求、处理完在途请求、释放资源。多数系统的数据丢失都出在这一步。
- **快速启动**：实例随时可能被创建，冷启动时间直接影响弹性能力。
- **健康检查分离**：存活探针（要不要重启）与就绪探针（能不能接流量）含义不同，混用会导致启动期误杀。
- **幂等初始化**：实例可能重复启动，初始化逻辑不能做只能成功一次的事。

## 声明式与收敛

声明式的价值在于**把「应该是什么」和「怎么达到」分离**。系统持续比较期望状态与实际状态并修正差异，这让自愈成为默认行为，而不是额外的运维脚本。

代价是：状态漂移的排查更需要工具支持，且不恰当的期望状态会被系统忠实执行（例如错误的副本数会被迅速扩散）。

## 实践建议

- 应用必须处理优雅关闭与信号，这是云原生环境的基本要求。
- 有状态服务（数据库、消息队列）在云原生环境需要专门设计，通常采用 Operator 模式或托管服务。
- 为每个服务定义明确的资源请求与上限，避免相互争抢与不可预测的调度。
- 把配置与密钥外置到配置中心或密钥管理服务，不要打进镜像。
- 分布式追踪与结构化日志应当从第一天就接入，后期补齐的成本极高。
