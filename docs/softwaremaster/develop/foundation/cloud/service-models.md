# 服务模型

服务模型的区别在于**责任边界**：谁管理什么。选择模型就是选择把哪部分复杂度留给自己。

## 责任划分

| 层次 | 本地部署 | IaaS | PaaS | SaaS |
| --- | --- | --- | --- | --- |
| 应用 | 自管 | 自管 | 自管 | 供应商 |
| 运行时 | 自管 | 自管 | 供应商 | 供应商 |
| 操作系统 | 自管 | 自管 | 供应商 | 供应商 |
| 虚拟化 | 自管 | 供应商 | 供应商 | 供应商 |
| 硬件与机房 | 自管 | 供应商 | 供应商 | 供应商 |

**抽象层次越高，控制力越弱、便利性越强**。这不是优劣问题，而是取舍。

## 选择的判断依据

| 问题 | 倾向 |
| --- | --- |
| 是否有特殊的运行时或内核需求 | 是 → 偏向 IaaS / 容器 |
| 团队是否有能力承担系统维护 | 否 → 偏向 PaaS |
| 该能力是否是核心差异化 | 否 → 偏向 SaaS，不要自建 |
| 合规是否要求数据与代码完全可控 | 是 → 需要私有化或专有部署 |
| 成本是否随规模非线性增长 | 是 → 需要评估自建临界点 |

一个常见的原则是：**非核心能力优先外购**。自建一个邮件系统、监控系统或身份系统，几乎不会成为竞争优势，却会长期占用工程师。

## 隐藏成本

抽象层次的提升会带来两类隐藏成本：

1. **迁移成本（供应商锁定）**：专有 API、专有数据格式会把切换成本推高到无法承受。缓解方式是保持核心数据可导出、在关键边界使用标准协议。
2. **调试成本**：托管服务屏蔽了可见性，出问题时只能依赖供应商提供的信息。需要提前确认可观测性能力（日志、指标、追踪的可得性）。

## 实践建议

- 在架构文档里写清每个组件所属的服务模型与责任方，「谁负责」不清楚就是事故隐患。
- 对核心数据保持可导出与可迁移，避免把护城河修在自己脚上。
- 评估总拥有成本时要包含迁移与调试的隐性投入。
