# 软件大师之路

> 你在做什么？你有什么愿景？

我的回答是：**我在做软件产品，并致力于做出更好的软件产品，成为一名软件大师**。

我将从 **4** 个维度定义我所从事的事业，分别是**价值**、**需求**、**开发**、**运维**，本项目系统性地记录和分享各个知识点。

## 四个维度，一条链

```
价值（为什么做） → 需求（做什么） → 开发（怎么做） → 运维（交付使用）
   ↑                                                      │
   └────────────────── 真实反馈 ──────────────────────────┘
```

| 板块 | 回答的问题 | 核心产出 |
| --- | --- | --- |
| [价值](./value/index.md) | 这事值不值得做、为谁做 | 价值主张、度量指标 |
| [需求](./requirement/index.md) | 为了让价值发生，系统要做什么 | 需求基线、验收标准 |
| [开发](./develop/index.md) | 用什么原理、结构与手段实现 | 可运行、可维护的系统 |
| [运维](./maintenance/index.md) | 如何让它持续为用户工作 | 服务级别、故障闭环 |

在软件开发的生命周期中，有一条贯穿四个维度的链，它有一个重要性质：**越靠前的问题，发现得越晚代价越大**。价值判断错了，后面所有环节的投入都会成倍浪费；运维是唯一能拿到真实反馈的环节，它的结论必须能流回最前端。

## 怎么用这个知识库

不建议顺序通读，更有效的用法是：

1. **按问题定位**——说不清某个需求该不该做，回[价值](./value/index.md)找判据；不确定某个技术方案行不行，回[开发](./develop/index.md)找原理。
2. **按链条追问**——每读一个知识点，向上追问它服务于哪条价值，向下追问它会带来什么运维代价。
3. **把反馈写回来**——真实故障、性能瓶颈、被证伪的假设，都是从[运维](./maintenance/index.md)回流到前端的输入。
