# 需求变更控制

变更控制的目的不是减少变更，而是让每一次变更的**代价被看见**，由合适的人在有信息的前提下决定是否接受。

## 变更进入系统的处理流程

1. **登记**：无论来自哪个渠道，先落成文字，进入需求池。
2. **影响评估**：分析对范围、设计、数据、测试、交付时间的影响。
3. **决策**：由有权决定范围的人（而非提出者或实施者）决定接受、延后或拒绝。
4. **同步**：更新[基线](./traceability.md)，通知所有受影响的相关方。
5. **实现与验证**：作为正式需求走完整流程。

跳过第 2 步是这个流程最常见的失效方式——没有影响评估的决策，其实是在替团队做承诺。

## 影响评估要覆盖的维度

| 维度 | 要回答的问题 |
| --- | --- |
| 范围 | 是否引入新的功能面 |
| 设计 | 是否冲击既有架构约束 |
| 数据 | 是否需要结构变更或历史数据迁移 |
| 接口 | 是否破坏对外的[兼容性承诺](../analysis/nonfunctional/compatibility.md) |
| 测试 | 回归范围扩大多少 |
| 交付 | 是否影响已承诺的时间点 |
| 运维 | 是否新增部署、监控、容量负担 |

其中**数据与接口**两项最容易造成不可逆影响，需要格外慎重。

## 范围蠕变的识别

范围蠕变的特征是：每一次变更单独看都合情合理，但合起来使交付无限延后。识别信号包括：

- 「这个顺便也改一下吧」频繁出现；
- 迭代中新增的工作量持续超过计划量的两成；
- 交付日期连续推迟但没有人明确批准过延期。

应对方式不是拒绝变更，而是让变更**显式换出**：接一条新的，就要明确放弃或延后一条旧的。

## 实践建议

- 变更记录保留**决策理由**，而不只是结论。理由在未来比结论更有价值。
- 为不同量级的变更设定不同的决策门槛，避免小事走重流程导致团队绕过流程。
- 需求文档与实现不一致时，默认以**代码与测试**为事实，并立即回补文档——不要留下长期的分歧状态。
