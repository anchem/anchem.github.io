# 需求追踪与基线

需求追踪回答「**这条需求被谁实现、被谁验证**」；需求基线回答「**这一版我们承诺了什么**」。两者共同构成变更控制的判断依据。

## 追踪关系的三条链

| 链条 | 作用 |
| --- | --- |
| 需求 → 设计 | 确认每条需求都有方案承载，没有悬空 |
| 需求 → 代码 / 提交 | 确认实现范围，定位改动影响 |
| 需求 → 测试 | 确认每条需求都可验证，且测试覆盖到位 |

反向追踪同样重要：任何一处设计、代码或测试，都应当能回答「它服务于哪条需求」。答不上来的部分，往往是过度设计或历史残留。

## 追踪的实际收益

- **影响分析**：需求变更时，能在几分钟内定位所有受影响的实现与测试。
- **覆盖检查**：快速发现「写了但没测」和「测了但没需求」的部分。
- **审计与合规**：在受监管场景中，追踪关系是必备交付物。
- **交接效率**：新成员通过追踪关系理解系统，比读代码快得多。

## 成本与取舍

完整的手工追踪矩阵维护成本极高，且极易过期。实践中更可行的做法是：

- 用**需求的稳定编号**贯穿设计文档、提交信息、测试用例名称；
- 用工具自动从提交信息与测试名称中提取关联；
- 只对**关键需求**（监管、高风险、跨团队）做严格的全链路追踪。

## 需求基线

基线是某个时间点被正式确认的需求集合，是后续变更的比较基准。

- 基线一旦确定，变更必须走[变更控制](./change-control.md)；
- 基线要有版本号与生效范围；
- 基线不是冻结：它允许演进，只是演进需要留痕。

## 实践建议

- 让需求编号成为团队的公共词汇（「这个改动对应 R-231」），追踪就自然发生了，而不需要额外的矩阵维护。
- 每次发布固化一份基线快照，这是回溯问题时最有效的起点。
- 追踪关系应在自动化流程中生成与校验，人工维护的矩阵通常活不过三个月。
