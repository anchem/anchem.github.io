# 需求生命周期

需求不是一次性写入的常量，它有自己的生命周期。明确这条链路，才能知道在哪个环节该做什么动作。

## 典型阶段

```
提出 → 评估 → 纳入基线 → 设计 → 实现 → 验证 → 发布 → 演进 / 退场
```

| 阶段 | 关键动作 | 常见产出 |
| --- | --- | --- |
| 提出 | 进入[需求池](../analysis/sources.md)统一登记 | 原始诉求 + 来源 + 证据 |
| 评估 | 价值、成本、依赖、优先级判断 | 决策结论与理由 |
| 纳入基线 | 明确范围与验收标准 | 版本范围清单 |
| 设计 / 实现 | 形成方案与代码 | 设计文档、提交记录 |
| 验证 | 按验收标准确认 | 测试报告 |
| 发布 | 交付到真实用户 | 发布记录 |
| 演进 / 退场 | 变更、拆分或下架 | 变更记录、下线计划 |

## 两个容易被省略的阶段

### 退场

大多数团队有「加需求」的流程，没有「下需求」的流程。功能一旦上线就无人敢删，导致系统持续膨胀、维护成本单调上升。**退场应当与新增同等流程化**：谁来决定下线、如何通知用户、数据如何处置。

### 验证

需求被实现并不等于被满足。没有按验收标准做显式验证，需求就只是「代码写完了」。

## 状态可视化

需求应当有明确的状态标签（如：待评估 / 已接受 / 开发中 / 待验证 / 已上线 / 已下线），并在团队内可见。状态不清晰时，最常出现的对话是「这个做完了吗」——而这本不该需要问。

## 实践建议

- 每条需求保留从提出到退场的完整记录，这是后续做类似决策时最有价值的参考。
- 定期审视长期处于「开发中」的需求：卡住的原因通常不是工作量，而是依赖或决策未定。
- 把退场纳入常规迭代，为功能总数设定上限，倒逼清理。
