# 需求来源

需求不是被「收集」的，而是从多种来源中被**辨识**出来的。不同来源的可靠性差异极大，混在一起采信会严重误导判断。

## 常见来源与可靠性

| 来源 | 可靠性 | 说明 |
| --- | --- | --- |
| 用户实际行为数据 | 高 | 埋点、日志、工单量反映真实痛点 |
| 用户主动付费 / 迁移 | 高 | 付出了代价，是最硬的证据 |
| 一线客服与运营 | 较高 | 直面问题，但样本偏负面 |
| 结构化访谈 | 中 | 受提问方式影响大 |
| 竞品功能对比 | 中 | 只能说明别人做了什么，不能说明该做 |
| 内部头脑风暴 | 低 | 容易产生「想象中的用户」 |
| 单个大声用户的要求 | 低 | 音量不等于频次，可能是特例 |

## 采集时的两条纪律

### 记录场景，不记录结论

「用户希望有一键导出」是结论；「财务每月 1 号要手工从系统里抄 200 行数据到 Excel」才是场景。场景可以被重新求解，结论只能被实现。

### 记录频次与影响面

同样强度的抱怨，发生在 50% 用户身上和发生在 1 个用户身上，优先级完全不同。采集时就要带上「多少人 / 多频繁 / 代价多大」这三个维度。

## 需求池

所有来源的原始诉求应先进**需求池**统一登记，而不是直接进迭代计划。需求池的作用是提供缓冲区：让「有人提了」和「我们决定做」之间有一个显式的决策环节。

## 实践建议

- 对每个需求标注来源与证据强度。来源不明的需求标注为「假设」，需要先验证。
- 定期回看被拒绝的需求：其中一部分会随环境变化重新成立。
- 警惕**沉默的大多数**：不投诉的用户不代表满意，可能已经流失。
