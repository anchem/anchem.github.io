# 可用性

可用性（availability）描述系统**在需要时可以被访问的比例**。它是最容易写成数字、也最容易被误解的质量属性。

## 用「几个 9」表达

| 可用性 | 年停机时间 | 适用场景 |
| --- | --- | --- |
| 99% | 约 3.65 天 | 内部工具 |
| 99.9% | 约 8.8 小时 | 一般商业系统 |
| 99.99% | 约 52 分钟 | 关键业务 |
| 99.999% | 约 5 分钟 | 基础设施级 |

每多一个 9，成本通常上升一个量级。**要求 5 个 9 之前，先确认业务是否真的需要**：多数系统的停机损失远低于达成该目标的投入。

## 必须与业务共同定义的三件事

1. **什么算不可用**：完全无法访问，还是关键功能不可用？只读降级算不算？
2. **可用时间窗口**：凌晨维护窗口是否计入？对全球化业务，窗口可能不存在。
3. **计算口径**：按月、按季度，还是滚动统计？口径不同，同样的故障率结论完全不同。

口径没有定义清楚，可用性就是一笔糊涂账——故障后双方各拿一套算法。

## 提升可用性的手段

| 层面 | 手段 |
| --- | --- |
| 冗余 | 多副本、多可用区、多机房 |
| 隔离 | 故障域划分，避免级联失败 |
| 快速恢复 | 健康检查、自动重启、蓝绿发布、快速回滚 |
| 降级 | 牺牲非核心功能保住核心链路 |
| 组织 | 值班机制、预案演练 |

多数团队高估了冗余的价值，低估了**快速恢复**的价值：一个能在 30 秒内回滚的系统，比一个复杂但恢复缓慢的双活架构更实用。

## 实践建议

- 可用性目标必须落到[服务级别目标](../../../maintenance/operation/sla.md)上，并配套监控与告警。
- 「可用性 100%」不是目标，是拒绝设计。任何分布式系统都应当假设自己会失败。
- 明确写出**降级优先级**：核心链路、次要功能、非必要功能的顺序必须由业务确认。
