# 性能

性能描述系统处理请求的**速度与容量**。它是用户最直接感知到的质量属性，也是唯一「用户会用脚投票」的指标。

## 必须区分的三个量

| 指标 | 含义 | 为什么不能混用 |
| --- | --- | --- |
| 延迟 | 单次请求耗时 | 用户感受的是延迟 |
| 吞吐量 | 单位时间处理的请求数 | 系统容量看吞吐 |
| 资源占用 | CPU / 内存 / IO / 连接数 | 决定成本与可扩展性 |

三者互相制约：并发上去以后延迟通常变差。**只看平均值会掩盖长尾问题**，必须同时约束分位数。

## 可度量的写法

- 95 分位延迟：95% 的请求在 200ms 内返回。
- 峰值吞吐：在 500 QPS 下错误率低于 0.1%。
- 资源上限：单实例内存不超过 2GB。

只写「平均响应时间 200ms」是不够的：平均值正常而尾部炸裂，是线上最常见的真实故障形态。

## 影响性能的常见位置

1. **网络往返**：跨机房、跨服务调用次数。这是最大的放大器，减少一次远程调用往往胜过优化一整天算法。
2. **数据访问**：N+1 查询、缺索引、全表扫描。
3. **锁与串行化**：临界区过大、连接池过小。
4. **序列化与内存分配**：大对象、频繁 GC。

## 实践建议

- 先建立**基线**再谈优化。没有测量数据的性能优化，多数是凭直觉调参。
- 关注最慢的那 1% 请求，而非平均。长尾往往影响最多的用户总量。
- 性能目标要区分场景：登录路径与报表导出，指标不应当相同。
- 性能预算（performance budget）应写进需求，成为持续验证的项，而不是上线前一次性冲刺。
