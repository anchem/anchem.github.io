# 非功能性需求

非功能性需求（质量属性）描述系统**做得多好**，而不是做什么。它决定了系统能跑多远，却最常在需求阶段被整段省略。

## 包含内容

| 文档 | 含义 |
| --- | --- |
| [性能](./performance.md) | 多快、多大吞吐 |
| [安全](./security.md) | 抗攻击、防越权 |
| [可靠性](./reliability.md) | 长时间不出错的能力 |
| [可用性](./availability.md) | 需要时能用的比例 |
| [隐私保护](./privacy.md) | 个人数据的收集与使用边界 |
| [可维护性](./maintainability.md) | 改得动、改得快的程度 |
| [易用性](./usability.md) | 学得会、用得对的程度 |
| [可测试性](./testability.md) | 能被有效验证的程度 |
| [可演进性](./evolvability.md) | 适应变化而不推倒重来的能力 |
| [兼容性](./compatibility.md) | 与外部环境与旧版本共存的能力 |

## 为什么这类需求特别难

### 它们互相冲突

性能与安全冲突（加解密要花时间），安全与易用冲突（强口令难记），可维护性与性能冲突（抽象有开销）。因此非功能性需求**不能逐条独立确定**，必须作为一个整体做权衡。

### 它们事后几乎不可补救

功能可以加，性能瓶颈、数据模型、安全边界这类问题一旦定型，改动的代价常常等于重做。**唯一的防线是在需求阶段写下来。**

### 它们没有自然验收人

功能性需求有明确的使用者去验收；非功能性需求「没出问题」就是常态，出问题才被发现。因此必须显式指定指标与责任人。

## 怎么写才有效

非功能性需求必须是**可度量**的：

| 无效写法 | 有效写法 |
| --- | --- |
| 系统应响应迅速 | 95% 的查询请求在 200ms 内返回（不含网络） |
| 系统要安全 | 所有接口需鉴权；敏感字段落库加密；通过 X 项安全检查 |
| 系统要稳定 | 月度可用性不低于 99.9%，单次故障恢复不超过 30 分钟 |

## 与后续环节的衔接

- 指标会成为[运维](../../../maintenance/index.md)的服务级别目标；
- 约束会成为[软件架构](../../../develop/development/architecture/quality-attributes.md)的质量属性输入；
- 它们同时也构成[价值度量](../../../value/measurement/metrics.md)里质量类指标的定义。
