# 可演进性

可演进性描述系统**在需求持续变化时保持可控的能力**。它与其他质量属性的区别在于：它约束的是「未来的改动」，而不是当前的行为。

## 核心判断

> 系统会成为什么样子，取决于它有多容易被改。

可演进性差的系统有两个特征：**改动的影响面不可预测**，以及**改动之间互相阻塞**。前者让每次变更都变成赌博，后者让并行开发变成排队。

## 支撑可演进性的手段

| 手段 | 作用 |
| --- | --- |
| 稳定的边界 | 模块边界对应业务边界，变化被限制在局部 |
| 契约优先 | 接口先定，实现可替换 |
| 演进式设计 | 只对已确认的变化做设计，不预测未来 |
| 自动化回归 | 让改动敢做 |
| 数据演进策略 | 表结构、消息格式的兼容与迁移方案 |
| 灰度与开关 | 让变化可控地发布与回退 |

## 架构层面的兑现

可演进性主要由[软件架构](../../../develop/development/architecture/evolutionary-architecture.md)承载。演进式架构的核心主张是：把「支持变化的机制」显式设计出来，而不是指望设计一次到位。

具体来说包括：

- 用**适应度函数**（fitness function）自动化检查架构约束是否被破坏；
- 用**增量变更**替代大刀阔斧的重写；
- 对不可逆决策（数据模型、对外协议）投入更多前置思考，对可逆决策快速试错。

## 实践建议

- 区分**可逆决策**与**不可逆决策**，把决策成本与决策速度匹配起来。
- 每条需求都问一句：如果这版做错了，改成另一版要花多久？这个时间就是可演进性的实际度量。
- 谨慎对待「先用临时代码顶上」——临时方案一旦承载流量就没有下线的那天。
