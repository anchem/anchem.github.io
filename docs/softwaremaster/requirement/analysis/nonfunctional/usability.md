# 易用性

易用性描述用户**学习、使用并达到目标的有效程度**。它是用户价值的直接载体：功能正确但没人会用的系统，等于功能不存在。

## 可度量的写法

| 指标 | 含义 |
| --- | --- |
| 任务完成率 | 用户能否完成目标操作 |
| 任务耗时 | 完成核心任务所需时间 |
| 错误率 | 误操作的频次与恢复难度 |
| 学习成本 | 首次成功完成核心任务所需引导时长 |
| 满意度 | 主观评价，用作辅助信号 |

## 易用性的常见误解

- **把美观当易用**：视觉好看与操作顺畅是两件事。动画流畅不能弥补流程绕。
- **把简单当易用**：给专家用户砍掉必要能力，只是把复杂度转移给了他们。**易用是相对于用户群体而言的**。
- **只测内部人员**：熟悉系统的开发者感知不到新手障碍，必须用真实新手验证。

## 与系统设计的关系

易用性需求会反向约束后端设计。例如：

- 「重复提交不得产生重复数据」要求接口幂等；
- 「操作必须可撤销」要求状态可回滚；
- 「列表要能秒开」要求分页与索引。

这些问题在交互设计阶段提出来是设计约束，到实现阶段提出来就是返工。

## 实践建议

- 需求阶段就明确**核心任务路径**，并为核心路径设定明确的步骤数与耗时上限。
- 错误提示必须写进需求：出现错误时，用户看到什么、能做什么。
- 为**破坏性操作**明确确认或撤销机制，这是易用性与可靠性共同的要求。
- 上线前做最小规模的可用性测试，成本极低但能发现大量问题。
