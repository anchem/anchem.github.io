# 可维护性

可维护性描述**修改系统的成本**。它不产生任何用户可见的功能，却是决定软件长期盈利能力的关键质量属性。

## 为什么必须写进需求

大型软件的维护成本可以达到开发成本的四倍左右。可维护性差意味着：每次改动的理解成本高、回归风险大、上线周期长。这笔钱不会体现在开发报表里，但会持续从利润中扣走。

## 可度量的写法

| 指标 | 说明 |
| --- | --- |
| 变更前置时间 | 从确定需求到可上线的时长 |
| 缺陷修复时长 | 平均修复时间与修复波及范围 |
| 模块耦合度 | 修改一个模块连带需要改动的模块数 |
| 回归测试覆盖 | 改动后能自动验证的行为占比 |
| 上手时间 | 新成员独立完成一次改动所需时间 |

「可维护性要好」不是需求，「新成员能在两周内独立完成一次线上改动」才是。

## 影响可维护性的主要因素

1. **结构清晰度**：模块边界是否对应业务边界。边界不清，改动必然扩散。
2. **测试覆盖**：没有自动化测试的代码库，任何改动都是高风险操作。
3. **文档与命名**：命名承担了大部分文档职能，尤其重要。
4. **技术债水平**：债务要显式记录并偿还，否则会以利息形式持续消耗产能。

## 与其他质量属性的张力

可维护性常与[性能](./performance.md)冲突：为性能引入的特化逻辑、缓存、并行化，都会降低可读性。这类取舍需要显式记录，而不是默默倒向一侧。

## 实践建议

- 在需求阶段就约定**编码规范与评审机制**，并把它们作为验收的一部分。
- 为关键模块设定复杂度阈值，纳入流水线检查，避免持续劣化。
- 把「技术债偿还」作为常规迭代的固定配额，而不是等系统改不动了再专项治理。
