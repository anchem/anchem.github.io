# 安全

安全需求约束的是：**谁能做什么、数据如何被保护、攻击面有多大**。它与其他质量属性最大的区别是——存在主动的对手。

## 安全性目标的三个方面

| 方面 | 含义 | 手段举例 |
| --- | --- | --- |
| 机密性 | 数据不被未授权读取 | 传输加密、落库加密、最小权限 |
| 完整性 | 数据不被未授权修改 | 签名、校验、审计日志 |
| 可用性 | 服务不被恶意打断 | 限流、防重放、容量冗余 |

## 需求阶段必须确定的事

1. **身份与授权模型**：谁是谁，谁能做什么。授权规则要写在需求里，而不是留给开发在代码里即兴发挥。
2. **数据分级**：哪些是敏感数据、需要什么保护等级、保留多久、何时删除。
3. **信任边界**：哪些输入来自不可信来源。**所有跨边界输入都必须校验**。
4. **审计要求**：哪些操作必须留痕、留多久、谁能看。
5. **合规约束**：适用的法律法规与行业标准（等保、数据安全法、个人信息保护法等）。

## 常见误区

- **把安全当加固**：安全不是上线前加一层防护，而是从数据模型与权限模型开始的设计约束。事后加固通常是补丁叠补丁。
- **只防外部**：内部越权、横向移动往往造成更大损失。
- **依赖隐式约定**：security by obscurity 不成立，任何可被观察到的实现细节都应视为已公开。

## 与开发阶段的衔接

安全需求会落到三个地方：安全设计（[威胁建模](../../../develop/development/security/secure-design/threat-modeling.md)）、安全编码规范、安全验证。三者缺一，需求就只是文档。

## 实践建议

- 每条安全需求都指定**验证方式**：渗透测试、代码审计、配置核查，三者覆盖的问题不同。
- 把安全检查做进持续集成流程，避免成为上线前的紧急关卡。
