# 可靠性

可靠性描述系统**在规定条件下、规定时间内持续正确工作的能力**。它关心的是「出错的频率」，与[可用性](./availability.md)（「能不能用」）不同。

## 可度量的写法

| 指标 | 含义 |
| --- | --- |
| MTBF | 平均无故障时间 |
| 故障率 | 单位时间内的失效次数 |
| 数据正确率 | 处理结果与预期一致的占比 |
| 缺陷逃逸率 | 上线后发现的缺陷占比 |

## 可靠性的两个来源

### 避免故障

- 输入校验：所有外部输入都当作不可信。
- 边界处理：空值、超长、并发、重复提交。
- 依赖治理：超时、重试、熔断，明确降级行为。

### 承受故障

- 冗余：无状态化、多副本。
- 隔离：舱壁模式，避免一个模块拖垮整体。
- 幂等：让重试安全，这是分布式系统可靠性的基石。
- 补偿：明确失败后的回滚或对账机制。

**只做前者是不够的**：真实系统的可靠性主要来自对故障的预期与承受能力，而不是幻想不出故障。

## 与可用性的区别

| 维度 | 可靠性 | 可用性 |
| --- | --- | --- |
| 关注 | 出错的频率与正确性 | 可访问的时间比例 |
| 反例 | 每秒都返回错误数据 | 一年停 1 分钟但数据全对 |

一个可靠的系统不一定高可用（停机维护），一个高可用的系统不一定可靠（一直返回错误页）。

## 实践建议

- 把「部分失败」作为一等公民写进需求：依赖不可用时，用户看到什么？
- 对每一个外部依赖明确超时与重试策略，并写清重试是否幂等。
- 用混沌工程手段主动验证：不演练的容错设计，等于没有容错设计。
