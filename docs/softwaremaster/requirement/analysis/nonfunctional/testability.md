# 可测试性

可测试性描述系统**被验证的难易程度**。它是所有其他质量属性的放大器：测不出来的问题，等于不存在；测不出来的指标，等于没有指标。

## 可测试性的来源

| 层面 | 具体条件 |
| --- | --- |
| 结构 | 依赖可替换、边界清晰、状态可控 |
| 接口 | 有明确的输入输出契约，可独立调用 |
| 可观测 | 有日志、指标、链路追踪用于定位 |
| 环境 | 可重复搭建、可造数据、可回放流量 |
| 过程 | 有自动化回归与持续集成 |

## 不可测试的典型形态

- 逻辑与外部依赖硬编码耦合，无法在测试中替换。
- 状态藏在全局变量或静态方法里，测试之间互相污染。
- 缺少稳定的测试数据，每次测试结果不可复现。
- 异步与定时逻辑没有可注入的时间源。

这些问题的代价是长期的：**任何一次改动都只能靠手工回归和上线观察**，交付速度会被永久性拉低。

## 为什么它是需求而不是实现细节

「可测试性」一旦留到实现阶段考虑，代价会成倍上升。依赖注入、时间源抽象、接口契约这些东西必须在设计阶段决定。

因此可测试性应当作为需求明确下来，例如：

- 核心业务逻辑的单元测试覆盖率不低于 80%；
- 所有对外接口提供契约测试；
- 关键路径支持流量回放验证。

## 实践建议

- 把「如何验证」作为每条需求的必填字段。写不出验证方式的需求，先不要进开发。
- 在架构评审中把可测试性作为独立的评估维度，与性能、安全并列。
- 先建设自动化回归能力，再谈快速迭代——顺序颠倒会导致频繁回滚。
