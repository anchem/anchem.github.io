# 利益相关者

利益相关者（stakeholder）是对系统有诉求、能影响系统成败的所有角色。**需求的第一来源是相关方清单**——清单不全，需求必然遗漏。

## 常见的相关方类型

| 角色 | 典型诉求 | 容易被忽略的点 |
| --- | --- | --- |
| 最终用户 | 好用、快、少出错 | 用户内部还会分层：新手与专家诉求相反 |
| 业务方 / 出资人 | 收入、成本、合规 | 往往只看近期指标 |
| 运营与客服 | 可解释、可补救 | 决定了出问题时的处置空间 |
| 运维 / 平台团队 | 可部署、可观测、可扩容 | 需求写漏了，上线后必然返工 |
| 安全与审计 | 可追溯、有边界 | 事后审查最贵 |
| 上下游系统 | 接口稳定、约定明确 | 对方的约束常被当成我方实现细节 |
| 监管 / 法务 | 数据合规、留痕 | 具有一票否决权 |

## 相关方分析的三个动作

### 1. 列全

对每个角色问：**如果这个系统明天上线，谁会因此受影响？** 包括那些「不会被通知但会被影响」的人。

### 2. 排权

不是所有相关方的诉求权重相同。要明确：谁是决策者、谁是使用者、谁只是知情者。**说不清谁拍板，需求会在多方之间反复摇摆**。

### 3. 记冲突

相关方之间诉求冲突是常态而非例外（安全要留痕 vs 用户要简洁）。冲突要被记录下来，由决策者在明确代价后选择，而不是由工程师在实现时偷偷取舍。

## 实践建议

- 维护一份**相关方登记表**，记录角色、诉求、权重、联系人，随需求一起演进。
- 需求评审会必须覆盖主要相关方。缺席的角色，等于默认放弃其诉求。
- 对每个关键角色问一句：「你最担心这个系统上线后发生什么？」负面问题的答案往往比正面需求更具体。
