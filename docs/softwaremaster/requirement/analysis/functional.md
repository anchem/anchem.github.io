# 功能性需求

功能性需求描述**系统做什么**：在什么条件下、对什么输入、产生什么输出与状态变化。它是需求中最直观的一类。

## 一条好需求的结构

> 当【前置条件】时，系统【应当做什么】，结果是【可观察的输出】。

三要素缺一不可。常见的残缺形式是只写了动作（「系统应支持导出」），没写条件与结果，导致实现与验收各执一词。

## 要素拆解

| 要素 | 作用 | 缺失后果 |
| --- | --- | --- |
| 前置条件 | 界定触发场景 | 实现者自行想象使用方式 |
| 行为 | 描述系统动作 | 无法编码 |
| 输出 / 结果 | 提供验收依据 | 无法判断是否完成 |
| 异常分支 | 明确失败时怎么办 | 上线后大量未定义行为 |

其中**异常分支**是最常被忽略的部分。只写正常路径的需求，等于把错误处理的设计权交给了开发者的临场判断。

## 与其他需求的边界

功能性需求与非功能性需求**不能混在一条里**。「系统应在 1 秒内返回导出结果」包含两件事：导出这个功能（功能性），以及 1 秒的响应约束（非功能性）。混写的后果是排期时只估了功能，性能目标被顺带漏掉。

## 实践建议

- 每条需求给一个稳定编号，便于在[变更控制](../management/change-control.md)与[需求追踪](../management/traceability.md)中引用。
- 需求描述中避免出现实现手段（数据库、框架、接口协议），除非该手段本身是约束。
- 写完一条需求，试着让另一个人只凭文字复述它。复述不一致的地方就是歧义所在。
