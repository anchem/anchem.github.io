# 需求：做什么

需求把[价值](../value/index.md)翻译成**可建造的东西**。它回答的是：为了让那件有价值的事真的发生，系统必须做什么。

需求阶段的产出质量，几乎决定了后面所有环节的上限。需求错一点，架构要放大它，代码要延长它，测试会被它拖住，最终用户会为它付代价。反过来，一个表述精确的需求能让设计、实现、验证各环节独立推进而不跑偏。

## 需求的两大类

| 类型 | 内容 | 特点 |
| --- | --- | --- |
| 功能性需求 | 系统做什么，输入输出是什么 | 容易写，容易改，容易验证 |
| [非功能性需求](./analysis/nonfunctional/index.md) | 做得多好：性能、安全、可靠、可维护 | **难写、代价高、事后无法补救** |

工程中最常见的事故不是功能做错，而是非功能性需求从头到尾没有被写下来。系统「跑得起来」和「跑得下去」是两件事，后者必须在需求阶段就被约束。

## 一条判据

写不出**验收方式**的需求，还不能叫需求，只能叫愿望。每条需求都应当能回答：怎么知道它被满足了？
