# 领域模型

领域模型用**业务概念及其关系**表达需求，目的是建立业务方与技术方共用的**统一语言**。

## 为什么需要它

同一个词在不同角色嘴里含义不同，是软件项目最隐蔽也最昂贵的成本来源。在销售眼里「客户」是签合同的人，在客服眼里「客户」是来投诉的人，在财务眼里「客户」是应收账款的承担者。如果代码里只有一个 `Customer`，业务规则迟早会打起来。

领域模型的作用就是把这些区分显式化。

## 核心构件

| 构件 | 含义 | 例子 |
| --- | --- | --- |
| 实体 | 有唯一标识、生命周期内身份不变 | 订单、用户 |
| 值对象 | 无标识、由属性定义 | 金额、时间段、地址 |
| 聚合 | 一致性边界，整体保存整体修改 | 订单及其明细 |
| 领域服务 | 不属于单个对象的重要业务规则 | 定价计算 |
| 领域事件 | 业务上已发生的事实 | 订单已支付 |

## 与数据模型的区别

领域模型描述**业务概念与规则**，数据模型描述**存储结构**。两者价值不同，不能互相替代：

- 只有数据模型，业务规则会散落到各个服务里，无法定位。
- 只有领域模型，无法落地存储。

实践中二者常常相似，但刻意让它们保持独立，能在业务规则复杂时保留清晰的边界。

## 与用例的关系

[用例](./use-case.md)描述「谁在什么时候做什么」，领域模型描述「这个东西是什么、规则是什么」。前者是行为视角，后者是结构视角，二者构成完整的表达。

## 实践建议

- 建模时坚持使用**业务原话里的词汇**，而不是技术术语。术语一旦被替换，沟通就断了。
- 把「这个词到底指什么」的讨论结果记录下来，形成术语表，成为团队的共有资产。
- 领域模型不应一次画完。它随业务理解的深化持续演进，这与[可演进性](../analysis/nonfunctional/evolvability.md)的要求一致。
