# 用例

用例（use case）以**参与者达成某个目标**为单位描述系统行为，并要求写出主流程之外的分支与异常。它的强项是**完整覆盖**。

## 组成要素

| 要素 | 说明 |
| --- | --- |
| 参与者 | 触发交互的角色或外部系统 |
| 前置条件 | 开始时必须成立的状态 |
| 主流程 | 顺利情况下的步骤序列 |
| 备选流程 | 主流程之外的合理分支 |
| 异常流程 | 失败情况的处理 |
| 后置条件 | 结束后系统应处的状态 |

其中**备选与异常流程**是用例最有价值的部分——写功能清单时最容易漏掉的正是这些。

## 何时值得写用例

- 流程有明确的多步骤与角色分工；
- 存在大量分支与异常路径；
- 需要与其他系统交互，时序重要。

不适合的场景：交互简单的增删改查。为它们写完整用例，投入产出比很低。

## 与其他模型的关系

- 用例描述**交互**，[领域模型](./domain-model.md)描述**概念**，两者互补。
- 用例的粒度大于[用户故事](./user-story.md)。一个用例常常拆成多个故事来实现。

## 实践建议

- 用例名称必须包含目标（「提交报销单」），而不是动作（「点击提交」）。
- 异常流程要写到「用户看到什么、系统留下什么痕迹」，否则实现者会自行简化。
- 避免把用例写成界面操作步骤——那会把交互设计提前锁死。
