# 用户故事

用户故事是以**角色 + 价值**为单位的轻量需求表达，属于敏捷实践中组织迭代的常用载体。

## 标准句式

> 作为【角色】，我希望【做某事】，以便【获得某种价值】。

第三段是重点，也是最常被省略的一段。省掉它，故事就退化成任务，失去判断优先级的依据。

## 3C 结构

| 要素 | 含义 |
| --- | --- |
| Card | 卡片本身：简短的一句话描述 |
| Conversation | 围绕卡片的讨论：细节在对话中澄清 |
| Confirmation | 确认标准：怎样算完成 |

**卡片是对话的引子，不是需求的全部。** 把细节全部塞进卡片，会得到既冗长又仍然不完整的文档。

## 验收标准

每个故事必须有可检验的验收标准，常用 Given / When / Then 形式：

- Given 已登录且购物车非空
- When 点击结算
- Then 生成订单并跳转支付页，购物车清空

验收标准写不出具体结果，说明这个故事还没有准备好进入开发。

## INVEST 原则

Story 应当满足：Independent（独立）、Negotiable（可协商）、Valuable（有价值）、Estimable（可估算）、Small（足够小）、Testable（可测试）。

其中最重要的是 **Small**：过大的故事无法在一个迭代内完成，也就无法获得反馈。

## 实践建议

- 故事只写「要什么」，不写「怎么做」。技术方案由团队在对话中确定。
- 用[优先级方法](../analysis/prioritization.md)排序故事，而不是按提出顺序实现。
- 故事完成后应能追溯到[价值主张](../../value/user/value-proposition.md)，形成闭环。
