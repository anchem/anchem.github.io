# 需求建模

需求建模解决的是**表达问题**：把散落在访谈、工单、数据里的诉求，固化成可以被讨论、被评审、被验证的形式。

## 包含内容

- [用例](./use-case.md)：以「参与者 + 目标」为单位的完整交互描述
- [用户故事](./user-story.md)：以「角色 + 价值」为单位的轻量需求卡片
- [领域模型](./domain-model.md)：以业务概念及其关系为单位的结构表达

## 三种模型各自的定位

| 模型 | 强项 | 适合的场景 |
| --- | --- | --- |
| 用例 | 完整覆盖交互与异常分支 | 业务流程清晰、逻辑复杂的系统 |
| 用户故事 | 轻量、便于排序与迭代 | 需求变化快、需要持续交付 |
| 领域模型 | 统一语言、承载业务规则 | 业务规则密集、需要长期演进 |

三者不是竞争关系。实践中常见的组合是：用领域模型统一概念，用用户故事组织迭代，对复杂流程补用例细化异常分支。

## 建模的共同价值

1. **暴露遗漏**：一旦要画出完整流程，缺失的分支会自己浮现。
2. **统一语言**：让业务方与技术方用同一套词汇，减少翻译损耗。
3. **支撑追踪**：模型中的每一项都可以成为[需求追踪](../management/traceability.md)的锚点。

## 一条纪律

模型是**沟通工具**，不是交付物。画模型的目的是让相关方达成一致，因此应当尽量轻、尽量早、尽量可改。追求完备而精致的模型文档，往往在完成时就已经过期。
